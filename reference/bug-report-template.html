Keep the two triage arguments separate

Severity Priority
How badly does this hurt stakeholders or requirements? When should this fix compete against other work?
Data loss, blocked work, affected users, workaround Release timing, exposure, dependencies, opportunity
Say: Severity is ___ because ___ loses / cannot ___. Say: Priority is ___ because it must land before ___; meanwhile ___.

Labels are team policy, not universal constants. Recommend both with evidence; let the project’s triage owner make the queue decision.

First-try gate

  • The title identifies one failure and proposes no unproved solution.
  • The exact build and relevant environment are named.
  • The starting state, actor, role and concrete data can be recreated.
  • The numbered steps are minimal and name the actual interface.
  • Actual and expected results are independently observable.
  • The expected result names its oracle or reference.
  • Evidence supports the path instead of replacing it.
  • Observed facts are visibly separate from hypotheses.
  • Severity has an impact reason; priority has a scheduling reason.
  • One issue gets one report.

Source boundary

ISTQB CTFL v4.0.1 §5.5 supplies the report objectives, workflow and field checklist. Mozilla’s Bug Writing Guidelines supply the practical rules for precise summaries, steps, actual and expected results, and separating observations from speculation. Neither source provides a universal severity or priority scale.
