Lesson 2 · Foundations

Where a test belongs, and what kind it is

Two questions that sound like vocabulary drill, and are actually about catching bugs where they are cheap.

Plan: covers QA-005 Test levels, and the black-box / white-box half of QA-004 · weeks 2–3 · coverage map

By the end of this lesson you will be able to take any test and say which level it belongs at and what type it is — and explain why moving it to a different level would cost more or find less. You will also stop confusing confirmation testing with regression testing, which interviewers ask about constantly.

1. Two independent questions

People new to QA mash these together. They are separate axes, and keeping them separate is most of the skill.

Test level Test type
Answers How big a piece am I testing, and when? Which quality aspect am I asking about?
ISTQB wording “Groups of test activities that are organized and managed together” “Groups of test activities related to specific quality characteristics”
Example System testing Performance testing

They combine freely.ISTQB CTFL v4.0 §2.2. The syllabus is explicit that test types can be applied at every test level — which is why “performance testing is a system-level thing” is wrong. “Performance testing of a single component” is a perfectly good sentence: level = component, type = non-functional. So is “functional acceptance testing”. Think grid, not list.

2. The five levels

Level What is under test Usually done by Typical defect it catches
Component One unit in isolation Developers Wrong calculation inside a function
Component integration Components talking to each other Developers Wrong data passed between two modules
System The whole assembled product Testers End-to-end flow breaks; requirement not met
System integration Your system plus external systems Testers Payment gateway rejects your request format
Acceptance Fitness for use, by the people who asked for it Users, customer, product owner It works, but it is not what they needed

The syllabus distinguishes levels by five things: approach, responsibilities, objectives, test basis, and the defect types found. That last one is the practically useful one — each level catches a class of bug the others structurally cannot. A component test cannot find a bug in how two components talk. A system test can, but by then the bug is more expensive to trace.

The point of levels

Levels are a cost argument, not a taxonomy. A defect caught at component level costs minutes; the same defect surfacing in acceptance testing costs a meeting. When someone asks “why bother with unit tests?”, this is the answer — and it connects straight to ISTQB principle 3, early testing saves time and money.

3. The four types

Type The question Example
Functional What does the system do? Does a 30% tip cap actually reject 31%?
Non-functional How well does it do it? Does the tip submit in under two seconds under load?
Black-box Based on behaviour, without looking at the code Derive tests from the spec
White-box Based on the internal structure Derive tests to cover every branch

Non-functional maps onto the quality characteristics you met in the risk triage card — performance, security, reliability, usability and the rest. That is not a coincidence: types and risks use the same axes. When you score a risk on “security”, the test that addresses it is security testing.

4. Confirmation vs. regression

After any change — a fix or an enhancement — two different questions need answering, and they are not the same question.

Confirmation testing Regression testing
Asks Did the fix actually work? Did the fix break anything else?
Scope The one thing that was broken Everything the change could have touched
Test used Re-run the steps from the bug report Re-run existing tests around the change
Automate it? Usually not worth it — runs once Yes — this is the strongest case for automation, because it repeats forever

A memory hook that survives interview pressure: confirm the fix, regress the rest.

Sort them

Each of these is a real test someone might run. Put it at the level where it belongs.

Carry this into an interview

“At what level would you test this?” is a favourite question because it exposes whether you think about cost. A strong answer names the level and the reason:

I’d test that at level, because the defect I’m hunting lives in — testing it later would still find it, but by then .
