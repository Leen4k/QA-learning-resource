Pair each development work product with the test work that challenges it, then preserve the evidence from requirement to result.

1. Same staged project, different testing promise

An SDLC model is a high-level representation of how development phases relate logically and chronologically. The current ISTQB syllabus places both Waterfall and the V-model among sequential development models. It also warns that the chosen lifecycle changes the timing, scope, documentation, automation, and responsibilities of testing.ISTQB CTFL v4.0.1 §2.1 and §2.1.1, pp. 24–25. A model is an abstraction; a project’s actual history can contain review, feedback, and rework.

In the classic Waterfall model, requirements, design, coding, and testing are shown one after another. Test execution waits until the developed system exists. The dangerous reading is “testers wait.” Even in a sequential lifecycle, the current syllabus says testers typically join requirement reviews, analysis, and test design before executable code is available.

The V-model makes that early work visible. The left arm refines the product from user need toward detailed design and implementation. The right arm tests increasingly complete objects. A line across the V pairs each development work product with the test level whose cases are derived from it. This lesson uses one common four-pair reference V; it is a teaching view, not a rule that every project or artifact must fit only one level.

How the classic Waterfall and reference V-model views differ
Question Classic Waterfall view V-model view
What moves? Work passes through requirements, design, code, test, operation. Work refines down to code, then testable objects assemble upward.
When is testing visible? Dynamic execution appears as a later project phase. Analysis and design begin beside the matching development work.
What must link? Each completed phase hands work to the next phase. Each test level traces back to the basis that defined correctness.
Main risk Late execution can expose requirement or design problems after costly work. A neat diagram can hide iteration, weak bases, and broken trace links.

Waterfall asks, “What phase comes next?” The V-model adds, “Which test activity challenges this work product, and what evidence will connect them?”

2. Read the V as four evidence pairs

A test basis is the work product or knowledge used to derive tests. A business requirement can be a basis for acceptance testing; an interface design can be a basis for integration testing. If the basis is vague, the matching test will inherit the ambiguity.

Testware is the output of test activity. Before execution it includes conditions, cases, data, procedures, environments, and schedules. After execution it includes logs, defect reports, completion reports, and other work products. Stakeholders use those results to make decisions; this lesson does not treat the decision itself as an ISTQB testware category. Here, evidence is the ordinary-language umbrella for reviewed bases, planned testware, and observed results.ISTQB CTFL v4.0.1 §1.4.3, pp. 19–20. The syllabus says names, shape, organization, and detail vary by context.

This lesson’s reference V: four example evidence pairs
Development work product Reference test level Plan while descending Observe while ascending
User or business requirement Acceptance testing Acceptance criteria, user workflow, acceptance case User outcome, acceptance record, deployment decision
System requirement or behavior model System testing End-to-end conditions, system cases, environment needs System log, result, defect, requirement coverage
Architecture, interface, or sequence design Integration testing Contract checks, interface data, failure-path cases Request trace, message/log evidence, interface defect
Detailed component design, code, or data model Component testing Focused cases, component data, and any needed substitute dependency Focused test result, decision-table coverage, component defect

The historical syllabus supplies these as example test bases in §§2.2.1–2.2.4; it does not prescribe one universal diagram. Teams can rename, combine, overlap, or repeat levels. The durable rule is the relationship: the test has a named basis, and its result can be traced back to that basis. An artifact can inform several levels; classify it by the primary test object and objective in the stated context.

Do not turn the V into two waiting lines

“Acceptance testing is on the far right” does not mean acceptance cases should be invented last. Current ISTQB good practice says test analysis and design for a level begin during the corresponding development phase. Execution waits for a testable object; thinking, review, data, environment, and case design do not.

5. Traceability turns a change into a bounded question

ISTQB defines traceability across test-basis elements, testware, results, and defects. It supports coverage evaluation and change-impact analysis. If Teamspace changes the rule so Admins may invite only from the UI, start at BIZ-INV-01 and follow links to every derived requirement, interface contract, case, result, and open defect. Do not search by the word “invite” and hope.

A traceability trap

One requirement-to-acceptance-result link can answer a narrow coverage question, but it does not expose the lower-level derivation shown in this reference V. If change-impact analysis is the objective, link the system behavior, interface contract, and component decision too. Trace depth should serve the question, not decorate a dashboard.

The historical caveat

The 1970 Royce paper commonly associated with Waterfall draws a staged flow, then immediately calls that implementation “risky” and describes late testing forcing disruptive redesign. Later it treats current documentation as tangible evidence of completion. Keep both ideas: a documented staged model can make decisions inspectable, but the diagram does not prove real work proceeds once, cleanly, without feedback.Royce, pp. 328–333, immediately after Figure 2 and around Figure 6. The paper does not use the term V-model or define this lesson’s four reference pairs.

Self-check before handoff

  • One requirement ID anchors every derived link.
  • Each pairing fits the reference V, or explains a different test object and objective.
  • The descending side contains reviewed bases and planned testware.
  • The ascending side labels recorded observations as evidence and keeps expected results separate.
  • Every right-arm result names the same implementation anchor.
  • The trace supports one explicit coverage or change-impact conclusion.
  • The conclusion admits that real work can iterate outside the neat V.
