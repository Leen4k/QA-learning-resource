Lesson 7 · Test management

Test cases someone else can run

Turn coverage targets into concrete, traceable instructions — then hand the suite to a tester who was not in the room.

Plan: completes QA-007 Test cases and scenarios — write 10–15 cases for one flow, covering normal, invalid, and boundary inputs · week 4 · coverage map

By the end of this lesson you will have a 12-case Teamspace role-management suite: every case names its starting state, concrete action and observable result, and every case earns its place by tracing to a decision rule, transition, boundary, or interface risk.

Start from the model, not the number

Lesson 6 found five decision rules and four valid state transitions. Those are the first nine coverage targets. The request for “10–15 cases” is a delivery constraint, not a technique; risk justifies the three extra cases.

1. Separate what to test from how to run it

A test condition is a testable aspect identified during test analysis: a rule, transition, risk, or other coverage target that answers what should be examined? “A sole Owner cannot demote themself” is a condition. It is not yet runnable. ISTQB CTFL v4.0.1 §1.4.1 places test conditions in analysis and asks “what to test?”

A test case turns one or more conditions into a concrete example: a known starting state, an action with specific data, and an observable expected result. It answers how will we test this? A test procedure then puts cases into an executable order, including setup, reset, and cleanup. ISTQB §1.4.1 separates design (elaborate conditions into cases) from implementation (organise cases into procedures and suites). §4.5.3 says natural-language cases include the necessary preconditions, inputs and postconditions.

Artifact Question it answers Teamspace example
Condition What deserves examination? R1: a role change must not leave zero Owners
Case How will one example exercise it? TC-01: Olivia, the sole Owner, tries to become Admin in the UI
Procedure In what order can the cases be run? Reset Base A; run denial cases; reset; run live-session cases

The handoff test: if another tester must ask which account, which starting state, which action or data, or what they should observe, the case is not ready to hand off.

2. Use a small case contract

The syllabus does not prescribe a test-case spreadsheet. For this course, use five fields because each prevents a common handoff failure:

Field What belongs there Weak version to reject
ID A stable name such as TC-07 “the permissions test”
Covers The rule, transition, boundary, or risk that earns the case “role changes”
Precondition Actor, data and state that must exist before the action “log in as an Owner”
Action + data Interface, target and concrete value or event “change the role”
Expected result An observable response and the state that must remain afterward “works correctly”

Keep actual result, pass/fail status, evidence and defect ID in an execution record. They describe a particular run; they are not part of the reusable design. This separation prevents yesterday’s result from masquerading as tomorrow’s expectation.

3. Make the test basis concrete

A runnable case cannot be more precise than its oracle. The Teamspace rule sheet from Lesson 6 now has this small interface contract. These details are part of the worked feature, not claims from ISTQB:

  • Role changes use PATCH /api/teamspaces/redwood/members/{id}/role with {"role":"ADMIN"} (or another role).
  • An allowed change returns 200 and the new role. An unauthorised change returns 403 FORBIDDEN_ROLE_CHANGE.
  • A change that would leave zero Owners returns 409 LAST_OWNER. The UI explains that ownership must be transferred; the stored role does not change.
  • Removal uses DELETE .../members/{id} and returns 204. Permissions are rechecked on the next request, even from an already-open session.
  • Invitations use POST .../invitations. An Admin receives 201; a Member receives 403 INSUFFICIENT_ROLE. A removed member’s workspace request returns 403 MEMBERSHIP_REQUIRED, and the UI shows that access was removed.

Reset the seeded workspace before each independent case. The names and IDs below make short preconditions unambiguous:

The boundary pair is TC-01 and TC-03: one Owner is the smallest valid workspace state, while two Owners is the nearest value from which one may safely step down. TC-02, TC-04 and TC-12 are not padding. They add the two-interface and stale-authorization risks from the test plan. The other nine cases cover every Lesson 6 rule and valid transition at least once.

7. Keep the case set honest

A scripted case is a repeatable check and a useful handoff or regression artifact. It is not proof that testing is complete. James Bach and Aaron Hodder argue that counting created or executed cases is a poor proxy for testing progress: cases can guide specific checks, while investigation, learning and noticing still require a tester.

That tension improves the artifact. Traceability tells you what the suite covers; the uncovered-risk note tells you what it does not. For this suite, concurrent role changes, re-invitation after removal, accessibility and performance remain outside the 12 cases. Name them rather than letting a green pass count imply they vanished.
