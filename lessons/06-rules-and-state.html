Lesson 6 · Test management

When the rules interact

Decision tables for combinations; state transitions for history. Two compact models for the cases a list of input values cannot reach.

Plan: covers the modelling step behind QA-007 Test cases and scenarios — write 10–15 cases for one flow · week 4 · coverage map

By the end of this lesson you will have turned the Teamspace permissions requirement into two coverage models: five combination rules and four valid role transitions. Lesson 7 can then turn those nine justified targets into instructions another person can run. No guessing a round number of cases first.

The Teamspace rule sheet

Owners may change any role. Admins may change roles only when both the current and requested roles remain below Admin. Members and Viewers may not change roles. A change that would leave the workspace with no Owner is blocked until ownership is transferred.

An Owner may promote a Member to Admin, demote an Admin to Member, or remove either one. The new role must apply immediately to an already open session. Removed membership is terminal for this model; re-invitation belongs to a different flow.

1. Ask what makes the outcome change

Lesson 5 split one input into equivalence partitions and tested their edges. That works when one value can be judged largely on its own. It does not answer either of these questions:

  • May an Admin change a Member to Viewer, and what if the same actor targets an Owner?
  • May a person who was an Admin a moment ago still invite people through a tab that was already open after they are demoted?

The first outcome changes because several facts combine. The second changes because something happened before. Carry this sentence:

If the outcome depends on , table the rules. If it depends on , model the states.

2. Decision tables: combinations become columns

A decision table records conditions and resulting actions as rows. Each column is a decision rule: one unique combination of conditions together with the actions that combination should produce. The technique is designed for business logic where conditions interact. It can expose combinations that prose quietly omitted or contradicted. ISTQB CTFL v4.0.1 §4.2.3. FL-4.2.3 is a K3 objective: use a decision table to derive coverage, rather than merely define one.

A dash means that condition cannot change the outcome for this rule. It is how columns with the same action are safely merged. Here is the Teamspace rule sheet made testable:

Conditions and actions R1 R2 R3 R4 R5
Actor is Owner T T F F F
Owner change would leave no Owner T F – – –
Actor is Admin – – T T F
Admin change stays below Admin – – T F –
Require ownership transfer first X
Apply role change X X
Deny role change X X

The table gives five coverage targets: one feasible scenario per column. R1 is deliberately separated from the ordinary Owner path. Without that column, a perfectly tested Owner path can still delete the final owner; without R5, the same attempted change by a Member could receive the wrong explanation. The risk ranking from lesson 1 tells you which column to execute first; the table tells you which columns exist.

Where the table earns its keep

Four Boolean conditions produce sixteen raw combinations. Six produce sixty-four. §4.2.3 allows infeasible columns to be deleted and columns whose conditions do not affect the outcome to be merged. Do that openly: a dash must mean “irrelevant to this outcome,” not “I forgot to decide.”

3. State transitions: the same event, a different past

A state is the situation the system is in that matters to what it may do next. A state transition is the move from one state to another after an event. State transition testing is useful when the same event can produce a different result because the starting state is different. A state table makes both valid and invalid moves visible; blank cells are questions the prose requirement often hides. ISTQB CTFL v4.0.1 §4.2.4. The syllabus treats a state table as equivalent to a state diagram, with the advantage that invalid transitions are shown explicitly.

Starting state Owner demotes to Member Owner promotes to Admin Owner removes membership
Admin Member; open session loses Admin actions Invalid: already Admin Removed; open session loses workspace access
Member Invalid: already Member Admin; open session gains Admin actions Removed; open session loses workspace access
Removed Invalid: no membership to demote Invalid: invitation is required first Invalid: no membership to remove

Valid transitions coverage means exercising every valid arrow at least once. One sequence may cover several arrows, so four transitions do not automatically require four separate runs. Visiting every state is weaker: you can reach Admin, Member and Removed while still skipping one of the ways between them. All-transitions coverage goes further and also attempts invalid moves; §4.2.4 recommends isolating invalid moves so one failure cannot mask another.

4. Practice: pick the model before making cases

Interleave the three techniques you now know. Ask what changes the outcome: one value, a combination, or prior history.

5. Practice: cover every valid transition with less work

The state model has four valid transitions: Admin to Member, Member to Admin, Admin to Removed, and Member to Removed. Choose as few sequences as possible while covering all four. There is more than one correct minimal answer; the checker grades coverage rather than matching one preferred set.

6. Your handoff to Lesson 7

You now have nine coverage targets before writing a single procedural step: decision rules R1–R5 and the four valid role transitions. Copy the two tables into your Teamspace artifact and add one line beneath each:

Table coverage is feasible rules exercised out of . Valid-transition coverage is arrows exercised out of .

That is a defensible basis for the plan’s role-and-action grid. It is not proof that permissions are defect-free. It says exactly what this model covered, leaving room for risk-driven exploration of the UI/API mismatch and stale sessions.
