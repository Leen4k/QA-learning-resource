Lesson 3 · Foundations

Finding bugs before the code exists

Static testing: the cheapest defects you will ever catch are the ones still sitting in a sentence.

Plan: no matching task — static testing is a whole ISTQB chapter the 52-task plan skips. Kept because reviewing requirements is the cheapest testing there is · coverage map

By the end of this lesson you will be able to read a user story and name the specific ways it will hurt someone — ambiguous wording, missing cases, claims nobody can verify — and turn each one into a question worth asking in refinement. This is the highest-leverage thing a tester does, and it needs no software at all.

1. Testing without running anything

Static testing means examining a work product without executing it — either by hand (a review) or with a tool (static analysis).ISTQB CTFL v4.0 §3.1. Nearly any readable work product qualifies: requirement specifications, source code, test plans, test cases, product backlog items, contracts, models. Nearly anything readable can be reviewed. If it can be misunderstood, it can be tested.

There is one distinction here worth memorising word for word, because it is the cleanest idea in the whole syllabus:

Static finds defects. Dynamic finds failures.

Static testing identifies defects directly. Dynamic testing produces a failure, and then someone has to work backwards to find the defect that caused it. Same bug, but one route hands it to you and the other makes you hunt.

That is why static testing is cheap. Add the rest of the ISTQB case for it: it catches defects at the earliest phases of the lifecycle; it finds things dynamic testing structurally cannot, such as unreachable code; it can assess qualities that have nothing to do with execution, like maintainability; overall project cost is usually much lower where reviews happen; and it builds shared understanding among stakeholders.

That last one is underrated. Half the defects you prevent in a refinement meeting were never defects in the code — they were two people confidently reading the same sentence differently.

2. What you are actually looking for

“Review this story” is useless advice without a target. Four failure modes cover most of what goes wrong in written requirements:

Fault Tell The question you ask
Ambiguous A word two people would read differently — fast, recent, user-friendly, appropriate What number would make this true?
Incomplete The happy path is described and nothing else. No error case, no empty case, no limit What happens when it fails or when there are none?
Unverifiable A claim with no observable outcome — the system should be intuitive How would we know, from the outside, that this holds?
Contradictory Two statements that cannot both be satisfied, often in different documents Which of these wins, and who decides?

Notice all four are answerable with a question, not an objection. That matters socially: you are not marking someone’s homework, you are surfacing a decision nobody has made yet.

3. How reviews are actually run

Reviews come in four formality levels. You will be asked to compare them.

Type Formality Led by Feel
Informal review Minimal Nobody in particular “Can you look at this?”
Walkthrough Low to moderate The author Author talks the group through it
Technical review Moderate to high A designated leader Peers examine it, findings documented
Inspection Highest A moderator Checklists, defined roles, metrics collected

The process itself has five activities: planning, review initiation, individual review, communication and analysis, then fixing and reporting.ISTQB CTFL v4.0 §3.2, following ISO/IEC 20246. Principal roles: manager, author, moderator, scribe, reviewer, review leader. The one people skip is individual review — everyone reads it alone, first. Skip that and the meeting becomes the loudest person’s opinion.

One success factor is worth calling out because it is a rule about people, not documents: reviews need clear objectives and measurable exit criteria, and evaluating the participants is explicitly excluded. A review that becomes a judgement of the author stops producing findings immediately.

Review this story

Here is a real-shaped backlog item. Each highlighted phrase has something wrong with it. Name the fault.

The story under review

As a customer, I want to tip my driver after delivery so that I can reward good service.

Acceptance criteria: the tip screen appears promptly after delivery; the customer can enter a tip amount; the tip is charged to the card on file; tipping should feel effortless; the driver is notified.
