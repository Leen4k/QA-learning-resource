Lesson 9 · Test management

Bug reports that get reproduced first try

Turn an observed failure into a report another person can reproduce, judge and act on without a meeting first.

Plan: QA-009 Defect reporting and triage · week 5 · deliverable: five sample bug reports with severity and priority reviewed separately · coverage map

By the end of this lesson you will be able to write five Teamspace bug reports a developer can reproduce on the first try, then defend two different judgements: how badly each failure hurts, and when each fix should compete for attention.

The feature under test

Continue with Teamspace, the permissions feature from lessons 6–8. Owner, Admin, Member and Viewer roles must be enforced in both the web UI and REST API. Role changes should affect an already signed-in user immediately. This lesson begins where Lesson 7 ended: a case failed, and somebody who was not in the room now needs the evidence.

1. Report the failure, not the code you imagine

ISTQB separates the causal chain: people make errors, errors create defects in work products, and executing some defects causes observable failures. A defect report records an anomaly for investigation; the process may later decide it is a real defect, a false positive, or a change request.ISTQB CTFL v4.0.1 §1.2.3 and §5.5. The cautious word is anomaly: when filing, you know what you observed, not necessarily its root cause.

That distinction decides how to write. “The permission cache is broken” is a diagnosis you may not be able to prove. “A demoted Admin sent an invitation and the API returned 201” is an observation another person can reproduce. Mozilla’s reporting guidance makes the same practical demand: separate observed facts from speculation, and give each issue its own report.

In , starting from , when , I observed ; I expected because .

Rapid Software Testing shifts the centre of gravity. Michael Bolton calls a bug anything about a product that threatens its value to people who matter. ISTQB’s field list asks you to record impact; Bolton asks you to name whose value is threatened. Keep both voices visible: the fields make the report operable, while the value argument makes it worth acting on.Michael Bolton, You’ve Got Issues, lightly edited 2025. ISTQB CTFL v4.0.1 §5.5 gives three informational objectives for a report; Bolton frames reporting as raising awareness of threats to value.

2. The first-try reproduction contract

ISTQB §5.5 lists eleven kinds of report content. A tracker may supply the ID, date, author and initial status automatically; you still own the facts that make reproduction possible. Compress the list into these seven questions:

Question Write this Failure it prevents
What failed? A short title naming condition, action and visible failure “Permissions broken” cannot be searched or routed
Which thing? The test object: product, component and exact version or build The developer tests a build where the failure never existed
Where? The test environment: URL, OS, browser or client, account role and relevant configuration “Works on my machine” ends the investigation
Starting from? Preconditions, account state and concrete test data The same actions begin from a different state
What actions? Numbered, minimal steps naming controls, endpoints and values The developer follows your intention, not your actual path
What mismatch? Actual result, expected result and the oracle behind the expectation A symptom is visible, but nobody can agree it is wrong
What proves it? Frequency, response, log, screenshot or recording, plus references One image replaces the steps instead of supporting them

Mozilla calls the steps the most important part because they let a developer trigger the failure and later tell whether it was fixed. Its guidance adds details §5.5 does not teach: state whether reproduction is reliable or intermittent, describe the interaction rather than only its intent, minimise the path, and separate the actual result from the expected result.

Title: [condition] + [action] + [failure].
Steps: begin at the first state that matters; stop at the first visible failure.
Evidence: supports the steps; it never replaces them.

4. One report, worked

This example comes from Teamspace’s highest-ranked permissions risk: the UI hides an action but the API fails to enforce the same rule. Notice that the report says nothing about which source-code module is wrong.

BUG-TS-014 · Open

Title. Viewer DELETE request removes a page despite read-only role.

Observed. 15 Aug 2026 by Wathna, QA. Reproduced 3/3.

Test object. Teamspace staging 1.8.0; API build 7ac91d.

Environment. staging.teamspace.example; Chrome 126 on macOS 14.5; REST API v1; workspace redwood.

Precondition. Vic u-401 is a Viewer with a newly issued token. Page p-184 exists. Olivia u-101 is Owner.

  1. Sign in as Vic and open page p-184.
  2. Confirm the UI offers no Delete action, then send DELETE /api/pages/p-184 with Vic’s token.
  3. As Olivia, request page p-184.

Actual. DELETE returns 204; Olivia’s GET returns 404; the audit entry names Vic as the actor.

Expected. The DELETE is denied with the product’s standard authorization response and page p-184 remains available. Teamspace rule R5 makes Viewer read-only.

Evidence. Attached request/response pair, audit entry ae-771, and 18-second recording. No customer data used.

Severity recommendation: High. A read-only user can permanently remove shared content belonging to the workspace.

Priority recommendation: P1. The vulnerable endpoint is enabled in tomorrow’s release candidate and users have no way to protect a page from a known Viewer token.

References. Risk R1; Teamspace permission rule R5; test case TC-API-11.

The title can identify the report in a search result. The precondition makes Vic’s role and token freshness explicit. Each step names an actor, interface and object. Actual and expected results are independently observable. The impact and scheduling arguments use different evidence. That is the whole contract.

5. Severity is not priority

Severity is the degree of impact a defect has on stakeholder interests or requirements. Priority is the order and importance of fixing it relative to other work. ISTQB defines the first and merely lists the second; Mozilla’s live Bugzilla field guide makes the split concrete.ISTQB CTFL v4.0.1 §5.5; Mozilla BMO User Guide, Severity and Priority fields. Mozilla uses S1–S4 and P1–P5, but those scales belong to Mozilla, not to every team.

Severity Priority
Question How badly does this hurt people or requirements? When should this fix compete against other work?
Evidence Data loss, blocked work, affected users, workaround Release timing, exposure, dependencies, fix opportunity
Stable? Usually stable while the impact remains the same Changes when schedules and business context change
Owner Reporter recommends; triage confirms by team policy Product and engineering decide against the work queue

This is a spacing callback to Lesson 1. Severity resembles the impact dial after a failure has occurred; it is not likelihood and it is not the old risk score. Priority is a scheduling decision informed by that impact plus release context. A low-severity typo on tomorrow’s launch screen can be P1. A high-severity failure in a disabled migration tool can wait until before that tool is enabled.

Severity is because is unable to / loses .
Priority is because it must be fixed before ; meanwhile .

Defect triage is the team’s step of analysing and classifying a report, then deciding the response: fix, defer, reject, mark duplicate, request information, or close. Your labels are a reasoned recommendation, not unilateral truth. Mozilla goes further and asks reporters to leave its severity default for component triagers; that is a project rule, and a useful reminder to learn the ownership model of the tracker you are using.ISTQB CTFL v4.0.1 §5.5 describes the workflow from logging through analysis, classification, response and closure. Mozilla BMO User Guide, Severity, says reporters should not set that field.

6. Exercise: turn both dials

Use Teamspace’s local scale: Low / Medium / High severity and P3 / P2 / P1 priority. The reference calls are not universal facts. A one-level difference is marked defensible; read the reasoning and decide whether yours is stronger.

8. The handoff gate

A report is ready when another person can answer all of these without contacting its author:

  • Which exact build and environment should I use?
  • Which starting state, account, role and data must exist?
  • What is the shortest numbered path to the failure?
  • What did the product do, and what observable result was expected?
  • Which evidence supports the path, and how often did it reproduce?
  • Who is harmed enough to justify severity?
  • Which deadline, exposure or dependency justifies priority?
  • Did the report keep observation separate from diagnosis?

You can carry the same gate into any tracker. The field names will change; the information contract does not. The printable bug-report handoff sheet holds the template without the teaching around it.

The interview move

“Tell me about a good bug report you wrote” is asking whether you can move evidence across a team boundary. Answer in the same order a developer consumes the report:

I observed in build under . The minimum reproduction was ; actual was , expected was based on . Severity was because ; priority was because .

Finish with one detail you removed. “I left the suspected cache cause out because I had not proved it” demonstrates more judgement than a screenshot count ever will.
