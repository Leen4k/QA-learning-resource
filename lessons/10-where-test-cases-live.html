Lesson 10 · Test management

Where test cases live

Compare how TestRail, qTest and Zephyr turn reusable cases into executions and evidence, then choose one for a real workflow.

Plan: QA-008 Test management tools · week 4 · deliverable: compare TestRail, qTest and Zephyr, then say which one you would try first and why · coverage map

By the end of this lesson you will be able to map the same Teamspace cases, execution scope and results into all three tools, then write a short choice note whose reason is about your team’s work rather than a vendor’s feature count.

Source boundary

There is no neutral primary source for comparing three commercial products. This lesson uses each vendor’s documentation only to describe its own object model, then uses the same Teamspace workflow as the comparison test. Product claims, pricing and popularity are deliberately excluded. The plan’s roadmap.sh link names the topic but does not teach this comparison.

SmartBear renamed Zephyr Scale to Zephyr and Zephyr Squad to Zephyr Essential. Here, “Zephyr” means the current Jira product whose documentation models a test library, test cycles and test plans—the successor to Zephyr Scale.

1. Compare the job, not the screenshots

A test management tool is software that helps a team organise testing work and its evidence. ISTQB’s entire product-independent description is one bullet: management tools can make the test process more efficient by supporting the lifecycle, requirements, tests, defects and configuration.ISTQB CTFL v4.0.1 §6.1, Tool Support for Testing. The syllabus defines the category; it does not compare TestRail, qTest or Zephyr.

That broad definition becomes useful when you ask three concrete questions. A test repository answers where reusable test-case definitions live. An execution scope answers which of those cases are being run, against what build and environment. A result answers what happened this time, who observed it, and what evidence was saved.

2. The same work, three object models

The products share a broad flow—define reusable cases, select work for an execution, record outcomes—but their nouns are not interchangeable. Read each arrow as containment or derivation, not as a claim that the labels mean the same thing.

Tool Where cases live How execution is organised Where outcomes appear
TestRail Project → repository or suite → sections → test cases A run selects cases from a suite. A plan can create related runs for configurations such as browsers. The run contains one test per selected case; each test receives a result such as Passed, Failed, Retest or Blocked.
qTest Test Design → Modules → Test Cases Release → Test Cycle → Test Suite → Test Runs. One qTest Test Run is one executed instance of a Test Case. TestPad records step status, actual results, notes, attachments and defects for the run, then saves the execution history.
Zephyr Jira project → test library folders → test cases A test cycle groups cases for a goal. A test plan can group cycles for a release or version. Executing a case creates an outcome linked to its cycle, including status and execution context; plan reporting aggregates linked cycles.

These paths come from the vendors’ own object documentation: TestRail, Introduction to TestRail → Test cases and sections, Test runs and tests, and Test plans and configurations; Tricentis qTest, Introduction to qTest Objects → Objects in Test Design and Objects in Test Execution; SmartBear Zephyr, Test Plans (overview) → The Role of Test Plans in Zephyr.

The naming trap

In TestRail, a run contains tests derived from selected cases. In qTest, a Test Run is a single executed instance of one Test Case, while a Test Suite groups runs. In Zephyr, the comparable group is usually a test cycle. A migration that matches objects only by name can map one group to one item.

The testing did not change. Only the storage grammar changed. That is why a useful comparison starts with one identical workflow and asks how much translation, duplication and administration each model creates.

5. Choose by friction you can observe

A feature matrix encourages imaginary needs. A short trial reveals the work your team will repeat. Enter three cases, execute them in two environments, fail one, attach evidence, link a defect, rerun it, and export what you would need if you left. Then compare these five axes:

Axis Question to answer with evidence
Workflow fit Does the model match how the team already plans releases and tracks defects?
Authoring cost How many fields and containers must exist before one useful case can run?
Execution clarity Can a tester see build, environment, assignment and remaining work quickly?
Evidence quality Can a reviewer trace a result to its case, requirement, defect and attachment?
Exit cost Can cases, results, links and attachments be exported in a usable form?

The repository model can have consequences. TestRail documents three project types; a multiple-suite project cannot combine cases from more than one suite in one run, and moving cases during a conversion can remove results from active runs. That is a better trial question than “Does it have dashboards?”TestRail, Projects and their types → Projects with test suites and How to change from one project type to another. Read the migration cautions before choosing a repository type.

Three defensible first trials

Try TestRail first when you want a dedicated, section-based case repository and a direct suite-to-run model.

Try qTest first when releases, requirements, design and a deeper cycle/suite execution hierarchy are part of the problem you need to model.

Try Zephyr first when Jira is already the team’s daily workspace and keeping cases, cycles, plans and delivery issues together is the constraint that matters.

These are hypotheses for a trial, not universal rankings. Your choice is defensible when it names the constraint, the documented object model that fits it, and the small experiment that could prove you wrong.

The counterweight: a result count is not a testing story

The vendors are designed around stored, countable cases and their outcomes. Michael Bolton challenges the premise that case counts describe testing well. His argument is not that a repository is useless; it is that scripted cases can hide the tester’s modelling, risk analysis and investigation, and that turning effort into case counts creates “no end of mischief.”Michael Bolton, Breaking the Test Case Addiction, Part 1, especially Traceability and Sharing efforts with stakeholders.

Keep both views. The tool should preserve repeatable checks, assignments and evidence. Your report must still explain which risks shaped the sample, what exploration happened outside the scripts, what was not tested, and why the remaining uncertainty is acceptable. Lesson 1 supplied the risk language; Lessons 7 and 9 supplied the traceable cases and defect evidence.
