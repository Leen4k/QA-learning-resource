Lesson 5 · Test management

Fewer tests, same coverage

Equivalence partitioning and boundary value analysis — the two techniques that turn “try some values” into a defensible number.

Plan: covers the technique behind QA-007 Test cases and scenarios — “normal, invalid, and boundary inputs” · week 4 · coverage map

By the end of this lesson you will be able to take a field with rules on it and produce a short list of test values, then say exactly why each one is in the list and why the ones you left out are redundant. This is the single most common whiteboard exercise in junior QA interviews.

1. Equivalence partitioning: why one value stands for many

A tip field accepts amounts from $0.00 to $6.00. How many values do you test? There are 601 of them. You test roughly four.

Equivalence partitioning divides the input data into groups whose members the system should treat identically. The syllabus states the assumption it rests on plainly: if a test case detects a defect, that defect should also be detected by test cases using any other value from the same partition.ISTQB CTFL v4.0 §4.2.1. Learning objective FL-4.2.1 is K3 — use the technique to derive test cases, not just describe it. Interviewers know this and will ask you to do it. So one value per partition is normally enough.

The mistake almost everyone makes first: partitioning only the valid values. Invalid inputs form partitions too, and they are where the interesting failures live. For our tip field:

Partition Valid? One value from it
Below the minimum Invalid −2.00
Within range Valid 3.00
Above the maximum Invalid 9.00
Not a number at all Invalid “abc”
Nothing entered Invalid (empty)

Coverage here is measurable: partitions exercised ÷ partitions identified. That is the sentence that turns your test set from a guess into a number you can defend — the same move you learned in lesson 1, applied to values instead of risks.

2. Boundary value analysis: where the bugs actually are

Partitioning tells you how many tests. It does not tell you which value to pick from each partition. Boundary value analysis does, and it picks the values most likely to fail.

The reasoning is about how people write code. Boundaries are where developers get it wrong: the implemented boundary ends up above or below where it was meant to be, or is left out altogether. That is a > that should have been >= — and it is invisible everywhere except at the edge.

One restriction worth remembering

BVA applies only to ordered partitions — ones where, if two values belong to the partition, everything between them does too. Numbers and dates qualify. “Not a number” does not: there is no edge of abc. So non-ordered partitions still get exactly one value, chosen by judgement.

There are two accepted depths, and knowing both is worth marks:

2-value BVA 3-value BVA
You test The boundary, and its nearest neighbour across the line The boundary, and the neighbour on each side
At max $6.00 6.00, 6.01 5.99, 6.00, 6.01
Catches A misplaced or missing boundary The same, plus an off-by-one in the other direction
Use when Default. Cheaper, and catches most boundary defects The boundary carries real risk — money, limits, access

Combine the two techniques and the choice of values makes itself: use partitioning to decide how many tests, and boundaries to decide which values. You end up with a handful of tests that are individually justifiable.
