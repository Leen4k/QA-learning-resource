# QA-040 — Vulnerability scanning and secrets

> Dossier, not lesson content. Every claim below must be re-read at source
> before it ships in a lesson.

- **Verdict:** WRONG-DOCUMENT
- **Named source:** https://owasp.org/www-project-top-ten/
- **Best primary source:** NIST SP 800-115, *Technical Guide to Information Security Testing and Assessment* (Sept 2008) — https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-115.pdf
- **Exact sections to read:** NIST SP 800-115 **§4.3** (pp. 4-4→4-6) · **§6.5–6.6** (6-10→6-12) · **§7.1–7.2** (7-1→7-3) · **§7.4 incl. 7.4.1–7.4.4** (7-4→7-7) · **Appendix B** (B-1→B-2). Then two operating manuals: ZAP *Baseline Scan* (https://www.zaproxy.org/docs/docker/baseline-scan/) and the gitleaks README (https://github.com/gitleaks/gitleaks).
- **Read time:** ~65 min (15 pp NIST ≈ 45 min, + ~20 min for the two tool docs)

## a. Does the named source cover this?

**No — and it is not a near miss.** The OWASP Top Ten is a taxonomy of *what can be
wrong*; this task is about *how to operate a scanner without hurting anyone, and how
to look after what falls out of it*. Different genre. The named URL is worse than the
document behind it: it is a **project landing page that does not even list the ten
categories** — just the self-description (*"a standard awareness document for
developers and web application security"*, *"the first step towards more secure
coding"*), translations, data-contribution process, sponsors. "Awareness" is OWASP's
own word and it is accurate.

Checked the closest category directly (**A02:2021 Cryptographic Failures**, renumbered A04
in the 2025 edition). It asks *"Are crypto keys checked into source code repositories?"* and
maps **CWE-259** and **CWE-321** — the question this task exists to answer, posed
rhetorically with no method attached. Its *How to Prevent* section never mentions scanning
or names a tool.

Against the DELIVERABLE it supplies none of the three verbs: **run** a scan, scan
**safely**, **protect the evidence**. Nothing on scanner operation, credential handling
during a scan, traffic volume or DoS risk, or where scan output lives afterwards. A
learner who reads all ten categories can name ten risk families and still cannot point
a tool at anything.

## b. Best primary source

**NIST SP 800-115** — free, standards body, and the only document I found that treats
scan output as *sensitive material with a lifecycle* rather than as a report:

1. **§4.3** — credentialed vs uncredentialed scanning, false-positive rates, network
   load, built-in DoS tests.
2. **§6.5–6.6** — who must say yes before you start.
3. **§7.1–7.2** — what to do when the scan trips the incident response team, which it will.
4. **§7.4 Data Handling** → **7.4.1 Collection**, **7.4.2 Storage**, **7.4.3
   Transmission**, **7.4.4 Destruction**. This *is* "protect the evidence," clause by
   clause. Read it twice.
5. **Appendix B — Rules of Engagement Template.** This *is* "document exactly how I
   would scan," pre-structured.

NIST gives zero commands: pair it with **ZAP's baseline-scan doc** and the **gitleaks
README** for the hands-on half — both short, both verified below.

## c. What it leaves out

- **It is 2008 and NIST files it under `/Legacy/`.** Appendix A's recommended toolkits are
  **BackTrack** and **Knoppix STD**, both long dead. Nothing on CI/CD, containers,
  dependency/SCA scanning, or cloud.
- **"Secrets" has no home in it.** Credentials committed to source control are never
  discussed — no rotation, no revocation, no git history. The second noun of this task's
  title is simply absent; hence gitleaks in §e.
- **How to supply scan credentials safely.** §4.3 notes some scanners hold
  *"administrator-level credentials on individual hosts"* and moves on — never says
  where that credential lives, that the scanner config file is now the most valuable
  file on the network, or that it should be scoped and rotated. The learner's stated
  worry, unanswered.
- **The report itself contains the secrets.** §7.4.2 says encrypt assessment data, never
  that a gitleaks report is a *plaintext list of live credentials* (hence `--redact`).
- **CI breaks §7.4.2's storage model.** NIST wants findings on media *"isolated physically
  or logically from day-to-day network resources"*, access *"limited to those individuals
  whose access is needed."* Then a pipeline writes the same findings to a build log, a PR
  comment, and an artifact bucket the whole org can read. Name that collision — it is the
  modern form of the failure NIST warns of.

## d. Credible disagreement

**1. The discrete engagement vs the pipeline.** NIST §7.2: *"The plan or ROE should be
followed unless specific permission to deviate has been obtained, normally in writing, from
the original signatory."* No CI job has a signatory. The practitioner position: per-run
authorisation paperwork for scanning your own pre-prod app on every commit is theatre — the
standing authorisation is the pipeline config, and control moves from paperwork to blast
radius (scan a disposable environment, never prod). Teach it as: NIST's *artifacts* don't
survive the move to CI, its *questions* do. Two that get dropped and shouldn't — Appendix B
§4's **"exclude list"** and §2.2's off-hours rule.

**2. Secrets: "detect and fix" vs "assume compromised and rotate."** The scanner-driven
instinct says a gitleaks hit is a bug: delete the line, rewrite history, done. **GitHub's
docs contradict this flatly** — *"as a first step you need to revoke and/or rotate that
secret,"* because after a force-push the commits *"may still be accessible elsewhere: In
any clones or forks of your repository, Directly via their SHA-1 hashes in cached views on
GitHub, Through any pull requests that reference them."* The line to end on: **a secrets
finding is not a defect to fix, it is an incident to rotate.** Reinforced by gitleaks'
pre-commit hook being bypassable by design — `SKIP=gitleaks git commit`.

**3. Scanner severity is not your risk.** NIST half-concedes it (§4.3: *"the risk
levels assigned by a scanner may not reflect the actual risk to the organization"*).
Empirical counter: FIRST's EPSS, https://www.first.org/epss/articles/prob_percentile_bins
— but **attribute carefully.** FIRST does not assert the headline as its own finding; it
collates vendor claims (Kenna/Cyentia *"less than 2%"*, Fortinet *"5.7%"*, Tenable
*"3%"*, NopSec *"3.4%"*) and summarises *"only around 5% of all vulnerabilities are ever
exploited in the wild."* Cite as a vendor range, not as fact.

*Unverified lead:* Bach/Bolton (RST) on scan reports as *checking* output — on-topic, but
**I did not fetch developsense this session.** Do not quote it yet.

## e. Worked examples worth adapting

- **The safe local scan, end to end — commands verified this session.** Target: OWASP Juice
  Shop, built to be scanned (*"…a guinea pig for security tools"*) — `docker run
  bkimminich/juice-shop`. Scanner: `docker run -v $(pwd):/zap/wrk/:rw -t
  ghcr.io/zaproxy/zaproxy:stable zap-baseline.py -t <url> -g gen.conf -r testreport.html`.
- **Make "safe" mean something.** Baseline *"doesn't perform any actual 'attacks'"* — spider
  plus passive only, one minute by default. ZAP on the other mode: *"Active scanning is a
  real attack on those targets and can put the targets at risk…"* Run baseline, then make
  the learner write one sentence on what a clean baseline does and does not prove. That is
  the lesson. Gate it: exit 0 success · 1 ≥1 FAIL · 2 ≥1 WARN no FAIL · 3 other.
- **The evidence lesson, felt not told.** Run `gitleaks git --report-path
  gitleaks-report.json`, open the report, find live secrets sitting in it in plaintext.
  Re-run with `--redact`. Then ask where the first file would have gone in CI. Follow with
  `--baseline-path` and `.gitleaksignore` for triage.
- **The written deliverable, if they can run nothing.** A one-page ROE off Appendix B:
  §1.2 Scope, §1.4 Risks, §2.2 Test Schedule (off-hours), §2.3 Test Site, §3.2 Incident
  Handling, §4 Target System/Network **with the exclude list**, §5 Testing Execution.
- **The activity-log exercise.** Log NIST §7.4.1's minimum fields (date/time, assessor,
  assessment system IP or MAC, target IP or MAC, tool, command, comments) for NIST's own
  reason — the log *"allows the organization to distinguish between the actions of
  assessors and true adversaries."* Your scan pages the SOC at 2am: can you prove it was you?

## Verbatim quotes

*ZAP, gitleaks, GitHub, EPSS, NIST §7.2 and App. B are quoted inline in §a–§e.*

**NIST §4.3:** "vulnerability scanners can have a high false positive error rate (i.e.,
reporting vulnerabilities when none exist)." · "it tends to generate significantly more
network traffic than port scanning. This may have a negative impact on the hosts or
network being scanned." · "Many vulnerability scanners also include network-based tests
for DoS attacks that, in the hands of an inexperienced assessor, can have a marked
negative impact on scanned hosts. Scanners often allow all DoS attack tests to be
suppressed."

**NIST §7.4.2 — the evidence-protection core:** "In the hands of an adversary,
information regarding network architecture, system configuration, security controls, and
specific system vulnerabilities would provide a blueprint and roadmap for exploiting the
organization's information systems." · media "should be isolated physically or logically
from day-to-day network resources"; access "limited to those individuals whose access is
needed"; "encrypted in compliance with FIPS 140-2." **§7.4.4:** "Disposal", "Clearing",
"Purging", "Destruction" — "Simple deletion of items does not suffice for clearing."

**NIST §6.6:** "captured data may include sensitive data that does not belong to the
organization—or personal employee data, which may create privacy concerns."
