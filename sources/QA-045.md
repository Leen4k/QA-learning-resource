## a. Does the named source cover this?

**Half of it — the deliverable half — and only if the learner navigates away
from the page you linked.** `docs.github.com/en/actions` is an index: its entire
prose is one sentence (see quotes) and the rest is headings. Nobody learns
anything here; replace the link. Three clicks deeper, GitHub **does** fully
cover the deliverable — fetched this session, `actions/upload-artifact` gives
`retention-days`, `if-no-files-found`, and the `!cancelled()` condition that
makes the report survive a red run, i.e. the whole "runs a smoke suite and keeps
the report as an artifact" sentence.

**What GitHub never covers is the stated learning goal.** "Which checks should
be *allowed* to block a release" is a judgment question; GitHub documents only
the mechanism. Nothing in its docs says which checks earn that power, what a
check must be worth before it stops a release, or what to do when the blocking
check is wrong. A learner finishing docs.github.com can build the gate and has
no basis for deciding what belongs behind it. That gap is the lesson.

## b. Best primary source

**Fowler, *Continuous Integration*** — the canonical free document on which
checks run where and why, answering the goal through the deployment-pipeline
idea: multiple builds in sequence, with the commit build as the one gate
everyone waits on. Self-testing build, ten-minute build, revert-don't-fix are
the actual criteria for "allowed to block." Pair with **continuousdelivery.com →
Patterns** (Humble; two paragraphs, defines the commit stage and the
stop-the-line rule) and **DORA → Test automation**, the sharpest sentence here:
a test may block only if its failure means a real defect. **MinimumCD**
(beyond.minimumcd.org/docs/reference/practices/) supplies the vocabulary. For
the deliverable, **Playwright's CI page** matches this learner's stack
(Playwright/TypeScript by QA-042) with a complete, correct workflow.

## c. What it leaves out

- **Nobody names the smoke-suite selection rule.** Fowler says fast, DORA says
  reliable; neither says *which* journeys. Write that rubric.
- **`always()` vs `!cancelled()`.** The *Expressions* page warns against
  `always()`; the artifacts tutorial mentions neither — so a learner who reads
  only the tutorial drops the report on failure, the case it exists for.
- **What happens when a gate fires and is wrong.** Nothing covers the social half:
  who may bypass, how an override is recorded, when a check is demoted from
  blocking to advisory. That is most of the real job.
- **Retention.** `retention-days` maxes at 90 and cannot exceed the org limit, so
  evidence can expire before the audit that needs it.
- **Artifacts are not reports.** Nothing says a zipped `playwright-report/` must
  be downloaded and unzipped to be read, so a gate whose evidence nobody opens is
  the default outcome.

## d. Credible disagreement

**RST vs. the premise of an automated gate.** Bach & Bolton
(satisfice.com/blog/archives/856) split *testing* — evaluating a product by
experiencing, exploring and experimenting — from *checking*, "the mechanistic
process of verifying propositions about the product." A CI gate is 100%
checking, and their conclusion challenges this task's framing directly:
**"Quality is an opinion, not a fact, so quality cannot be verified."** A green
pipeline is not evidence of releasability; it is evidence that a fixed set of
pre-stated propositions still hold. What nobody thought to check is invisible.

**MinimumCD says the opposite by design:** *Definition of Deployable* is
"automated criteria that determine when a change is ready for production" and
*Single Path to Production* is "all deployments flow through one automated
pipeline - no exceptions" — a deliberate transfer of the release decision to a
machine. Do not blend these. Honest framing: the gate answers *"has anything we
already knew to watch for broken?"* — mechanical, cheap, worth blocking on. It
does not answer *"is this good?"* Make the learner say which one theirs answers.

## e. Worked examples worth adapting

- **The skipped-check deadlock — a real, reproducible defect story from GitHub's
  own docs.** A workflow requires a successful `build` job but runs only when a
  PR touches `scripts`; a PR changing only a root file never triggers it and is
  "blocked with 'Waiting for status to be reported.'" The merge button is dead
  forever; GitHub's advice is blunt — "Avoid requiring workflows that can be
  skipped." **Build the bug, watch the PR hang, then fix it.** It teaches the
  goal better than prose: a blocking check must be one that always reports.
  Callout: a *workflow* skipped by path filter stays Pending and blocks; a *job*
  skipped by an `if:` conditional "reports 'Success'" and does not.
- **Break the test, lose the report.** Run the smoke suite with an unconditional
  artifact step, fail one test, watch the upload never run. Add
  `if: ${{ !cancelled() }}` and re-run — one diff teaches all three conditions.
- **Playwright's CI workflow is the deliverable, near-verbatim** —
  `on: push/pull_request` for main, `timeout-minutes: 60`, `npm ci` →
  `npx playwright install --with-deps` → `npx playwright test` →
  `actions/upload-artifact@v5` with `if: ${{ !cancelled() }}`,
  `retention-days: 30`. Adapt, don't invent.
- **`if-no-files-found` drill.** Default is `warn`: misspell the path and the job
  stays green with nothing uploaded. Set `error` — a gate that cannot notice its
  own evidence going missing is not a gate.
- **Ten-minute-build audit.** Time the smoke suite; if it exceeds Fowler's budget,
  cut tests until it fits and record what was cut and where it moved. That list
  *is* the answer to "which checks should block."

## Verbatim quotes

**The named page, complete prose:** "Automate, customize, and execute your
software development workflows right in your repository with GitHub Actions. You
can discover, create, and share actions to perform any job you'd like, including
CI/CD."

**GitHub, *Troubleshooting required status checks*:** "Associated checks stay in
a 'Pending' state and block merging." · "Avoid requiring workflows that can be
skipped." · "A pull request that only changes a file in the repository root will
not trigger this workflow. If `build` is required, the pull request is blocked
with 'Waiting for status to be reported.'" · a job skipped by a conditional
instead "reports 'Success'". · *About protected branches*: "Required status
checks must have a `successful`, `skipped`, or `neutral` status before
collaborators can make changes to a protected branch."

**GitHub, *Expressions* → Status check functions:** `always()` "Causes the step to
always execute, and returns `true`, even when canceled." · "Avoid using `always`
for any task that could suffer from a critical failure" — use `if: ${{ !cancelled() }}`.

**`actions/upload-artifact` README:** `if-no-files-found` — "warn: Output a
warning but do not fail the action / error: Fail the action with an error message
/ ignore: Do not output any warnings or errors… Default is 'warn'". ·
`retention-days` "Maximum 90 days unless changed from the repository settings page."

**Fowler, *Continuous Integration*:** "The idea behind a deployment pipeline… is
that there are in fact multiple builds done in sequence." · "Usually the best way
to fix the build is to revert the faulty commit from the mainline." · "the XP
guideline of a ten minute build is perfectly within reason." **·
continuousdelivery.com, *Patterns*:** the commit stage "creates deployable
packages and runs automated unit tests and other validations such as static code
analysis" and is "optimized so that it takes only a few minutes to run." · "If
this initial commit stage fails, the problem must be fixed immediately—nobody
should check in more work on a broken commit stage."

**DORA, *Test automation*:** "Tests should be reliable: that is, when the tests
pass we should be confident the software is releasable, and test failures should
indicate a real defect." · "don't tolerate flaky tests" **· Bach & Bolton
(satisfice.com/blog/archives/856):** checking is "the mechanistic process of
verifying propositions about the product." · "Quality is an opinion, not a fact,
so quality cannot be verified." · "Checking is a tactic of testing."
