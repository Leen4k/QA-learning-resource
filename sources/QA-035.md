# QA-035 — Auditing one page for keyboard, focus, labels and contrast

> Dossier, not lesson content. Every claim below must be re-read at source
> before it ships in a lesson.

- **Verdict:** WRONG-DOCUMENT
- **Named source:** https://webaim.org/intro/
- **Best primary source:** W3C WAI — *Easy Checks – A First Review of Web Accessibility* — https://www.w3.org/WAI/test-evaluate/preliminary/
- **Exact sections to read:** "Scope"; "Using these Easy Checks"; "Contrast ratio (color contrast)"; "Keyboard access and visual focus"; "Forms, labels, and errors"; "Next steps"
- **Read time:** ~45 min

## a. Does the named source cover this?

No. `webaim.org/intro/` is an awareness essay about *what* accessibility is. It
states principles to implement, never procedures to test. On labels: "Every form
element (text field, checkbox, dropdown list, etc.) needs a
programmatically-associated label" — and it stops there. No "press Tab", no
threshold, no tool, no way to tell pass from fail. The want is "checks I can
perform"; this page yields zero checks. A fine 10-minute orientation worth
linking as a prerequisite — but right site, wrong page. WebAIM's own procedural
pages (`/techniques/keyboard/`, `/resources/contrastchecker/`) do the work.

## b. Best primary source

**WAI Easy Checks.** Purpose-built for this deliverable, W3C-authored, free, no
account. Its own framing — "You can do most of these checks with any browser,
that is, you do *not* need to download special tools" — is verbatim the
learner's constraint. Sections map 1:1 onto the four items:

- Keyboard access + Focus → "Keyboard access and visual focus" (SC 2.1.1, 2.1.2,
  2.4.7 — focus is the "Visual focus" bullet inside the keyboard section)
- Labels → "Forms, labels, and errors" (SC 1.3.1, 3.3.2)
- Contrast → "Contrast ratio (color contrast)" (SC 1.4.3)

Supporting, free, fetched this session: WebAIM Contrast Checker
(https://webaim.org/resources/contrastchecker/ — browser-based, no install, hex
in → ratio + AA/AAA verdicts for normal text, large text, and 3:1 for graphics
and UI components); WAVE (https://wave.webaim.org/ — URL field plus
Chrome/Firefox/Edge extensions) as an automated baseline to diff against.

## c. What it leaves out

- **It is stale.** Footer: "Updated: 9 August 2023" / "Major revision planned for
  late 2023" — not landed as of this fetch. It names IE and Opera, the pre-Ventura
  macOS "System Preferences > Keyboard > Shortcuts" path, and Web Developer
  Toolbar / IE WAT. Retarget to current browsers and the DevTools colour picker.
- **WCAG 2.1 only.** WCAG 2.2 (Oct 2023) added two criteria squarely on the
  "focus" half of this deliverable: **2.4.11 Focus Not Obscured (Minimum)** (AA)
  and **2.4.13 Focus Appearance** (AAA). Easy Checks' focus test is only "you can
  tell which element has focus" (2.4.7) — it passes a focus ring hidden behind a
  sticky header, and passes a 1px hairline outline. Both are common real defects.
- **No recording format.** The deliverable says "record what I find"; Easy Checks
  ends at "Share your findings with someone who can fix accessibility barriers."
  No template, no severity, no repro steps — the lesson must supply the table.
  (The WCAG-EM Report Tool, https://www.w3.org/WAI/eval/report-tool/, is live at
  v3.0.3, updated 1 July 2026 — but I could not read its output format; don't
  promise it sight-unseen, and it is likely too heavy for a 5h task.)
- **No sampling guidance** (which page, how many) — deliberate; that is WCAG-EM's
  job. **No screen reader step**, and no statement of what a keyboard pass does
  *not* prove: a page can be fully keyboard-operable and announce nothing useful.

## d. Credible disagreement

**The 4.5:1 number is actively contested.** Andrew Somers (Myndex, W3C Invited
Expert) built APCA — the candidate replacement for WCAG 3,
https://git.apcacontrast.com/documentation/WhyAPCA.html — on the claim that the
WCAG 2.x formula is perceptually wrong: it "far overstates contrast for dark
colors", "4.5:1 can be functionally unreadable when a color is near black", and
"WCAG 2.x contrast cannot be used for guidance designing 'dark mode.'" APCA is
not normative and 1.4.3 is what is testable today — teach 4.5:1, but say out loud
that the threshold is disputed and known-weak in dark mode.

**Adrian Roselli disagrees with the audit artifact itself.** *Your Accessibility
Claims Are Wrong, Unless…* (adrianroselli.com/2022/11/, upd. 5 Jan 2026): "Don't
assert **anything** about how it works with assistive technology." His demand is
specificity — "Tell me *which* screen readers (plural). Tell me which versions of
those screen readers on which operating systems with which browsers" — and he
warns off the crutch: "Do not rely on the output of the accessibility inspector
in your browser dev tools." Applied here: the report must state browser, OS, date
and which checks ran, and claim only what was tested. "I audited the page" is the
wrong sentence; "I tabbed this page in Chrome 1xx on macOS and found N focus
defects" is the right one.

**The Overlay Fact Sheet** (overlayfactsheet.com, 1,031 signatories) gives the
motive for doing this by hand: "There are 0 automated tools that can detect
accessibility problems accurately at anything above 30% of the time." *(An RST
angle — this is checking, not testing — likely applies, but I did not fetch
Bach/Bolton this session and am not claiming it.)*

## e. Worked examples worth adapting

- **WAI Before and After Demonstration (BAD)** — https://www.w3.org/WAI/demos/bad/
  — "a multi-page resource that shows an inaccessible website and a retrofitted
  version of this same website." Five pages per version (Home, News, Tickets,
  Survey, Template), *each accompanied by an evaluation report* — a known-answer
  audit target: audit `before/`, then diff against the published report. Best
  exercise available. **Caveat:** last updated 20 Feb 2012, WCAG 2.0-era, survey
  form needs PHP — verify it still renders before assigning it.
- **WebAIM Million 2026** — top failures: low contrast 83.9%, missing alt text
  53.1%, missing form input labels 51.0%, empty links 46.3%, empty buttons 30.6%.
  Two of the top three are this deliverable's checks. Opening stat and
  expectation-setter: the learner *will* find defects on any page they pick.
- **Named defect patterns from Easy Checks**, reproducible on live sites: the
  **keyboard trap** ("the keyboard focus gets caught in media controls and you
  cannot get out"); the **drop-down navigation trap** (arrowing down loads a new
  page, so the other options are unreachable); **hover-only functionality**
  ("available only with mouse hover, and is not available with keyboard focus").

## Verbatim quotes

(Roselli and APCA are quoted inline in §d with URLs; not repeated.)

**WAI Easy Checks** — Scope:
> "These checks cover just a few accessibility issues and are designed to be quick
> and easy, rather than definitive. A web page could seem to pass these checks,
> yet still have significant accessibility barriers."

Using these Easy Checks:
> "You can do most of these checks with any browser, that is, you do *not* need to
> download special tools."

Keyboard access and visual focus — What to check for:
> "Tab away: Check that you can tab away from all elements that you can tab into.
> (A common problem is the keyboard focus gets caught in media controls and you
> cannot get out; it's called the 'keyboard trap'.)" / "Visual focus: Check that
> the focus is clearly visible as you tab through the elements, that is, you can
> tell which element has focus."

Forms/labels; Contrast ratio; Next steps; footer:
> "every form control has a label associated with it using 'label', 'for', and 'id.'"
> "a contrast ratio of at least 4.5:1 for normal-size text."
> "Share your findings with someone who can fix accessibility barriers."
> "Updated: 9 August 2023." / "Major revision planned for late 2023."

**WAI, Evaluating Web Accessibility** (https://www.w3.org/WAI/test-evaluate/):
> "No tool alone can determine if a site meets accessibility standards.
> Knowledgeable human evaluation is required to determine if a site is accessible."

**WCAG 2.2** (https://www.w3.org/TR/WCAG22/):
> 2.4.7 Focus Visible: "Any keyboard operable user interface has a mode of
> operation where the keyboard focus indicator is visible."
> 2.4.11 Focus Not Obscured (Minimum): "When a user interface component receives
> keyboard focus, the component is not entirely hidden due to author-created content."

**WebAIM Million 2026** (https://webaim.org/projects/million/):
> "95.9% of home pages had detected WCAG 2 failures."
> "All automated tools, including WAVE, have limitations—not all conformance
> failures can be automatically detected. Absence of detected errors does not
> indicate that a page is accessible or conformant."
