## b. Best primary source

**Spine: the Karate v1.5.1 README.** One page, MIT-licensed, vendor-authored but
technically candid, and it is deliverable-shaped — the *Hello World* block is
literally a passing API check in five lines. Recommend Karate over the other two
plan options, for reasons the sources support:

1. **SoapUI Open Source is a GUI desktop app, not a code-based tool.** soapui.org
   ships platform installers (Windows / macOS ARM / Linux) for version 5.10.0;
   projects are XML files edited in a window. Picking it makes the deliverable
   *"prototype three API checks in a different GUI than Postman"* — the learning
   goal evaporates. **Drop SoapUI from the task's option list.**
2. **REST Assured is healthy but demands more.** Actively maintained — 6.0.1 dated
   2026-07-10, Java 17+ baseline since 6.0.0. But it is a Java library: the learner
   needs Maven, JUnit, Hamcrest matchers and a compile step before check one. Docs
   are a wiki (https://github.com/rest-assured/rest-assured/wiki/Usage) organised by
   feature, not by task — 26 headings, no quickstart, and it never discusses when to
   use it over a GUI tool.
3. **For the Postman half there is no comparable primary source — use Postman's own
   documented limits.** https://learning.postman.com/docs/postman-cli/postman-cli-run-collection/
   is the honest anchor: Postman itself lists what its runner can't do. Far better
   than a vendor comparison chart.

**Version trap — the load-bearing practical fact.** Two doc sets, two artifacts:
- v1.x: `io.karatelabs:karate-junit5:1.5.1`, docs = the v1.5.1 README.
- v2.x: `io.karatelabs:karate-junit6:2.1.1`, **Java 21+**, docs = https://docs.karatelabs.io.
  v2 is weeks old (v2.1.1 tagged 15 Jul, GitHub omits the year → 2026) and v2.1.0
  shipped a breaking security fix. `search.maven.org`'s legacy index returns 0 for
  `karate-junit6` and tops out at 1.5.2.RC4 — it is **stale**; central.sonatype.com
  confirms 2.1.1 is published. Pick one line and don't mix docs.

## c. What it leaves out

- **The whole "vs Postman" question.** The README argues Karate vs REST-assured and
  vs Cucumber. It never argues Karate vs a GUI client — the actual learning goal.
- **No selection method.** No criteria list, no cost model, no "when NOT to use
  Karate." (docs.karatelabs.io/faq has a thin *when to use alternatives* list, but
  it is marketing copy.) CTAL-TAE v2.0 §2.2 supplies the generic method — already
  dossiered under QA-028; reuse it, don't re-derive it.
- **The comparison table on docs.karatelabs.io/getting-started/why-karate is vendor
  self-assessment**, and it shows: Karate scores ✓ on all nine rows while every
  competitor gets blanks, "Manual" or "Limited." Do not ship it as evidence. Its one
  useful row is honest — Postman is marked "Limited" on parallel execution.
- **Nothing on the real reasons teams move off Postman**: code review on test
  changes, merge conflicts in collection JSON, secrets handling, reuse/abstraction
  across suites, seeding test data. None of this is in any source I found.
- **Postman is no longer the strawman the task implies.** Postman ships a CLI and
  Native Git integration (learning.postman.com/docs/agent-mode/native-git). "Postman
  can't do CI or version control" is an outdated argument — the lesson must not make
  it. The surviving arguments are the *documented* ones in §b3 and the reuse gap.

## d. Credible disagreement

**1. Pact says both approaches are the wrong tool for the job people use them for.**
docs.pact.io/getting_started/what_is_pact_good_for lists what Pact is *not* good for
and explicitly includes *functional testing of the provider* — "this is the
provider's own responsibility" — and states Pact "is about checking the contents and
format of requests and responses." Read the other way: if your goal is catching
provider/consumer breakage, three Karate checks against a deployed service are the
wrong instrument. This disagrees with the task's premise, not just its tool choice.

**2. Karate's author disagrees with the BDD community, in writing.** The README's own
section: "Yes, Karate is not *true* BDD... it is the opinion of the author of Karate
that *true* BDD is un-necessary over-kill for API testing." Gherkin here is a DSL,
not a collaboration artefact. Cucumber's position is the opposite. Worth 3 sentences
so learners aren't confused by the `.feature` extension.

**3. REST Assured's counter-premise: stay in the app's language.** Its README opens
"Testing and validation of REST services in Java is harder than in dynamic languages
such as Ruby and Groovy. REST Assured brings the simplicity of using these languages
into the Java domain." That is a bet on staying inside the build, the IDE and the
refactoring tools — against Karate's bet on a separate plain-text DSL. Karate's own
FAQ concedes the point: it recommends REST Assured for "Java-heavy teams."

**4. RST (Bach & Bolton), as in QA-028:** these are *checks*, not tests. Name it, don't re-litigate it.

## e. Worked examples worth adapting

- **Karate's own Hello World is check #1, verbatim and runnable** — it hits
  `jsonplaceholder.typicode.com`, a public API needing no auth or signup.
- **A three-check ladder that maps onto the README's own sections:** (1) status +
  single field — the Hello World block; (2) *contract* check using fuzzy markers,
  `match response == { id: '#number', name: '#string' }` — proves the shape without
  pinning volatile values, the thing Postman's `pm.test` scripting makes tedious;
  (3) *chained* check — POST then GET the created id, using `match contains`.
  All three keywords are documented at docs.karatelabs.io/assertions/match-keyword.
- **Real defect story #1 — from Karate's own v2.1.0 release notes:** "Mock servers no
  longer evaluate untrusted request data as code by default. Java interop
  (`Java.type`) and embedded-expression evaluation of request-derived data...are now
  **off by default** for mocks, closing a remote-code-execution risk." A test tool
  that shipped an RCE. Good, uncomfortable material about trusting tooling.
- **Real defect story #2 — Postman's documented dead ends:** "The Postman CLI doesn't
  support OAuth 2.0 authentication" and "can't run requests that use files in your
  local working directory to send body data." Hand learners a scenario needing OAuth2
  in CI and let them find the sentence themselves. Best exercise here — it teaches
  reading vendor limits as requirements, and it answers the *want* line with evidence
  instead of opinion.
- **Ordering note:** GROUNDED.md assumes no programming ability until lesson 24
  (Playwright). QA-032 must come after it, or ground the Maven/JVM setup itself.
- **Gap:** no public postmortem found of a team hitting a Postman-to-code migration
  wall. Do not invent one; the two stories above are real and cited.
