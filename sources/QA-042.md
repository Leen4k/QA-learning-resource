# QA-042 — Test reporting with JUnit and Allure

> Dossier, not lesson content. Every claim below must be re-read at source
> before it ships in a lesson.

- **Verdict:** PARTIAL
- **Named source:** https://allurereport.org/docs/
- **Best primary source:** Playwright *Test Reporters* — https://playwright.dev/docs/test-reporters (the JUnit half, in the learner's actual stack), paired with the Allure deep pages below
- **Exact sections to read:** Playwright *Test Reporters* → **JUnit reporter**, **HTML reporter**, **Blob reporter** · Playwright *Trace viewer* intro · Allure `/docs/playwright/` · `/docs/test-statuses/` · `/docs/history-and-retries/` · `/docs/test-stability/` · `/docs/categories/` · `/docs/v3/readability/` · `/docs/guides/junit5-github-actions/` (workflow only) · JUnit 5 User Guide → *JUnit Platform Reporting*, §*Legacy XML format* · Surefire XSD (skim the element list)
- **Read time:** ~50 min

## a. Does the named source cover this?

Half of it, and not the half the deliverable turns on. The named URL is a **documentation root**, not
a document — but unlike a project portal it links straight to real, task-shaped material (Features:
Test Steps, Attachments, Test Statuses, Categories, Test Stability, History & Retries, Quality Gate;
15+ Guides; 30+ Frameworks), so a learner does land somewhere useful. Three failures:

**1. It never mentions JUnit XML.** The task is titled "JUnit *and* Allure." The Allure JUnit 5
quickstart, fetched this session, walks add-dependency → AspectJ javaagent → `allure.properties` →
`./gradlew test` → `allure generate`, and bypasses JUnit XML entirely — Allure has its own
`allure-results` format. A learner reading only the named source cannot say what a JUnit XML file is.

**2. It teaches production, not evaluation.** Nothing on the site asks whether a report is any good.
The nearest page, *Improving readability of your test reports*, is a **metadata-annotation guide** —
Title, Tags, Owner, Links, ID, Other Labels, Parametrized Tests, Environment Information. It says
which fields exist, not whether a stranger could understand your failure. "Review whether it tells
the full story" has no counterpart anywhere on the site.

**3. Wrong stack, no warning.** By week 21 this learner has Playwright/TypeScript (QA-023→QA-027,
QA-050); the flagship JUnit 5 and Actions guides are Java/Gradle, `/docs/playwright/` is three lines.

**Version-split hazard — say this in the lesson.** Allure 2 and 3 sit side by side with silently
divergent mechanics. History: v2 = copy the `history` subdirectory from the previous report into your
results dir; v3 = set `historyPath` to a JSONL file. Categories: v2 = `categories.json` in the results
dir; v3 = a `categories` field with `rules`/`matchers` in the runtime config. Wrong branch → history
never appears: no error, just an empty trend chart.

## b. Best primary source

**Playwright *Test Reporters*** — the only source that hands this learner *both* named artifacts, in
the stack they already have, from one config block:

```ts
reporter: [['junit', { outputFile: 'results.xml' }], ['html'], ['allure-playwright']]
```

One run, three reports; that line turns the deliverable's vague second half into an empirical
comparison (§e). This is honestly a **two-source task** — don't pretend otherwise. Playwright covers
generation and the JUnit half; the Allure deep pages cover history, statuses, flakiness, categories.
JUnit XML itself: **JUnit 5 User Guide → JUnit Platform Reporting**
(https://docs.junit.org/6.1.1/advanced-topics/junit-platform-reporting.html) and the **Apache
Surefire XSD** (https://maven.apache.org/surefire/maven-surefire-plugin/xsd/surefire-test-report.xsd).

## c. What it leaves out

- **JUnit XML has no owner and no spec.** JUnit's own docs call it "compatible with the de facto
  standard for JUnit 4 based test reports that was made popular by the Ant build system," and the
  nearest thing to a schema is Apache's Surefire XSD — a *different project's* file. That explains
  every flaky CI report parser the learner will meet. Nobody says it out loud.
- **JUnit XML cannot carry attachments.** Per the XSD a `testcase` gets `name`, `classname`, `time`,
  plus `failure`/`error` (message, type, stack text), `skipped`, `system-out`, `system-err`. No
  screenshot, video, trace or steps. **The key fact for this deliverable** — "does it tell the full
  story" has a concrete, checkable answer at the format level.
- **JUnit XML has no history either.** One file, one run, no trend. Every history feature in this
  task comes from the *consumer* (Allure, CI), never the format — and the plumbing is CI work the
  quickstarts skip (`executor.json` supplies `buildOrder`, which drives the trend-chart columns).
- **Where the report lives.** Playwright's HTML report is a self-contained folder; an Allure report
  needs a static host or `allure open`. Neither doc warns that emailing the folder loses the report.
- **No rubric for judging a report** in either source. It has to be written.

## d. Credible disagreement

**Bolton/RST vs. the dashboard.** In *Braiding The Stories (Test Reporting Part 2)*, Michael Bolton
argues a report must braid **three** stories: the product story ("how the product *can* work, how it
fails, and how it *might* fail in ways that matter to our clients"), the testing story ("what we
actually did and what we actually saw"), and a story about **the quality of the testing**. On
pass/fail summaries: they "come from the *fake* world, a world where numbers have magical properties
to soothe troubled and uncertain souls." That is the sharpest frame available for "does it tell the
full story," and it maps onto the tooling — use it as the lesson's spine. Allure's Overview tab is
**story 1, partially**: it says a thing failed. Steps, attachments, descriptions and the Playwright
trace buy **story 2** — that is what the annotation work in §a.2 is actually *for*. And **story 3 has
no field in any tool**: what wasn't covered, what couldn't be tested, where the time went, how far to
trust the result. A human writes it or it does not exist — that gap is the lesson's real content.

**Second split, inside Allure itself.** Quality Gate automates exactly the metric RST calls invalid —
`successRate`, `maxFailures`, `minTestsCount`. Name the tension: a gate is a *deployment control*, not
a measure of quality. Conversely, Allure's refusal to let red mean one thing (Failed = product defect
vs. Broken = test defect) is a case where the tool sides with the critique. Use both.

## e. Worked examples worth adapting

- **The three-reporter run — this is the deliverable.** Configure `junit`, `html` and
  `allure-playwright` together, break one test on purpose, run once, then diff what each report can
  say about the same failure. The JUnit XML physically cannot hold the trace; the learner discovers
  the limit instead of being told it.
- **Retry-and-trace, from Playwright's default config:** `retries: process.env.CI ? 2 : 0` with
  `trace: 'on-first-retry'`. Run at 0 retries, then with retries on, and compare the evidence.
- **Two drills off Allure's own definitions** (quoted below, both fully specified): predict the run on
  which the Flaky badge appears, then run it; and sort eight failure descriptions into Failed vs Broken.
- **The GitHub Actions workflow** in `/docs/guides/junit5-github-actions/` is a complete
  history-persisting pipeline: checkout `gh-pages` into a path → `simple-elf/allure-report-action@master`
  → `peaceiris/actions-gh-pages@v4`; adaptable to Playwright by swapping the run step. **Flag two
  things:** that Allure action is an unpinned third-party `@master`, and the workflow sets
  `permissions: write-all`. Fix both rather than copying them.
- **Read the XSD as an artifact.** List the evidence wanted for one real failure; mark what has nowhere to live.

## Verbatim quotes

**Surefire XSD** — `testsuite`: `name`, `tests`, `errors`, `skipped`, `failures` required; `time`,
`timestamp`, `flakes`, `group`, `version` optional. `testcase`: `name`, `time` required;
`classname`, `timestamp`, `group` optional. Children of `testcase`: `failure`, `error`, `skipped`
(each with `message`/`type`), `system-out`, `system-err`, `rerunFailure`, `flakyFailure`,
`rerunError`, `flakyError`. **No attachment element of any kind.**

**JUnit 5 User Guide, §Legacy XML format:** `LegacyXmlReportGeneratingListener` "generates a separate
XML report for each root in the TestPlan"; the format is "compatible with the de facto standard for
JUnit 4 based test reports that was made popular by the Ant build system." §Open Test Reporting: the
newer format "supports all features of the JUnit Platform such as hierarchical test structures,
display names, tags, etc." — off by default (`junit.platform.reporting.open.xml.enabled` "defaults
to `false`").

**Bolton, *Braiding The Stories* (developsense.com, Feb 2012):** "Tell the product story… how the
product *can* work, how it fails, and how it *might* fail in ways that matter to our clients." · "To
make the product story credible, tell the testing story… what we actually did and what we actually
saw." · "To make the testing story credible, tell a story about the quality of the testing." · "Pass
vs. fail ratios come from the *fake* world, a world where numbers have magical properties to soothe
troubled and uncertain souls."

**Allure `/docs/test-statuses/`:** Failed — "a test that encountered an unexpected behavior in the
system under test… the test itself seems to be valid (not Broken), but its execution ended with a
false assertion." Broken — "a test that failed because of a test defect… the failure may or may not
indicate an actual product defect." **`/docs/test-stability/`** — flaky when all three hold: "the
test got the Failed status at some point within the latest 5 launches" · "the test got the Passed
status at least one time since then" · "the test got the Failed or Broken status in the latest launch."

**Allure, misc:** `/docs/history-and-retries/` — "Using each test's unique identifier, Allure Report
is able to link its latest result to the results of the same test from previous launches"; "the
retries do not get included in the Tests history"; v2 keeps "data from up to 20 latest reports." ·
`/docs/quality-gate/` rules: `maxFailures`, `minTestsCount`, `successRate`, `maxDuration`,
`allTestsContainEnv`, `environmentsTested`; on violation, exit code 1. · `executor.json` "should
contain information about the CI build" (`reportName`, `buildOrder`, `reportUrl`, `name`, `type`).

**Playwright:** HTML reporter "produces a self-contained folder that contains report for the test run
that can be served as a web page." · Blob reports "contain all the details about the test run and can
be used later to produce any other report." · `PLAYWRIGHT_JUNIT_OUTPUT_NAME=results.xml npx playwright
test --reporter=junit`. · *Trace viewer intro*: `trace: 'on-first-retry'` means traces are "recorded
on the first retry of a failed test but not on the first run and not on the second retry"; a trace
carries actions, a "DOM snapshot so you can fully interact with it and open the browser DevTools",
network, console and source.
