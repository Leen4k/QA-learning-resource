# QA-044 — Moving a test asset through a branch and a reviewed pull request

> Dossier, not lesson content. Every claim below must be re-read at source
> before it ships in a lesson.

- **Verdict:** PARTIAL
- **Named source:** https://git-scm.com/docs/gittutorial
- **Best primary source:** *Pro Git* (2nd ed., Chacon & Straub, free) — https://git-scm.com/book/en/v2/GitHub-Contributing-to-a-Project
- **Exact sections to read:** Pro Git **§6.2** (*Forking Projects · The GitHub Flow · Creating a Pull Request · Iterating on a Pull Request · Pull Requests as Patches*) · Pro Git **§5.2** (*Commit Guidelines*, *Private Small Team*) · GitHub Docs [about-pull-request-reviews](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/about-pull-request-reviews) + [about-status-checks](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/collaborating-on-repositories-with-code-quality-features/about-status-checks) · QA framing: ISTQB CTFL v4.0 **§5.4**, **§1.4.3**
- **Read time:** ~55 min (Pro Git §6.2 ≈ 25, §5.2 ≈ 15, GitHub ≈ 10, ISTQB ≈ 5)

## a. Does the named source cover this?

**Half of it, and that half it covers well.** `gittutorial(7)` has a *Managing branches*
section teaching `git branch`, `git switch`, `git merge`, `git branch -d/-D`, and a
*Using Git for collaboration* section covering `git clone`, `git fetch`, `git pull`,
`git remote add`. Branches: yes. Commits: yes.

**Pull requests: not once.** Fetched this session, the string "pull request" does not
appear, and there is no section on review. Not an oversight — a pull request is a
GitHub/GitLab **product feature**, not a git concept, so the git man pages have no
reason to carry it. But the DELIVERABLE ("through a branch and **reviewed pull
request**") is unreachable from here. Worse, its collaboration model is one nobody
meets at work: *"alice$ git pull /home/bob/myrepo master"* — peer-to-peer pull over a
shared filesystem, no server, no shared `origin`, no forge, no review. Its own *Next
Steps* points onward to `gitworkflows(7)`, a fair signal it knows it is a starting
point. Also dated: everything is `master`, GitHub creates `main`.

## b. Best primary source

**Pro Git §6.2.** Same publisher as the named source, free (CC BY-NC-SA), and the only
free authoritative document I found that walks branch → push → PR → review → merge as
one continuous story. Its *GitHub Flow* is an eight-step list you can hand a learner
directly (quoted below), and it states the thing that matters most for a first PR — a
PR is a conversation, not a finished patch: feedback is answered by pushing **new
commits to the same branch**, not by re-rolling. Pair with **§5.2 *Commit Guidelines***
for the commit half, and the two GitHub Docs pages for review states and status checks,
which Pro Git omits entirely. **ISTQB §5.4** supplies the QA *why* in one paragraph —
test assets are configuration items — and names no tool.

## c. What it leaves out

- **The fork is wrong for the job.** §6.2 teaches the *outside contributor* flow (fork →
  topic branch → PR from fork). A tester adding a test to their own team's repo has push
  access and needs the **shared-repo** flow: `git switch -c`, `git push -u origin
  <branch>`, PR within one repo. Pro Git covers the shared-repo case in §5.2 *Private
  Small Team* — but there **without** pull requests. The two halves the learner needs
  never appear on one page. The lesson must join them.
- **Review states.** Pro Git says "discuss." It never says a review is a *decision*:
  **Comment / Approve / Request changes**. Nor required approvals, branch protection,
  or CODEOWNERS. That is the GitHub Docs page.
- **CI on the PR.** Nothing in Pro Git connects a PR to a test run — odd, in a task whose
  subject *is* a test change. And the status-checks page carries a trap worth building
  the lesson around: *"A job that is skipped will report its status as 'Success'. It will
  not prevent a pull request from merging, even if it is a required check."*
- **What belongs in the repo, and what must not.** No source fetched here answers it:
  which testware is version-controlled (ISTQB §1.4.3 lists test cases, procedures,
  automated scripts, test data, logs, reports) versus what stays out (credentials,
  environment URLs, multi-GB fixtures). Same gap for **how to review a *test*** —
  Google's guide gives two lines and no test-specific checklist. The lesson supplies
  both; don't pretend a source did.

## d. Credible disagreement

**Sharp, and it is with the practice this task teaches, not with git.** Fowler's
*Patterns for Managing Source Code Branches* classifies the PR as *"a mechanism designed
to support the combination of Feature Branching and Pre-Integration Review"*, then names
the cost: *"Pre-Integration Reviews always introduces some latency into the integration
process, encouraging a lower integration frequency."* He quotes Kief Morris: *"Imposing
pull requests on devs in your own team is like making your family go through an airport
security checkpoint to enter your home."*

**DORA agrees and gets specific.** High performers *"Have three or fewer active
branches"* and *"Merge branches to trunk at least once a day"* (2016/2017 reports), and
review **synchronously**: *"when the developer is ready to commit the code, they should
ask somebody else on the team to review the code right then."* Async PR review is what
that camp is trying to shrink.

**Second, quieter: the git project itself does not use pull requests.** `gitworkflows(7)`
documents git.git's own model — topic branches plus a patch workflow over email. Say it
aloud so the learner never confuses tool with platform.

**Honest gap:** I did **not** fetch Bach/Bolton or any RST material this session. I have
no evidence RST takes a position on version control for testware. Don't invent one.

## e. Worked examples worth adapting

- **The drill, from §6.2.** `git checkout -b slow-blink` → commit → push → the "Compare
  & pull request" banner → open PR → reviewer comments → **push another commit to the
  same branch** to answer them → merge. GitHub's page confirms the UI path and
  base/compare dropdowns; `gh pr create` is the CLI form.
- **Manufacture the rejected push** (§5.2 *Private Small Team*). John and Jessica edit
  *different* files; John's push still fails: `! [rejected] master -> master (non-fast
  forward)`. He must `git fetch origin` then `git merge origin/master` first. Best
  single exercise in either book — the one error message every learner hits. Note Pro
  Git's aside that John *"might want to test this new code"* after merging.
- **Commit message template** (§5.2, adapted from Tim Pope): 50-char capitalised summary,
  blank line, body wrapped at 72, imperative — *"Fix bug" and not "Fixed bug" or "Fixes
  bug."* Plus `git diff --check` before committing. **Size it** — Google: *"100 lines is
  usually a reasonable size for a CL, and 1000 lines is usually too large."*
- **The status-check trap, as a lab.** Make the test job conditional so it skips,
  watch the required check go green, merge a change no test ever ran on. Then fix it.
- **Real incident: Homebrew, 31 July 2018.** A leaked Jenkins token *"gave them access
  to `git push` on Homebrew/brew and Homebrew/homebrew-core."* The remediation is this
  task's syllabus. Answers "why not just push to main?"

## Verbatim quotes

**Pro Git §6.2, *The GitHub Flow*:** "1. Fork the project. 2. Create a topic branch
from `master`. 3. Make some commits to improve the project. 4. Push this branch to your
GitHub project. 5. Open a Pull Request on GitHub. 6. Discuss, and optionally continue
committing. 7. The project owner merges or closes the Pull Request. 8. Sync the updated
`master` back to your fork." · *Pull Requests as Patches*: "Most GitHub projects think
about Pull Request branches as iterative conversations around a proposed change,
culminating in a unified diff that is applied by merging." · "the patch series is
generally not re-rolled, but instead the difference is pushed as a new commit to the
branch."

**Pro Git §5.2:** "try to make each commit a logically separate changeset" · "no more
than about 50 characters… followed by a blank line, followed by a more detailed
explanation" (rest in §e).

**GitHub Docs:** "Pull requests are proposals to merge code changes into a project." ·
"Draft pull requests cannot be merged." · Comment — "Leaves general feedback without
explicitly approving or requesting changes."; Approve — "Signals that the changes are
ready to merge."; Request changes — "Flags feedback that the author should address
before merging." · "Repository administrators can require approvals before pull requests
are merged." · "If status checks are required for a protected branch, they must pass
before the pull request can be merged." · "A job that is skipped will report its status
as 'Success'."

**ISTQB CTFL v4.0 §5.4:** "In testing, configuration management (CM) provides a
discipline for identifying, controlling, and tracking work products such as test plans,
test strategies, test conditions, test cases, test scripts, test results, test logs, and
test reports as configuration items." · "All configuration items… are uniquely
identified, version controlled, tracked for changes, and related to other configuration
items so that traceability can be maintained throughout the test process". **§1.4.3:**
"Proper configuration management… ensures consistency and integrity of work products."

**gitworkflows(7):** "Rule: Topic branches — Make a side branch for every topic
(feature, bugfix, …​). Fork it off at the oldest integration branch that you will
eventually want to merge it into." **Fowler:** "I see Pull Requests as a mechanism
designed to support the combination of Feature Branching and Pre-Integration Review."
**DORA:** "Each developer divides their own work into small batches and merges that
work into trunk at least once (and potentially several times) a day." **Google:** "The
right size for a CL is one self-contained change." **Homebrew:** repos "were also
updated to require CI checks from a pull request to pass before changes can be pushed
to `master`."
