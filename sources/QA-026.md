## c. What it leaves out

Against this DELIVERABLE the Playwright page is missing most of the judgment:

- **No cost side.** Its six-bullet advantage list (encapsulate / reusable /
  on-demand / composable / flexible / grouping) is unopposed — the page never
  says a fixture can make a test *harder* to read. That is the whole risk in
  "keeping the test intent obvious."
- **No stopping rule.** Nothing says when two tests should *not* share.
  Playwright's own *Best Practices* page contradicts this omission (§d).
- **`auto: true` presented without warning.** Invisible setup — "even when the
  test does not list them directly" — is offered as a feature, and the *global
  beforeEach hooks* section recommends it. No downside is flagged.
- **Almost nothing on test data.** It covers *objects*, not *data*: no
  unique-data-per-test, no collision between parallel workers writing the same
  record, no cleanup of data a fixture created, no builders. The worker-scoped
  `'user' + workerInfo.workerIndex` snippet is the only nod to collisions.
- **No refactoring method.** Before and after, but not the move. The lesson must
  supply the steps (name the intent → extract only the arrange → leave the values
  the assertion depends on in the test body).
- **POM assumed.** `TodoPage`/`SettingsPage` come from a page-object page never
  explained here.

SWE@Google's own gaps: unit-test-shaped and Java/Python — nothing on browser
context, worker parallelism, async teardown, or auth-state reuse.

## d. Credible disagreement

The real fight is over *implicit* setup; all three positions are sourced.

1. **Playwright *Fixtures* — extract aggressively.** Fixtures "encapsulate setup
   and teardown in the same place," are "reusable between test files," and
   "simplify grouping. You no longer need to wrap tests in `describe`s."
2. **SWE@Google — extraction obscures, and duplication is often cheaper.**
   "Instead of being completely DRY, test code should often strive to be DAMP...
   'Descriptive And Meaningful Phrases.'" On fixtures directly: "One risk in
   using setup methods is that they can lead to unclear tests if those tests
   begin to depend on the particular values used in setup" — such tests "should
   state those values directly, overriding the default defined in the setup
   method if need be."
3. **Playwright *Best Practices* sides with Google against Playwright
   *Fixtures*.** Same docs site: "it is also ok to have a little duplication when
   tests are simple enough especially if it keeps your tests clearer and easier
   to read and maintain." Both quotes verified — name this internal contradiction
   in the lesson; it is the most honest way to teach the trade-off.

**pytest adjudicates it.** Its *About fixtures* page argues the win is not
sharing but *naming*: "fixtures have explicit names and are activated by
declaring their use from test functions." A fixture named in the test signature
(`async ({ todoPage }) => {}`) survives DAMP because the test still says what it
needs; `beforeEach` and `auto: true` do not. **Rule for the lesson: share via
named parameters, never via ambient hooks.**

**RST angle — flagged, not sourced.** No Bach/Bolton document fetched this
session; verified RST quotes are in `sources/QA-016.md` §d.

## e. Worked examples worth adapting

- **The ready-made one: Playwright *Fixtures* §§ *Without fixtures* / *With
  fixtures*.** Hand the learner the `beforeEach` version — including the
  `let todoPage;` shared mutable above the tests — and have them derive the
  fixture version. It *is* the DELIVERABLE, with a solution key.
- **Google's `ACCOUNT_1` / `ACCOUNT_2` example (§ Shared Values).** Opaque shared
  constants make the reader scroll away to learn what the account is; the fix is
  a helper with defaults so each test names only the values it cares about.
- **Google's `@Before` / "Donald Knuth" example (§ Shared Setup).** A test asserts
  on a value defined in the setup method, not the test. Fix: set it in the test
  body even though that duplicates setup — the exercise that teaches the stopping
  rule. *Re-read both at source; a fetch flagged the book as CC BY-NC-ND, so
  re-type them into Playwright/TS rather than reproduce them.*
- **A collision exercise Playwright half-supplies.** Take its worker-scoped
  `'user' + workerInfo.workerIndex` account fixture, make it test-scoped and
  constant, run `--workers=4`, watch two tests fight over one record.
- **Gap — no citable real defect story found.** The Google Testing Blog's "Where
  do our flaky tests come from?" (2017) attributes flakiness to test *size* and
  timing, **not** shared fixtures — do not cite it here. Write the shared-state
  failure as an explicit hypothetical.

## Verbatim quotes

**Playwright, *Fixtures*, §§ Introduction / Automatic fixtures / Execution order:**
- "Test fixtures are used to establish the environment for each test, giving the test everything it needs and nothing else."
- "Fixtures **encapsulate** setup and teardown in the same place so it is easier to write"
- "Fixtures simplify **grouping**. You no longer need to wrap tests in `describe`s."
- "Automatic fixtures are set up for each test/worker, even when the test does not list them directly."

**Playwright, *Best Practices* § Make tests as isolated as possible:**
- "Each test should be completely isolated from another test and should run independently with its own local storage, session storage, data, cookies etc."
- "However it is also ok to have a little duplication when tests are simple enough especially if it keeps your tests clearer and easier to read and maintain."

**Playwright, *Parameterize tests* § Before and after hooks:**
- "Most of the time you should put `beforeEach`, `beforeAll`, `afterEach` and `afterAll` hooks outside of `forEach`, so that hooks are executed just once"

**SWE@Google ch. 12:**
- § Complete and Concise — "A test's body should contain all of the information needed to understand it without containing any irrelevant or distracting information."
- § DAMP, Not DRY — "Instead of being completely DRY, test code should often strive to be DAMP—that is, to promote 'Descriptive And Meaningful Phrases.'"
- § Shared Values — "A little bit of duplication is OK in tests so long as that duplication makes the test simpler and clearer." · "Using helper methods to construct these values allows each test to create the exact values it needs without having to worry about specifying irrelevant information or conflicting with other tests."
- § Shared Setup — "One risk in using setup methods is that they can lead to unclear tests if those tests begin to depend on the particular values used in setup."
- § Shared Helpers and Validation — "The best validation helper methods assert a single conceptual fact about their inputs."
- § TL;DRs — "Follow DAMP over DRY when sharing code for tests."

**pytest, *About fixtures* § Improvements over xUnit-style setup/teardown:**
- "fixtures have explicit names and are activated by declaring their use from test functions, modules, classes or whole projects."
