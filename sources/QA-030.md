# QA-030 — Postman collections, environments and variables

> Dossier, not lesson content. Every claim below must be re-read at source
> before it ships in a lesson.

- **Verdict:** PARTIAL
- **Named source:** https://learning.postman.com/docs/getting-started/quick-start/
- **Best primary source:** Postman Docs, "Store and reuse values using variables" — https://learning.postman.com/docs/use/send-requests/variables/variables (spine), plus four companions below
- **Exact sections to read:** *Store and reuse values using variables* §§ *Variable scopes*, *Variable types* · *Group sets of variables in Postman using environments* §§ *Create an environment*, *Switch between environments* · *Share variables in Postman* (whole page, short) · *Write scripts to test API response data* §§ *Testing in Postman*, *Add a post-response test*, *Validate responses* · *Test your API using the Collection Runner* §§ run config, *Iterations*, *Test data file*
- **Read time:** ~40 min

## a. Does the named source cover this?

Right docs site, wrong page — and the miss is exactly the half the DELIVERABLE names. The
Quick start has four sections: *Send an API request*, *How it works*, *Create a
collection and save your request*, *Write a test for your API request*. It defines a
collection ("a group of saved requests that you can organize into folders") and hands over
one working assertion, `pm.test("Status code is 200", …)`. Then it stops. Asked directly
which strings appear anywhere on the page: **"environment" — no. "variable" — no.
"collection runner" — no. `{{` — no.**

The task title says *collections **and environments***; the deliverable says *using
**variables** and assertions*. The named page contains neither word. A learner following it
produces a collection with one hardcoded URL and one status check — they cannot point it at
a second server, cannot chain a token, and have not met the runner. PARTIAL, not
WRONG-DOCUMENT: it is genuinely step 0 (~10 min) and the one assertion it teaches is the
right one to teach first. It is about a third of the task.

## b. Best primary source

**Postman Docs, "Store and reuse values using variables"**
(https://learning.postman.com/docs/use/send-requests/variables/variables). The only page
carrying the concept that makes collections-plus-environments *work* rather than merely
exist: five scopes — **global, collection, environment, data, local** — and the precedence
rule, *"the value stored in the variable with narrowest scope will be used."* Nearly
everything a learner gets wrong here is a scope-precedence mistake. Four companions:

1. **"Group sets of variables… using environments"** (…/variables/managing-environments/) —
   the mechanism. §*Create an environment*, §*Switch between environments*.
2. **"Share variables in Postman"** (…/variables/share-variables) — local vs shared values
   and the secrets warning. Short; do not skip (see §e).
3. **"Write scripts to test API response data"** (…/write-scripts/test-scripts/) +
   **"Test script examples"** (…/write-scripts/test-examples/) — assertions, Chai.js BDD,
   copy-paste library. Signatures: **"Reference variables in Postman scripts"**
   (…/write-scripts/postman-sandbox-reference/pm-variables).
4. **"Test your API using the Collection Runner"** (…/running-collections/intro-to-collection-runs/)
   — "easy to rerun", which is the actual point of the task.

## c. What it leaves out

- **No guidance on *which* scope to use.** The docs list five and a precedence rule; nothing
  says "base URL → environment, token → collection variable set by script, per-row data →
  data file." That decision is the lesson, and no page makes it.
- **No chained workflow end to end.** The pieces sit in five separate places; the
  *End-to-end testing* page is a stub pointing at a template rather than showing code.
- **Most tutorials online are now wrong about initial vs current value.** Postman replaced
  that split with a single local-by-default value you optionally *Share*. Flag it explicitly.
- **The CI story has a live trap.** The Newman page states *"Newman isn't compatible with the
  collection v3 format used in Postman v12 and later"* and steers to the Postman CLI — while
  every blog still teaches `newman run`. Re-verify at source; the CLI overview doesn't repeat it.
- **Nothing on reviewability** — no official page discusses diffing collections or two people
  editing one. **And no oracle guidance:** `pm.response.to.have.status(200)` passes on a 200
  returning the wrong customer's data, and the docs never say so.

## d. Credible disagreement

**1. Bruno vs. the cloud workspace.** Bruno's docs
(https://docs.usebruno.com/introduction/what-is-bruno) state its philosophy as: store
collections as files and "review API changes like code", "work locally without requiring a
cloud account", "store requests in YAML for readable, versionable collections" — a
point-by-point rejection of the model this task teaches. Honest framing: Postman optimises
for shareability and onboarding, Bruno for reviewability and offline control; which matters
more depends on whether the collection is a scratchpad or a regression suite.

**2. RST — a collection is a set of checks, not testing.** Bach & Bolton, "Testing and
Checking Refined" (satisfice.com, 10 Aug 2024): checking is *"the mechanistic process of
verifying propositions about the product"*, and *"the defining feature of a check is that it
can be COMPLETELY automated, whereas testing is intrinsically a human activity."* Unusually,
the task's own wording — "organize API **checks**" — is already RST-correct. Lean on that: a
green run is evidence the propositions you thought to write down still hold, nothing more.

**3. Postman disagrees with its own ecosystem.** Newman is what every tutorial teaches;
Postman's docs now flag it as incompatible with the current collection format. Show that the
tool's own guidance moved and copied blog snippets rot.

## e. Worked examples worth adapting

- **The docs' own two-minute demo** (*Reuse data with variables and environments*): create
  `my_variable` = `Hello`, send `https://postman-echo.com/get?var={{my_variable}}`. Free, no
  auth. Use it verbatim, then redo it as an *environment* variable and switch environments —
  the switch is where the concept lands.
- **The chaining move, one line:** `pm.environment.set("variable_name", pm.response.json().property)`
  (from *Test script examples*). Request 1 logs in and captures a token, requests 2–3 consume
  `{{token}}`. That line is the difference between a folder of requests and a workflow.
- **Test script examples as an assertion menu** — status code, `pm.expect(json.name).to.eql("Jane")`,
  `Content-Type` includes `application/json`, `responseTime` below 200ms, JSON schema. Have
  the learner pick three and justify each; resist letting them add all five.
- **Deliberate scope collision.** Same variable name at collection *and* environment scope,
  different values; run it; watch the narrower one win. Cheapest demo of the precedence rule.
- **Real defect story — Truffle Security, "(The) Postman Carries Lots of Secrets"
  (25 Apr 2024, trufflesecurity.com/blog/postman-carries-lots-of-secrets).** ~40,000 public
  workspaces scanned; 1,689 live unique credentials across 183 secret types; estimate *"over
  4,000 live credentials are currently leaking publicly on Postman."* They sat in
  **environment variables and collection forks** — exactly the artefacts this lesson builds.
  16% of public OpenAI forks held live credentials; one large company exposed its production
  stack including IAM servers and ElasticSearch. Pair with the docs' own warning (see quotes),
  then teach the secret variable type / Postman Vault as the fix — environments land as a
  safety lesson, not a convenience one. (A larger CloudSEK figure — 30,000 workspaces, Dec
  2024 — appeared in search but the blog 403s. Do not cite until someone reads it.)
- **Rerun as the real deliverable test:** Collection Runner first, then
  `postman collection run <path> --environment <env> --reporters cli,junit --bail`. Running it
  against two environments back to back proves the variables were factored correctly.

## Verbatim quotes

**"Postman quick start" (named source)** — headings in order: *Send an API request* · *How it
works* · *Create a collection and save your request* · *Write a test for your API request*.
Only code block: `pm.test("Status code is 200", function () { pm.response.to.have.status(200); });`
- "A collection is a group of saved requests that you can organize into folders. You can also save responses, documentation, and tests in a collection."
- Confirmed absent: "environment", "variable", "collection runner", `{{`.

**"Store and reuse values using variables":**
- "A variable is a symbolic representation of data that enables you to access a value without having to enter it manually wherever you need it."
- Scopes broadest→narrowest: "global, collection, environment, data, and local".
- "If a variable with the same name is declared in two different scopes, the value stored in the variable with narrowest scope will be used."
- "Postman stores variables as strings." Sensitive data → secret variable type or Postman Vault.

**"Group sets of variables in Postman using environments"** (H1 exact): an environment is "a set of one or more variables that you can reference when sending requests, writing pre-request scripts, or writing post-response scripts" · "when you switch between environments, all of the variables in your requests and scripts will use the values from the current environment"

**"Share variables in Postman":**
- "By default, variables have a local value that only you can access in your instance of Postman."
- "Make sure your shared values don't contain sensitive information such as passwords or tokens."
- "the shared values of all variables are published with your documentation"

**Scripts pages:**
- "A pre-request script associated with a request runs before the request is sent. A post-response script associated with a request runs after the request is sent." · "Collection-level scripts run first, then folder-level scripts, and then request-level scripts." · Assertions use "Chai.js behavior-driven development (BDD) syntax."
- Signatures: `pm.environment.set(variableName:String, variableValue:*)` · `pm.collectionVariables.set(...)` · `pm.variables.get(...)` · `pm.variables.replaceIn(...)`

**"Test your API using the Collection Runner":** "Send some or all of the API requests in a Postman Collection using the Collection Runner, in the order you choose. The Collection Runner logs the test results for each request." Order also settable at runtime via `pm.execution.setNextRequest()`.

**Postman CLI / Newman:**
- `postman collection run <collection> [options]`; `--environment` "Specifies an environment file path or UID"; `--env-var` key=value; `--bail`; `--reporters` → `cli`, `json`, `junit`, `html`. · `npm install -g newman`; `newman run my-collection.json -e dev-environment.json`; "Newman doesn't support OAuth 2.0 authentication."
- **Re-verify before shipping:** "Newman isn't compatible with the collection v3 format used in Postman v12 and later."

**Bruno, "What is Bruno":** "store collections as files and review API changes like code" · "work locally without requiring a cloud account" · "store requests in YAML for readable, versionable collections".

**Bach & Bolton, "Testing and Checking Refined" (10 Aug 2024):** "Checking is the mechanistic process of verifying propositions about the product." · "the defining feature of a check is that it can be COMPLETELY automated, whereas testing is intrinsically a human activity"

**Truffle Security (25 Apr 2024):** "We estimate over 4,000 live credentials are currently leaking publicly on Postman for a variety of popular SaaS and cloud providers." — 1,689 live unique credentials across ~40,000 workspaces, 183 secret types, found in environment variables and collection forks; 16% of public OpenAI forks contained live credentials.
