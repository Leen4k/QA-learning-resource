# QA-024 — Playwright: local setup and the run/report loop

> Dossier, not lesson content. Every claim below must be re-read at source
> before it ships in a lesson.

- **Verdict:** PARTIAL
- **Named source:** https://playwright.dev/docs/intro
- **Best primary source:** The named page is the right document. Pair it with two siblings — "Writing tests" (https://playwright.dev/docs/writing-tests) and "Best Practices" (https://playwright.dev/docs/best-practices)
- **Exact sections to read:** Docs have no section numbers; use headings. *Installation* → all headings, `Installing Playwright` through `System requirements` · *Writing tests* → `First test`, `Actions`, `Assertions`, `Test Isolation` (skip `Using Test Hooks`) · *Best Practices* → `Test user-visible behavior`, `Avoid testing third-party dependencies`, `Use locators`, `Use web first assertions`
- **Read time:** ~10 min for the named page, ~40 min for all three

## a. Does the named source cover this?

Mostly yes — this is the correct document, not a roadmap stub. It is a hands-on
install guide that states its own scope up front:

> "**You will learn** — How to install Playwright / What's installed / How to run
> the example test / How to open the HTML test report"

Those four map almost exactly onto the DELIVERABLE's first two clauses, with the exact
commands (`npm init playwright@latest`, `npx playwright test`, `npx playwright
show-report`) and the scaffold listing. A learner following it gets a project and green
example tests. It falls short on the third clause, **"commit one passing test,"** twice:

1. **It never teaches you to write a test.** Every test the learner ends up with was
   generated for them; authoring one is the *next* page, linked only under `What's
   next`. If the clause means a test the learner wrote, this page doesn't get them there.
2. **It says nothing about what to commit.** No `.gitignore` discussion on the page —
   nor on the CI page, which I also checked. The generator does write one
   (`node_modules/`, `/test-results/`, `/playwright-report/`, `/blob-report/`,
   `/playwright/.cache/` — microsoft/playwright#33307), so the default path is safe, but
   a learner adding Playwright to an *existing* repo gets no warning and will commit
   report artifacts.

Also flag the plan's arithmetic: a ~10-minute read for a **5h Must** task. That budget
only makes sense if the lesson also covers writing tests, locators, and the trace viewer.

## b. Best primary source

Keep `playwright.dev/docs/intro` as the spine — free, official, versioned with the
tool, correct. Add two siblings to close the gaps in (a):

- **Writing tests** — https://playwright.dev/docs/writing-tests. Supplies the authored
  test. Its `Test Isolation` heading is the conceptually important bit: the `page`
  fixture is a fresh browser context per test, which is why Playwright tests need no
  teardown code.
- **Best Practices** — https://playwright.dev/docs/best-practices. Supplies judgment.
  Without it the learner copies the example's shape without knowing which parts are
  good practice and which are demo shortcuts (see §e — that matters unusually much here).

Stable, canonical; no blog posts needed for the mechanics.

## c. What it leaves out

- **How to point it at your own app.** The generated `playwright.config.ts` ships
  `baseURL` and the whole `webServer` block **commented out**, and the intro page
  mentions neither. Testing your own local app — the actual job — needs both.
- **What "3 browsers" costs.** The default config enables `chromium`, `firefox` and
  `webkit` projects, so 2 example tests report as 6 runs. `--project=chromium` appears
  only as a one-line tip; the multiplication is never explained.
- **The trace viewer.** Config ships `trace: 'on-first-retry'` with `retries: 0`
  locally — so locally, traces are never captured. The best debugging tool is off by
  default, and intro only links to it under `What's next`.
- **Git hygiene** — see (a). **When not to reach for Playwright at all** — see (d).

## d. Credible disagreement

Two, at different altitudes:

**1. Bach & Bolton (RST) — automation performs *checking*, not *testing*.** Cuts
against the framing that "setting up Playwright" is progress in testing skill. The
distinction is definitional, not rhetorical: checking mechanistically verifies
propositions you already knew to state; testing is the human evaluation that produces
those propositions. Playwright only ever does the former.

**2. Mike Wacker / Google Testing Blog (2015) — "Just Say No to More End-to-End
Tests."** Argues for roughly **70% unit / 20% integration / 10% end-to-end**, because
E2E gives slow feedback, flakes for reasons unrelated to the code, and is expensive to
debug. Not anti-Playwright — anti-*mostly*-Playwright.

Name both as disagreements rather than blending them in: Playwright's docs are a tool
manual and take no position on either question.

## e. Worked examples worth adapting

**The strongest teaching artifact here is a contradiction inside Playwright's own
docs.** The generated `tests/example.spec.ts` (verified at
microsoft/create-playwright `assets/example.spec.ts`) does this:

```ts
test('get started link', async ({ page }) => {
  await page.goto('https://playwright.dev/');
  await page.getByRole('link', { name: 'Get started' }).click();
  await expect(page.getByRole('heading', { name: 'Installation' })).toBeVisible();
});
```

Both example tests navigate to **`https://playwright.dev/`** — a live third-party
website. Playwright's own Best Practices page says: *"Only test what you control. Don't
try to test links to external sites or third party servers that you do not control."*

So the first test the learner runs violates the project's own published rule. It also
fails offline, and asserts on a heading (`Installation`) that Playwright's site could
rename at any time. A real, checkable, self-contained defect story — better than a
synthetic exercise:

- Run the example tests. They pass.
- Disconnect from the network. Run again. They fail, with zero changes to any code
  under test. Ask: *what did that failure tell you about your application?* (Nothing.)
- Rewrite them against something the learner controls; add `webServer` to the config so
  the app starts itself.

That delivers the DELIVERABLE (an authored, committed, passing test) and teaches the
flakiness lesson from (d) at once.

Smaller second exercise: run `npx playwright test`, note 6 results from 2 test functions, and have the learner explain why before reading the config.
