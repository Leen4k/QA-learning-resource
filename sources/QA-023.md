## a. Does the named source cover this?

No — and not marginally. `playwright.dev/docs/intro` is the **installation page** for one end-to-end runner:
`npm init playwright@latest`, the generated file tree, opening the HTML report, Node versions. I fetched it.
No pyramid, no test levels, no unit-vs-e2e comparison, no guidance on whether a given test is worth
automating. Its only conceptual sentence is *"Playwright Test is an end-to-end test framework for modern web
apps"* — what the tool is, not when to reach for it.

The mismatch is structural, not a bad page pick. The task is a **strategy** question; Playwright answers one
layer — the 5%-of-the-suite layer every source below says to use *sparingly*. Naming it here quietly teaches
the ice-cream-cone antipattern the lesson should warn against. The likely-intended sibling,
`playwright.dev/docs/best-practices`, is a better page (isolation, user-visible behaviour, "only test what you
control") but it too "does not contain any statements about the test pyramid, testing levels, or tradeoffs
between unit tests and end-to-end tests." Keep Playwright as the *tool* for the top layer once the pyramid is
drawn; don't use it to teach the pyramid.

## b. Best primary source

**Spine: SWE at Google, Ch. 11.** Free, complete, stable, written by the people running the largest test suite
in the industry, and the only source here with a **numeric target** to sketch against (80/15/5) *plus* an
honest section on where automation stops. Critically it separates two things most pyramid drawings mash
together: **size** (what resources a test may touch — process, network, machine) and **scope** (how much code
it validates). That split is the key idea for the deliverable: "which layer?" is really two questions.

**Companion (5 min): Fowler, `TestPyramid` (2012-05-01)** — canonical statement of the metaphor, attributed to
Mike Cohn's *Succeeding with Agile* (2009). Short enough to read inside the lesson; its caveat (§d) is
essential. **Companion (10 min): Wacker, "Just Say No to More End-to-End Tests"** (Google Testing Blog,
2015-04-22) — https://testing.googleblog.com/2015/04/just-say-no-to-more-end-to-end-tests.html. The 70/20/10
split and the best short defect story available (§e). *Optional depth:* Vocke's "The Practical Test Pyramid"
(martinfowler.com, 2018-02-26) — real sample app, but a 12,000-word Java/Spring walkthrough.

## c. What it leaves out

- **No selection method — i.e. the actual deliverable.** Google gives 80/15/5 but never how to pick *which*
  flows earn the 5%. **The lesson must supply the criterion.** One defensible version assembled from these
  sources: automate when the check is *repeatable, has an unambiguous oracle, runs often, and is cheap to keep
  alive* — then push it as far down the pyramid as still catches the bug.
- **No payback arithmetic.** Nothing on maintenance cost or how many runs an automated check needs before it
  beats doing it by hand — usually the real decider on a small team.
- **Assumes Google's build system.** "Having precise definitions of test sizes has allowed us to create tools
  to enforce them." A learner has no Blaze stopping a "small" test hitting the network — taxonomy transfers,
  enforcement doesn't.
- **No rule for what stays manual.** *The Limits of Automated Testing* names the boundary but gives no way to
  spot it in your own backlog. Nor does the spine say the right shape depends on what you build (§d).
- **No tooling bridge** — selectors, isolation, mocking third parties. That is where Playwright's
  best-practices page legitimately belongs.

## d. Credible disagreement

**1. Fowler disagrees with his own pyramid — quote this.** The shape is a *consequence of a cost assumption*,
not a law: "If my high level tests are fast, reliable, and cheap to modify—then lower-level tests aren't
needed." Best single line in the lesson: it turns the pyramid from dogma into a claim the learner can test
against their own project.

**2. Spotify: the pyramid is wrong for microservices.** Schaffer & Dybeck, 2018-01-11 —
https://engineering.atspotify.com/2018/1/testing-of-microservices. It "is no longer the case, and we would
argue that it can be actively harmful," because "the biggest complexity in a Microservice is not within the
service itself, but in how it interacts with others." They propose the **Testing Honeycomb**: integration-heavy,
few implementation-detail tests, ideally zero *integrated* tests (one that "will pass or fail based on the
correctness of another system"). The integrated/integration distinction is worth stealing.

**3. Kent C. Dodds, the Testing Trophy** (2021-06-03,
https://kentcdodds.com/blog/the-testing-trophy-and-testing-classifications) — "End to End, Integration, Unit,
Static", weighted toward integration, because "the more your tests resemble the way your software is used, the
more confidence they can give you." Static is added "because in the world of JavaScript that's not a given
like it is in the predominant languages when the testing pyramid was introduced."

**4. Rapid Software Testing: the question itself is malformed.** Bach & Bolton hold that testing cannot be
automated at all — only *checking* can. So "which tests should we automate?" is the wrong question: you are
choosing which *checks* to mechanise, and tools also serve testing in ways that aren't checks (data
generation, environment setup, deploy, instrumentation). A genuinely different frame from Google's, not a
footnote — present it as an argument, don't blend. *Sources:* "Testing and Checking Refined,"
https://www.satisfice.com/blog/archives/856 (fetch reported 2024-08-10 — **re-verify**; the original is widely
cited as 2013); "A Context-Driven Approach to Automation in Testing," Bolton & Bach, 2016-01-31,
https://developsense.com/blog/2016/01/a-context-driven-approach-to-automation-in-testing (the paper PDF at
satisfice.com/download/a-context-driven-approach-to-automation-in-testing was **not fetched** — my claims here
come from the blog page).

## e. Worked examples worth adapting

- **Google Web Server (Ch.11).** Tests mandated for all new code; "within a year of instituting this policy,
  the number of emergency pushes *dropped by half*." A before/after story with a number in it.
- **Wacker's day-before-release bug (2015).** Bug lands the day before ship; the E2E suite doesn't surface it
  for hours; debugging runs into days, compounded by lab flakiness. Ready-made as "why the 10% layer can't be
  your safety net." *My fetch summarised this passage rather than quoting it — re-read at source.*
- **Shape-diagnosis exercise.** Describe three suites; have the learner name the shape — pyramid / **ice cream
  cone** / **hourglass** (Ch.11, Figure 11-4) — then say which test they'd delete and which they'd rewrite one
  layer down. Rehearses the deliverable directly.
- **Size-vs-scope sorting drill.** Give ~8 concrete checks from a small web app (password hashing; login form
  validation; checkout against a real payment sandbox; service↔database read) and sort each by *size* and
  *scope* separately using Ch.11's constraints, then place them on the sketch. **The Beyoncé Rule** works as
  the candidate-selection prompt: walk the feature list, ask it of each.

## Verbatim quotes

**SWE at Google, Ch.11 — Test Size:** small "must run in a single process" and "aren't allowed to sleep,
perform I/O operations, or make any other blocking calls"; medium "can span multiple processes, use threads,
and can make blocking calls, including network calls, to `localhost`"; large "remove the `localhost`
restriction imposed on medium tests, allowing the test and the system being tested to span across multiple
machines."

**Ch.11 — Test Scope (ellipses mine):** "Narrow-scoped tests (commonly called *unit tests*) are designed to
validate the logic in a small, focused part of the codebase, like an individual class or method." ·
"Medium-scoped tests… verify interactions between a small number of components; for example, between a server
and its database." · "Large-scoped tests… validate the interaction of several distinct parts of the system."

**Ch.11 — sizes in practice:** "around 80% of our tests being narrow-scoped unit tests…15% medium-scoped
integration tests…and 5% end-to-end tests." · the "'ice cream cone' and the 'hourglass,' as illustrated in
Figure 11-4." · "as you approach 1% flakiness, the tests begin to lose value."

**Ch.11 — Beyoncé Rule / Limits of Automated Testing:** "If you liked it, then you shoulda put a test on it." ·
"Automated testing is not suitable for all testing tasks. For example, testing the quality of search results
often involves human judgment." · "Searching for complex security vulnerabilities is something that humans do
better than automated systems." · "Exploratory Testing is a fundamentally creative endeavor in which someone
treats the application under test as a puzzle to be broken, maybe by executing an unexpected set of steps or
by inserting unexpected data."

**Fowler, `TestPyramid` (2012-05-01):** have "many more low-level UnitTests than high level BroadStackTests
running through a GUI" · UI-based testing is "brittle, expensive to write, and time consuming to run," "slow,
increasing build times," "very brittle," with "non-determinism problems" · "If my high level tests are fast,
reliable, and cheap to modify—then lower-level tests aren't needed."

**Vocke (2018-02-26):** "The 'Test Pyramid' is a metaphor that tells us to group software tests into buckets
of different granularity." · "The more high-level you get the fewer tests you should have."
**Wacker (2015-04-22):** ~70% unit / 20% integration / 10% E2E; "in general, it should retain that pyramid
shape." **The ratio sentence is my fetch's paraphrase — re-read before quoting.**

**Bach & Bolton, "Testing and Checking Refined":** testing = "the process of evaluating a product by learning
about it through experiencing, exploring, and experimenting"; checking = "the mechanistic process of verifying
propositions about the product." · "Checking is a process that can, in principle be performed by a tool
instead of a human, whereas testing can only be *supported* by tools." · "Tools can help us in many ways far
beyond the automation of checks. But in this, they necessarily play a supporting role to skilled humans."
