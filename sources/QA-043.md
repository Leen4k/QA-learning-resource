## a. Does the named source cover this?

No. Unlike QA-041 the node is at least *about* monitoring — it is just 667 bytes long and teaches no
procedure. `monitoring--logs@pJvijtG-a0vOq16EFu3Gr.md` is **one paragraph plus one link** (full body
quoted below). The paragraph is a DevOps-marketing definition; the words *error*, *stack trace*,
*correlation ID*, *request ID*, *timestamp* and *grep* never appear, and it never mentions reading a
log.

Its sole link is a Medium post, *The Two Pillars of Modern QA*. I fetched it: readable, no paywall,
~15 min, on-topic in argument — QA should own post-release monitoring — but conceptual. It names
Datadog, Sentry and CloudWatch and describes "log filtering" in the abstract; it gives **no query
syntax, no correlation-ID method, no worked trace**. A learner finishes it persuaded they should do
this and still unable to. Its five sibling nodes (`datadog`, `grafana`, `kibana`, `new-relic`,
`pager-duty`) are vendor stubs the same size — nothing here to repoint to. Drop it.

## b. Best primary source

**SRE Ch. 12 is the spine because it teaches the *walk itself*.** The deliverable is a
troubleshooting procedure, not a tooling tour, and Ch. 12 is structured as exactly that: Problem
Report → Triage → Examine → Diagnose → Test and Treat → Cure. It also insists the skill is
teachable, which sets the lesson's frame. Ch. 6 supplies the one distinction the deliverable turns
on — **symptom vs. cause**, **black-box vs. white-box**: the task asks the learner to start
black-box (UI symptom) and end white-box (log entry).

**Pair it with the correlation mechanism** — neither SRE chapter says how to find *the relevant* line among millions:

- **W3C *Trace Context*** — https://www.w3.org/TR/trace-context/ — §3.2 gives `traceparent`
  and its `trace-id`: the string a tester copies out of DevTools and pastes into a log search.
- **OTel *Logs Data Model*** — https://opentelemetry.io/docs/specs/otel/logs/data-model/ — the
  `TraceId`/`SpanId` log fields that make that paste match. Take vocabulary first from the
  **Observability Primer** (https://opentelemetry.io/docs/concepts/observability-primer/), ~5 min.
- UI end: **Chrome DevTools *Network*** — https://developer.chrome.com/docs/devtools/network — §§
  *Inspect a resource's details*, *Filter resources*. Thin, but the only page covering "click →
  which request was that?"; the **Initiator** column is the useful bit.

## c. What it leaves out

- **Written for operators, not testers.** Ch. 12 assumes you are paged, own the service and have
  dashboards. The tester starts a step earlier and a privilege lower — you clicked a button and may
  not have prod log access. No source covers that negotiation.
- **No browser→backend bridge.** Nobody states the actual move: DevTools → Network → failing call →
  Headers → copy `traceparent`/`x-request-id` → search the log store. That chain is assembled from
  four documents and must be written fresh.
- **No log-search syntax** — not Lucene/Kibana, SPL, LogQL, CloudWatch Insights; pick one. **Clock
  skew** goes unmentioned as a trap, though OTel hints `Timestamp` is measured "by the origin clock…
  it may be missing if the source timestamp is unknown."
- **What to do when the log says nothing** — the most valuable outcome; only Bach frames that as a finding rather than a dead end. Nothing on what goes in the bug report, either.

## d. Credible disagreement

**Two, cutting in opposite directions. Do not blend them.**

**1. Bach (RST): logs are a *testability* property you demand, not an artifact you get.** Google's
framing is operational — logs exist because production needs them. Bach files observability under
*Intrinsic Testability* and makes it the tester's job: "**The tester must ask for testability. We
cannot expect any non-tester to seriously consider testability.**" On this view a learner who cannot
complete the deliverable has not failed the exercise — they have **found a defect**, and "we could
not trace this failure" is the report. That reframing appears on no SRE/OTel page.

**2. Majors (Honeycomb): the "three pillars" framing OTel teaches is itself the problem.** The
metrics/logs/traces split is, on her account, a vendor artifact that forces engineers to
hand-correlate one request across disconnected tools; she argues for "arbitrarily wide, structured
raw events" instead. Relevant because the deliverable's difficulty *is* her thesis — the walk is
hard precisely because the UI event and the log line live in different systems.

*Lesson verdict: teach the SRE process and the OTel mechanism as current reality, use Bach to define
what a failed walk means, name Majors as the reason the walk is awkward — don't teach o11y 2.0 as
settled. I did not fetch the ISTQB CTFL syllabus this session and make no claim about it; note that
ISTQB's "test monitoring" is test-progress metrics, not application logs — verify before using it.*

## e. Worked examples worth adapting

**1. The OpenTelemetry Demo is a ready-made exercise generator — the best find here.**
https://opentelemetry.io/docs/demo/feature-flags/ — a runnable microservice shop with flags injecting
*specific, user-visible* failures, verified this session: `productCatalogFailure` ("Generate an error
for `GetProduct` requests with product ID: `OLJCESPC7Z`"), `cartServiceFailure` ("whenever
`EmptyCart` is called"), `paymentServiceUnreachable`, `imageSlowLoad`. `productCatalogFailure` is the
pick — one product ID fails and everything else works, forcing *isolation* rather than observation.
The one published walkthrough, *Using Metrics and Traces to diagnose a memory leak*
(https://opentelemetry.io/docs/demo/feature-flags/recommendation-cache/), models the right shape:
dashboard anomaly → sort Jaeger traces by latency → find `app.cache_hit=false` in the waterfall.
Adapt its structure; its subject is off-target.

**2. SRE Ch. 12's App Engine case study — the counter-lesson.** CMS latency spiked with no code change; the datastore hypothesis was wrong; the cause was a security scanner that had created thousands of spurious whitelist objects costing 250ms per request *in memory, generating no RPCs*. The point: the logs did not contain the answer until someone added instrumentation. Pair with Bach.

**3. Cloudflare, 18 Nov 2025 — the best public symptom-to-cause narrative.**
https://blog.cloudflare.com/18-november-2025-outage/ — free, timestamped, and it goes wrong first:
they suspected a DDoS, and their status page went down by coincidence, reinforcing the error. The
tell was a single line (below), and it looked intermittent because a bad config file regenerated every
five minutes on a partially-migrated cluster. Best exercise: hand learners the timeline with the
panic message removed and ask what they would search for.
