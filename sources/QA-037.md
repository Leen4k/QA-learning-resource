## a. Does the named source cover this?

Partly — right project, right docs site, but it is step 1 of 4. Stated scope:
*"Follow along to learn how to: 1. Run a test. 2. Add virtual users.
3. Increase the test duration. 4. Ramp the number of requests up and down as the
test runs."* That gives `k6 run script.js`, `--vus`, `--duration`,
`export const options`, `options.stages`. Against the DELIVERABLE — *"a small
**authenticated** k6 test with realistic **checks** and **limits**"* — it covers
**none of the three nouns**: *authenticated* is not mentioned anywhere on the
page; `check()` appears inside one code sample and is never explained; and it
teaches `stages` (load you *apply*) while never mentioning `thresholds` (the
pass/fail limit you *assert*) — two things easy to confuse, and this page
encourages the confusion.

A learner finishing this page can start a load generator and cannot write a test
that passes or fails. PARTIAL, not WRONG-DOCUMENT, only because the missing

## c. What it leaves out

- **The word "authenticated" is never actually delivered.** The tutorial POSTs
  credentials and asserts `status == 200` — it never captures the returned token
  or uses it on a second request. *Correlation and dynamic data* hardcodes
  `Authorization: 'Token abcdef0123456789'` with no note of its origin. *HTTP
  authentication* covers basic, NTLM and AWS SigV4 — per-request schemes, no
  session. **Checked directly: no complete login → capture token → reuse flow
  exists anywhere in the k6 docs.** The learner must write it.
- **Where threshold numbers come from.** `p(99)<1000` and `rate<0.01` are handed
  down, never derived. Nothing on reading real SLOs off production data.
- **Login-per-iteration is a modelling bug and nobody says so.** Login sits in the
  default function, so at 140 VUs the test hammers the auth endpoint. `setup()`
  (once) vs per-VU login decides what the test measures; never posed.
- **Think time and test data.** No `sleep()` discussion — without it VU count
  bears no relation to user count, which is exactly where "realistic" dies. And
  one hardcoded user (`default`/`12345678`) gives cache hits and lock contention
  real traffic wouldn't produce.
- **"Safe environment."** `quickpizza.grafana.com` is a shared public host; the
  local Docker target lives in `grafana/quickpizza`, not the tutorial.

## d. Credible disagreement

**1. Coordinated omission — and k6 concedes it in its own docs.** The tutorial
teaches VU-based (closed-model) load and reports `p(99)`. The counter-argument is
that this method is not merely imprecise but systematically optimistic, and k6's
own *Open vs closed models* page states the mechanism plainly:
*"when the target system is stressed and starts to respond more slowly, a closed
model load test will wait, resulting in increased iteration durations and a
tapering off of the arrival rate"* — naming it *coordinated omission*. The slower
the system gets, the less load your test applies, so the run flatters exactly the
system you meant to catch. Fix, same page: `constant-arrival-rate` /
`ramping-arrival-rate` *"decouple the start of new VU iterations from the
iteration duration."* Teach the default, then break it (§e).

*Source note:* the canonical statement is **"How NOT to Measure Latency," Gil
Tene, QCon London, 4 Apr 2013, 54:40** —
https://www.infoq.com/presentations/latency-pitfalls/. **The slide deck 403'd and
I could not read it — do not quote Tene's specific claims until someone watches
the talk.** The k6 quote above carries the point alone and is primary.

**2. Bolton & Bach: k6's `check()` is not testing.** k6 named its primitive after
the exact word RST uses for the thing that *isn't* testing. Bolton, *Testing vs.
Checking* (https://www.developsense.com/blog/2009/08/testing-vs-checking):
checking is *"a process of confirmation, verification, and validation"* motivated
by *"confirming existing beliefs"*; testing is *"a process of exploration,
discovery, investigation, and learning"* motivated by *"finding new
information."* End the lesson on: *"When a check passes, we don't know whether
the program works; we only know that it's still working within the scope of our
expectations."* A green k6 run means the system stayed inside the numbers you
guessed in §c — not that it is fast enough.

## e. Worked examples worth adapting

- **The tutorial's three-run arc, as-is.** One script, three shapes: smoke (10
  iterations) → average load (ramp to 20 VUs/10s, hold 50s, ramp down) →
  breakpoint (20 → 140 VUs in 50s stages, `abortOnFail: true`). Don't rebuild it.
- **The open-vs-closed demo is the best 5 minutes available.** Two scripts against
  `quickpizza.grafana.com/api/delay/6`: `constant-vus` with `vus: 1, duration:
  '1m'` → **~10 iterations**; `constant-arrival-rate` with `rate: 1, timeUnit:
  '1s', preAllocatedVUs: 20` → **60**. Same minute, same target, 6× the load. Diff
  the summaries: coordinated omission without a word of theory.
- **Close the auth gap as the graded exercise.** Docs stop at `status == 200`.
  Have the learner take the token off the response (verify the field name at
  source), move login into `setup()`, pass it to the default function, and hit a
  protected endpoint with `Authorization: Bearer …`. That edit *is* the word
  "authenticated", and no k6 page will do it for them.
- **Threshold on the check rate**, so a functional failure fails the build: add
  `checks: ['rate>0.9']` and show the exit code change.
- **The safe environment, done properly.** Run QuickPizza locally
  (https://github.com/grafana/quickpizza, Docker; k6 ≥ v1.0.0) rather than aiming
  a breakpoint test at Grafana's shared public host. k6's rule: *"Don't load test
  servers that you don't own."* Make the learner state in one line who owns the
  target and who authorised the run — the real professional skill here.

## Verbatim quotes

*Running k6*, *Open vs closed models*, *Load testing websites* and Bolton are
quoted inline in §a, §d, §e — not repeated here.

**Checks:** "like asserts but differ in that they do not halt the execution,
instead, they just store the result of the check, pass or fail, and let the
script execution continue." · "failed checks do not cause the test to abort or
finish with a failed status." · "Each check creates a rate metric. To make a
check abort or fail a test, you can combine it with a Threshold."

**Thresholds:** "the pass/fail criteria that you define for your test metrics";
if the SUT "does not meet the conditions of your threshold, the test finishes
with a failed status." · form `<aggregation_method> <operator> <value>` · Counter
→ `count`,`rate`; Gauge → `value`; Rate → `rate`; Trend →
`avg`,`min`,`max`,`med`,`p(N)` · sub-metrics `'metric_name{tag_name:tag_value}'` ·
long form `{ threshold: 'p(99) < 10', abortOnFail: true, delayAbortEval: '10s' }`.

**Get started §Test for functional behavior:** POST
`https://quickpizza.grafana.com/api/users/token/login`, payload `{username:
'default', password: '12345678'}`, header `'Content-Type': 'application/json'`,
check `'response code was 200': (res) => res.status == 200`. · "Failed checks do
not stop tests. Rather, k6 tracks the success rate and presents it in your end of
test summary." **§Test for performance:** `thresholds: { http_req_failed:
['rate<0.01'], http_req_duration: ['p(99)<1000'] }` — "99% of requests should be
successful", "99% … latency of 1000ms or less."

**Test types:** smoke — "validate that your script works and that the system
performs adequately under minimal load" · average-load — "expected normal
conditions" (5–60 min) · stress — "at its limits when load exceeds the expected
average" · soak — "over extended periods" · spike — "sudden, short, and massive
increases in activity" · breakpoint — "gradually increase load to identify the
capacity limits of the system." · "The correct load testing strategy is highly
dependent on the risk profile for your organization."
