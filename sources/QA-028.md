# QA-028 — Choosing a browser automation tool

> Dossier, not lesson content. Every claim below must be re-read at source
> before it ships in a lesson.

- **Verdict:** WRONG-DOCUMENT
- **Named source:** https://roadmap.sh/qa
- **Best primary source:** ISTQB *Certified Tester Advanced Level Test Automation Engineering (CTAL-TAE) v2.0* syllabus (2024-05-03) — landing page https://istqb.org/certifications/certified-tester-advanced-level-test-automation-engineering-ctal-tae-v2-0/ ; readable PDF mirror https://www.gasq.org/files/content/iqbohs/images/logo/ISTQB_CTAL-TAE_Syllabus_v2.0.pdf
- **Exact sections to read:** CTAL-TAE v2.0 §1.1.1 + §1.2.2 (pp. 15–16) and §2.2.1 + §2.2.2 (pp. 20–21) · ISTQB CTFL v4.0 §6.2 (pp. 58–59) for the risk list · then the five vendor pages in §b
- **Read time:** ~45 min

## a. Does the named source cover this?

No. roadmap.sh/qa is a node graph and its per-node text is a stub. I fetched the
Playwright node from the content repo — this is the *entire* file:

> "Playwright is an open-source test automation library initially developed by
> Microsoft contributors. It supports programming languages such as Java, Python,
> C#, and NodeJS. Playwright comes with Apache 2.0 License and is most popular with
> NodeJS with Javascript/Typescript." — plus two links, one a BrowserStack
> marketing article.

Three sentences of neutral description: no selection criteria, no trade-offs, no
comparison. The node files are one-per-tool, so the graph never puts two tools side
by side — the exact thing the DELIVERABLE asks for. The landing page itself is nav,
community stats and CTAs, with no roadmap prose at all. (My directory listing
truncated at 100 files, alphabetically at `sanity-testing`, so I could not confirm
`selenium*`/`webdriverio*` nodes exist — immaterial, they'd be the same shape.)
Use roadmap.sh as a checklist of *what tools exist*. Nothing more.

## b. Best primary source

**Spine: CTAL-TAE v2.0 §2.2, "Evaluation Process for Selecting the Right Tools and
Strategies."** The only free, vendor-neutral, standards-body document I found that
describes the *act of choosing* rather than the tools — and it is deliverable-shaped:
§2.2.1 says analyze the SUT and gather requirements first; §2.2.2 says build a
comparison table with tools in columns and requirements in rows, then take the
proposal to stakeholders for approval. That *is* the decision note. §1.2.2 adds the
team-skill and language-match criteria; §1.1.1 supplies the limitations framing.
CTFL v4.0 §6.2 is the cheap companion (20 min, K1) — its eight-item *risk* list is
better beginner prompting material than the TAE chapter.

Tool facts must come from the vendors, one page each. Four of the five are candid:

1. **Cypress, "Trade-offs"** — https://docs.cypress.io/app/references/trade-offs.
   Best of the five: the vendor itself lists its permanent limitations.
2. **WebdriverIO, "Why WebdriverIO"** — https://webdriver.io/docs/why-webdriverio.
   Frames the choice as *standards vs. injected JS / patched browsers*, and raises
   governance (OpenJS Foundation) as a criterion.
3. **Playwright, "Browsers"** — https://playwright.dev/docs/browsers. The
   engine-vs-branded-browser caveat that decides Safari coverage. (Note
   `playwright.dev/docs/why-playwright` 404s; the pitch is on the landing page.)
4. **Puppeteer** — https://pptr.dev/. Self-describes as a *library*, not a test
   framework — the one fact that settles most Puppeteer-vs-X arguments.
5. **Selenium, "Overview of Test Automation"** —
   https://www.selenium.dev/documentation/test_practices/overview/, plus the
   *Discouraged behaviors* index https://www.selenium.dev/documentation/test_practices/discouraged/
   (captchas, file downloads, HTTP response codes, email/social logins, test
   dependency, performance testing, link spidering, two-factor auth).

Standards anchor: **W3C WebDriver BiDi** — https://www.w3.org/TR/webdriver-bidi/,
Working Draft 29 June 2026. The protocol split (W3C WebDriver / CDP / BiDi) that used
to separate these tools is converging, so "which protocol" is a weakening tiebreaker.

## c. What it leaves out

- **It never names a tool.** Deliberately — ISTQB syllabi are product-neutral. The
  spine gives the *method* and zero *content*: every row of the table comes from
  elsewhere.
- **Nothing web-specific.** No browser-engine coverage, no Safari/WebKit problem, no
  flakiness or auto-waiting, no headless-vs-headed, no trace/debug tooling, no
  parallelism model (Grid vs. workers) — the axes that separate these five.
- **No cost model.** §2.2.2 says costs "must always be considered" and stops. No CI
  minutes, no grid infrastructure, no maintenance-hours-per-test.
- **No weighting or tie-break rule.** It produces a table, not a decision. The lesson must supply
  the must-have vs. nice-to-have cut, or learners hand in a matrix with no recommendation.
- **Wrong reading level, and stale by construction.** 65 pages at K3/K4 for a working engineer;
  assign only the four pages above. Dated 2024-05-03 while these tools ship monthly.

## d. Credible disagreement

**1. Rapid Software Testing — the framing is wrong, not just the tools.** Bach &
Bolton, "Testing and Checking Refined" (satisfice.com, updated 2024-08-10), state
flatly: *"There is no such thing as automated testing. Testing cannot be automated."*
They allow tools a large role — *"a robust role for tools in testing must be
embraced"* — but only in support of skilled humans. Against QA-028 this bites: a
tool comparison compares **checking** engines. The RST move: reframe the note's
opening question from "which tool automates our testing?" to "which tool runs our
checks, and what does it cost us in the testing it can't do?" Bach's *Test Automation
Snake Oil* (1996; v2.1 1999) is the on-point essay —
https://www.satisfice.com/download/test-automation-snake-oil — but the PDF is
JavaScript-gated and **I could not fetch the text.** Do not quote it unread.

**2. A real vendor-level disagreement about architecture.** WebdriverIO's docs argue
that tools which download modified browser engines or inject JavaScript to emulate
behavior are the wrong bet, and that standardized W3C protocols buy long-term
stability and real-browser fidelity. Cypress's trade-offs page concedes the opposite
architecture and its consequences — it runs *inside* the browser and accepts
permanent limits as the price. Playwright sits between, and admits it "cannot work
with branded Safari." A decision note that doesn't pick a side here hasn't decided.

**3. Selenium disagrees with the premise that you should automate at all.** Its own
overview asks *"whether or not you really need to use a browser"* and says *"It is
not always advantageous to automate test cases"* — naming volatile UIs and tight
deadlines. Rare: a tool's docs telling you to consider not using it.

## e. Worked examples worth adapting

- **The Cypress trade-offs page is a ready-made exercise.** Give learners five
  constraints — "the flow opens a payment provider on another domain," "the app opens
  a receipt in a second tab," "the team writes Python," "we need real hover states,"
  "we must stub individual WebSocket frames" — and have them match each to the
  trade-off it hits. Four disqualify; one has a documented workaround (`cy.origin`).
- **The Safari question as a single decisive criterion.** "We must test real Safari"
  eliminates Playwright by its own documentation (§b3) and points at
  Selenium/WebdriverIO via `safaridriver` — the cleanest demonstration of why
  §2.2.1 comes before §2.2.2.
- **Selenium's *Discouraged behaviors* list as an all-tools-equal column.** Most of
  the eight are limits of browser automation *as a category*, not of Selenium — good
  for showing which table rows are useless for deciding. **I fetched only the index;
  per-item reasoning is on sub-pages I did not read.**
- **CTAL-TAE §2.2.2 is itself the template**: tools in columns, requirements in rows,
  cells hold properties *and priorities*. Hand out the empty table — the priorities
  column forces a recommendation.
- **Gap: no real defect story found.** No citable public postmortem of a team picking
  the wrong tool. Write it as an explicit hypothetical from a constraint above.

**[PDF] CTFL v4.0 §6.2 (pp.58–59):** "Simply acquiring a tool does not guarantee success.
