## a. Does the named source cover this?

No — and this is worse than the usual roadmap miss, because the node *does* exist
and is about the wrong kind of email. Its entire body is **two sentences**,
fetched verbatim from the content repo this session:

> "Email testing allows you to view your email before sending it out to your
> subscriber list to verify links, design, spelling errors, and more."

That is **marketing-email QA** — subscriber lists, rendering, spelling. Its three
outbound links are two vendor blog posts (Campaign Monitor, Sponge) and a daily.dev
tag feed. The words *password*, *token*, and *expiry* never appear. The deliverable
is a transactional-email problem about token lifetime, single use, and link
consumption; the node is pointed at newsletter proofreading. Nothing else in the
roadmap's QA content directory fills the gap — the only adjacent files are two tool
nodes, `mailinator` and `gmail-tester`. Drop it; unlike QA-035/QA-038, there is no
better page on this site to repoint to.

## b. Best primary source

**WSTG-ATHN-09 is the spine.** Free, versioned, no account, and written as a *test*
document rather than a build document — its "How to Test" section is literally a
list of questions to ask the system, which is the shape the deliverable wants.
"Email - Link Sent" covers the named topics directly: expiry, single use, token
entropy, host-header injection, referer leakage. **Pair it with two more, because
ATHN-09 covers reset only, not notifications:**

- **OWASP *Forgot Password Cheat Sheet*** — https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html — the prescriptive twin. Gives the *expected* behaviour ATHN-09 probes for, plus the post-reset notification email and the no-auto-login rule.
- **RFC 8058, *Signaling One-Click Functionality for List Email Headers*** — https://www.rfc-editor.org/rfc/rfc8058.txt — the notification half, and the only source here that states the root cause of the biggest defect class in this area (§1, quoted below).
- Deliverability, optional: **Gmail *Email sender guidelines*** — https://support.google.com/a/answer/81126 — SPF/DKIM/DMARC, PTR, TLS, spam rate <0.30%, one-click unsubscribe. Concrete enough to assert against.

## c. What it leaves out

- **"Broken links" in the ordinary sense is unaddressed.** ATHN-09 treats a link as
  a security object only. Nothing on the mundane failures that dominate real bug
  reports: URLs baked to `localhost` or a staging host in production mail, relative
  URLs that resolve nowhere in a mail client, tracking wrappers that 404.
- **No notification-email coverage at all.** That half needs RFC 8058 + Gmail's
  guidelines, and neither covers content correctness — unrendered `{{first_name}}`,
  wrong timezone on a timestamp, a digest firing on an empty set.
- **No test *mechanics*.** None say how you capture mail in a test environment
  (SMTP sink, Mailpit/MailHog, provider API, catch-all inbox). Not executable
  without picking one; the lesson must supply it.
- **Expiry has no agreed number.** ATHN-09 says "typically within one hour"; NIST
  SP 800-63B-4 §3.1.3.2 says 10 minutes. See (d) — different scopes.
- **Nothing on resend/idempotency:** click "resend" three times — all three tokens
  live, or only the last? Common real defect, absent from every source here.

## d. Credible disagreement

**The sharpest disagreement is not ISTQB vs RST — it is OWASP vs the observed
behaviour of corporate mail systems, and it lands on the deliverable's own word,
"expiry".** ATHN-09 and the Cheat Sheet both require the reset link be **single
use**, invalidated on visit. In production that is routinely broken, because
security scanners fetch the link before the human does. RFC 8058 §1 states why:

> "anti-spam software often fetches all resources in mail header fields
> automatically, without any action by the user, and there is no mechanical way for
> a sender to tell whether a request was made automatically … or manually
> requested by a user."

Its answer is to move the state change off GET and onto POST; several identity
vendors have been forced to the same conclusion for reset links (see (e)). So the
honest position to teach is **"single use" is a property of the token, not of the
URL, and the GET must be idempotent.** A tester who asserts only "the second click
fails" will pass a system unusable for every Outlook customer.

**Second, a scoping trap worth naming rather than resolving.** NIST SP 800-63B-4
§3.1.3.1 says *"Email SHALL NOT be used for out-of-band authentication"* — but the
same section carves out this exact case: recovery codes and email-validation codes
*"are not authentication processes and not affected by the above prohibition."*
NIST's 10-minute SHALL (§3.1.3.2) therefore governs OOB *authenticators*, not reset
links; citing it as "NIST says reset links expire in 10 minutes" would be wrong.
Teach the distinction; don't launder one number into the other. *(I did not fetch
Bach/Bolton RST this session and make no claim about it.)*

## e. Worked examples worth adapting

**The Safe Links defect family is the best real-defect story here** — one root
cause, four products, all public, all fetched this session, two failure modes:

1. **Prefetch consumes the token.** Authelia #2994 — https://github.com/authelia/authelia/issues/2994 — carries the detail that makes it teachable: the scanner arrives as *"a preceding HTTP HEAD request with a User-Agent of Go-http-client/1.1"*. A **HEAD**, not a GET — so "my test clicked the link" would never reproduce it.
2. **Rewriting mangles the token.** FusionAuth #629 — https://github.com/FusionAuth/fusionauth-issues/issues/629 — *"Outlook will rewrite email links to direct them towards https://\*.safelinks.protection.outlook.com/ with the original url encoded as a query parameter."* The reporter lists both hypotheses (encode/decode damage vs. GET consumption) without resolving them — a ready-made "how would you tell these apart?" exercise.
3. **The fix is a redesign, not a patch.** PKP #8392 — https://github.com/pkp/pkp-lib/issues/8392 — *"It will change the entire password reset process so that outlook's safelink feature will not have any impact."* Authentik #8953 shows the options weighed in the open: allow a second request inside a short window, or *"allow the use of a code and input form instead of a URL with a token as the argument."*

**Turn ATHN-09's "Email - Link Sent" question list straight into the test suite** —
already the right shape, ~ten yes/no questions, one test case each. **RFC 8058 adds
a negative test for notifications:** GET the `List-Unsubscribe` URL and assert the
user is *still subscribed*. Silent unsubscribes are otherwise invisible.
