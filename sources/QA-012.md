## b. Best primary source

**ISTQB CTFL v4.0, §4.5 plus §2.1.3.** Free, stable, and it covers *both* halves of the learning goal better than its reputation suggests:

- **"How testers encourage testable work"** — §4.5.1 gives INVEST (the T is Testable) and one genuinely good diagnostic: *"If a stakeholder does not know how to test a user story, this may indicate that the user story is not clear enough."* §5.1.2 (p.47) adds that testers in release planning "participate in writing testable user stories and acceptance criteria."

## c. What it leaves out

1. **Red-green-refactor as a loop.** ISTQB spends *two bullets* on TDD, and FL-2.1.3 is a **K1 (recall)** objective — the syllabus only asks you to name the approaches, not do them. The cycle is compressed into one clause: "Tests are written first, then the code is written to satisfy the tests, and then the tests and code are refactored." Take the cycle from **Fowler's bliki**, which states it in three numbered steps and cites Beck 2003 — the same citation ISTQB uses.
2. **"Watch it fail first."** Absent from ISTQB and from the roadmap. This is the most important mechanic in the loop: a test that has never been red proves nothing about the code, only that it compiles. Neither source says it. (Cucumber's BDD page comes closest — see quotes.)
3. **No worked example anywhere.** §4.5.2 names two formats — scenario-oriented (Given/When/Then) and rule-oriented — and gives **zero instances of either**. The deliverable asks for three acceptance examples; the primary source shows none. This gap must be filled by the lesson itself.
4. **Step size.** How small is one step? What do you do when the test won't go green? Neither source addresses it.
5. **Who actually does this.** TDD is a developer practice. ISTQB mentions the specification workshop but never says how a tester gets invited to one or what they do in the room — which is most of what this task's learner actually needs.

## d. Credible disagreement

Two separate disagreements. They are not the same objection and should not be blended.

**1. RST (Bach & Bolton) — an example is a *check*, not a test.** This lands on one specific ISTQB sentence, §4.5.3: *"Since examples and tests are the same, these terms are often used interchangeably."* RST says that interchangeability is precisely the error. From *Testing and Checking Refined* (satisfice.com, fetched this session): testing is *"the process of evaluating a product by learning about it through experiencing, exploring, and experimenting"*; checking is *"the mechanistic process of verifying propositions about the product."* Bach is blunt: *"I would say 'unit tests' are not tests. Checking is not the same as testing."* He does grant that *designing* the check is sapient work. Sharp framing for the lesson: three green acceptance examples mean the propositions you thought of are true. They say nothing about the ones you didn't.

**2. DHH — test-first damages design.** A developer-side objection, not a testing-philosophy one. *"Test-first units leads to an overly complex web of intermediary objects and indirection in order to avoid doing anything that's 'slow'"*, producing *"a dense jungle of service objects, command patterns, and worse."* He proposes rebalancing *"from unit to system"* tests. Worth including because it explains why a learner's team may already have rejected TDD.

## e. Worked examples worth adapting

- **Example Mapping (Cucumber) is the deliverable, already designed as an exercise.** Yellow card = the story; blue = rules/acceptance criteria; green = **examples illustrating those rules**; red = questions nobody can answer in the room. The green cards *are* the three acceptance examples. The red cards are the pedagogical payoff: writing examples first surfaces unanswered questions before any code exists. *Caveat: the Cucumber page itself contains no filled-in worked instance — it links out to Matt Wynne's and Steve Tooke's write-ups, which I did **not** fetch this session.*
- **ISTQB §4.5.3's ordering rule as a grading rubric.** Positive → negative → non-functional, no two examples covering the same characteristic. Hand the learner their own three examples back and check them against it.
- **Cucumber's three practices** — Discovery ("what it *could* do"), Formulation ("what it *should* do"), Automation ("what it *actually does*") — is a cleaner scaffold for the deliverable than anything in ISTQB, and explicitly describes the red step.
- **The mislabeled roadmap link from (a)** is itself a small teachable artifact: a curated resource pointing at a TDD article under an ATDD heading, inside a lesson about telling the two apart.

## Verbatim quotes

**ISTQB CTFL v4.0 §2.1.3, p.25** — "TDD, ATDD and BDD are similar development approaches, where tests are defined as a means of directing development." **TDD:** "Directs the coding through test cases (instead of extensive software design) (Beck 2003)" / "Tests are written first, then the code is written to satisfy the tests, and then the tests and code are refactored". **ATDD:** "Derives tests from acceptance criteria as part of the system design process (Gärtner 2011)" / "Tests are written before the part of the application is developed to satisfy the tests". **BDD:** "Expresses the desired behavior of an application with test cases written in a simple form of natural language, which is easy to understand by stakeholders – usually using the Given/When/Then format. (Chelimsky 2010)".

**ISTQB CTFL v4.0, FL-2.1.3, p.23** — "(K1) Recall the examples of test-first approaches to development". *(K1 = recall only. That is the whole ambition.)*

**ISTQB CTFL v4.0 §4.5.1, p.44** — "Good user stories should be: Independent, Negotiable, Valuable, Estimable, Small and Testable (INVEST) (Wake 2003)." … "If a stakeholder does not know how to test a user story, this may indicate that the user story is not clear enough, or that it does not reflect something valuable to them, or that the stakeholder just needs help in testing."

**ISTQB CTFL v4.0 §4.5.2, pp.44–45** — "Acceptance criteria for a user story are the conditions that an implementation of the user story must meet to be accepted by stakeholders. From this perspective, acceptance criteria may be viewed as the test conditions that should be exercised by the tests." … "The two most common formats are: Scenario-oriented (e.g., Given/When/Then format used in BDD…) / Rule-oriented (e.g., bullet point verification list, or tabulated form of input-output mapping)".

**ISTQB CTFL v4.0 §4.5.3, p.45** — "The first step is a specification workshop where the user story and (if not yet defined) its acceptance criteria are analyzed, discussed, and written by the team members." … "The test cases are based on the acceptance criteria and can be seen as examples of how the software works." … "Since examples and tests are the same, these terms are often used interchangeably." … "Typically, the first test cases are positive… After the positive test cases are done, the team should perform negative testing. Finally, the team should cover non-functional quality characteristics as well". … "no two test cases should describe the same characteristics of the user story." … "The acceptance tests then become executable requirements."

**ISTQB CTFL v4.0 §2.1.5, p.26** — good practices for shift-left include "Writing test cases before the code is written and have the code run in a test harness during code implementation".

**Fowler, TestDrivenDevelopment bliki** — "Test-Driven Development (TDD) is a technique for building software that guides software development by writing tests." Cycle: "Write a test for the next bit of functionality you want to add." / "Write the functional code until the test passes." / "Refactor both new and old code to make it well structured." — "often summarized as *Red - Green - Refactor*".

**Cucumber, BDD docs** — three practices: "Discovery: What it *could* do" / "Formulation: What it *should* do" / "Automation: What it *actually does*". … "taking one example at a time, we automate it by connecting it to the system as a test. The test fails because we have not implemented the behaviour it describes yet."

**Cucumber, Example Mapping** — story on "a yellow card and place it on top"; beneath it "acceptance criteria, or rules" (blue); under each rule "examples to illustrate these rules" (green); "questions that cannot be answered during the session" (red). "we keep going until the group is satisfied that the scope of the story is clear, or we run out of time."

**Bach & Bolton, Testing and Checking Refined** — testing is "the process of evaluating a product by learning about it through experiencing, exploring, and experimenting"; checking is "the mechanistic process of verifying propositions about the product." … "I would say 'unit tests' are not tests. Checking is not the same as testing."

**DHH, TDD is dead. Long live testing.** — "Test-first units leads to an overly complex web of intermediary objects and indirection in order to avoid doing anything that's 'slow'." … "A dense jungle of service objects, command patterns, and worse." … rebalance "from unit to system".
