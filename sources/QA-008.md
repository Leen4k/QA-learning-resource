## b. Best primary source

Be honest about the shape of this task: it asks to compare three *commercial products*. There is no standards body, no free syllabus and no neutral authority that describes them. Anything that compares all three in one document is either vendor marketing or SEO affiliate content (my searches surfaced a lot of both — `getautonoma.com`, `qasphere.com`, `testgrid.io`, and TestRail's own "why QA teams choose TestRail" blog). **Do not cite those.**

The primary sources are the three vendors' own data-model docs. Read them for structure, not for claims:

1. **qTest — Introduction to qTest Objects.** The best of the three: one page, every object defined, open to fetch. URL above.
2. **TestRail — Support Center.** Equally good content, but `support.testrail.com` returns **403 to automated fetches**; I read it through `r.jina.ai`. *Projects and their types* is the highest-value page — TestRail is the only one of the three that makes you choose a repository model up front, and it warns that changing it later destroys results.
3. **Zephyr — support.smartbear.com/zephyr-scale-cloud/docs/en/.** Also **403 direct**, partly readable via `r.jina.ai`, and several documented URLs 404 (the `terms-and-concepts` and `test-cases-overview` pages both failed this session). Weakest documentation of the three.

**A trick worth teaching: read the REST API reference, not the marketing site.** The API *is* the data model with the spin removed. TestRail's `get_runs` response exposes `plan_id`, `milestone_id`, `suite_id`, `passed_count`, `failed_count`, `blocked_count`, `untested_count`, `retest_count` — that single JSON object tells you more about how TestRail thinks than any feature page.

**Frame it with ISTQB CTFL v4.0 §6.1** (p.58), which is the whole of what the syllabus says on the subject — one bullet in a 20-minute chapter. Useful as the category definition and as evidence that the certification body treats this as trivia, not skill.

## c. What it leaves out

1. **"Zephyr" is not one product, and the names changed in 2025.** SmartBear unified the line at Atlassian Team '25 (April 2025): **Zephyr Squad → Zephyr Essential**, and **Zephyr Scale → "Zephyr"** on Standard/Advanced tiers. Zephyr Enterprise is a separate standalone platform not sold through the Atlassian Marketplace. The live product page I fetched lists **Essential / Standard / Advanced**; the docs still sit on `/zephyr-scale-cloud/` URLs, and one Squad-era docs page now renders with a "Zephyr Essential" title. Every comparison article the learner finds will use dead names. *(Rebrand confirmed via search results + the live product page; re-verify against SmartBear before this ships.)*
2. **No vendor doc tells you the trade-offs.** Each describes its own model as if it were the only sane one. The comparison axes — Jira-native vs standalone, folder tree vs suite/section, whether a test case is reusable across runs, whether results are versioned — must be constructed by the reader.
3. **Pricing and free tiers, which decide "which would I try first."** I found only secondary sources (G2, Vendr, vendor blogs) giving TestRail ~$35/user/mo, qTest ~$1,000/user/yr, Zephyr Scale ~$39/user/mo, none with a permanent free tier. **All of that is unverified** — check vendor pricing pages directly. This matters: the deliverable's second half is a *choice*, and a tool a learner cannot log into is not a real candidate.
4. **Migration and lock-in.** What happens when you leave. Nobody documents this willingly.
5. **The prior question — whether you need one of these at all.** See (d).

## d. Credible disagreement

**Michael Bolton / RST vs the entire premise of a test case management tool.**

The three products all assume the same unit of account: the *test case*, a stored, countable, re-runnable artifact. Bolton's "Breaking the Test Case Addiction" (11-part series, developsense.com, 2019–2020) attacks exactly that assumption. Fetched Part 1 this session:

- Tests get **"reified, turned into things, widgets… Effort becomes recast in terms of counting test cases, which leads to no end of mischief."**
- **"A mandate to follow a script removes agency, turning the tester into a robot instead of an investigator."**
- **"the most important things that testers do happen inside their heads: modeling the product, studying it, observing it"** — none of which a test case records.
- **"A test case doesn't tell people much about your modeling and evaluation of risk."**

This is the sharpest possible framing for the lesson, and it lands directly on the TestRail `get_runs` payload above: `passed_count` / `failed_count` / `untested_count` is precisely the "counting test cases" Bolton says leads to mischief. The tool's data model *is* the argument.

Don't blend them. Honest framing: the vendors tell you how to organize test cases; RST asks whether the count of them means anything. A learner who can hold both will pick a tool for what it lets them *see*, not for how many rows it holds.

*(I also chased a "keep test cases in Git instead" position. Everything I surfaced was vendor or affiliate content — testomat.io, remote.qa, testmanagement.com. **Not credible practitioner sources; do not cite.** The idea may be worth raising, but it needs a real source first.)*

## e. Worked examples worth adapting

- **The same 8 test cases, entered into all three.** The strongest exercise available, and it forces the deliverable. Take one small feature (login: valid, invalid password, locked account, empty field, SQL injection, session timeout, remember-me, password reset) and model it in each tool's trial. The learner discovers the differences by hitting them: in TestRail you must first pick a project type; in qTest you author in **Test Design** then separately build **Test Cycles → Test Suites → Test Runs** in Test Execution; in Zephyr you create cases in a folder tree and pull them into a **test cycle**, all inside Jira.
- **qTest's "Retain test design structure" checkbox** — documented behaviour: Test Design folders containing subfolders become **Test Cycles** in the execution tree, otherwise they become **Test Suites**. A perfect small worked example of design-time vs run-time structure diverging.
- **TestRail's project-type warning** as a real-consequences story: *"if you move test cases to another suite rather than copying them this will delete any test results of any not-yet closed runs"*, and you must close all active runs/plans before converting modes. An irreversible up-front decision with data loss attached — exactly the kind of thing a comparison should surface and a feature matrix never does.
- **TestRail's multi-suite limitation:** *"if you use multiple test suites, you will not be able to add test cases from more than one test suite in the same test run."* Concrete, checkable, and it decides real projects.
- **Read the three glossaries against each other.** "Test suite" means a container of *runs* in qTest and a container of *cases* in TestRail; Zephyr has no suite at all and uses folders plus cycles. Same word, three referents — a good 10-minute exercise and a genuine source of team confusion.
