## a. Does the named source cover this?

No. It is a certification storefront. Read this session through a text proxy
(istqb.org 403s direct fetches), the page's complete heading list is:
**Overview, Audience, Content, Exam Structure, Business Outcomes, More
Information, Download Materials, Syllabus, Sample Exams, Exam Structures and
Rules, General Files.**

The proxy fetch found **zero occurrences** of "test level", "unit",
"integration", "system testing" or "acceptance testing" anywhere on the page. Not
a thin treatment — an absent one. A learner sent here cannot produce a test-level
map because they will not learn that test levels exist. Its only value is the
**Download Materials → Syllabus** link, the real source (§b). Repoint the plan
line at the PDF, not the storefront.

Caveat (as in QA-006): the named URL looks like a legacy path — the live CTFL v4.0

## b. Best primary source

ISTQB CTFL Syllabus v4.0, **§2.2 Test Levels and Test Types**, pp.27–28. Free,
stable, versioned, and the document the named page is selling. Learning
objective **FL-2.2.1 (K2) "Distinguish the different test levels"** — exactly
this task's goal.

- §2.2 intro (p.27) — what a test level *is*, and how levels relate to the SDLC
- §2.2.1 (pp.27–28) — the five levels, plus the five attributes that distinguish them
- §5.1.6 Test Pyramid (p.49) — granularity, isolation, speed; effort allocation
- §5.1.7 Testing Quadrants (p.50) — a second axis to overlay on the map

**The most useful thing in it for the deliverable** is the attribute list closing
§2.2.1: levels are distinguished by **test object, test objectives, test basis,
defects and failures, approach and responsibilities**. Those five are the *column
headers* of the learner's map — and the syllabus names the columns without ever
filling the table in. Filling it in is the lesson.

## c. What it leaves out

1. **The table itself.** §2.2.1 spends ~250 words on five levels, lists five
   attributes, then stops — never working one level through all five. The
   artifact the deliverable asks for is the one the syllabus declines to produce.
2. **Any worked example or diagram.** No request path, no trace from UI to
   database. Chapter 2 contains no example at all at this level.
3. **Every technical specific a web request needs.** No HTTP, no
   controller/service/repository, no test doubles, no in-memory database, no
   contract testing (a real level in modern web systems, absent entirely). Its
   integration vocabulary is "bottom-up, top-down or big-bang" — monolith
   build-order framing, not a modern stack.
4. **Where to draw the boundary.** It says levels "may overlap in time" and that
   the attributes exist "to avoid overlapping of test activities", but gives no
   rule for deciding a borderline case — the hard question a learner hits within
   five minutes of drawing the map.
5. **That the names are contested** (presented as settled taxonomy — see §d), and
   **cost/speed/flakiness trade-offs**, which sit 20 pages away in §5.1.6 and are
   never joined up to §2.2.1. The lesson has to do that stitching.

## d. Credible disagreement

Three distinct dissents, on three different axes. Do not blend them.

**ISTQB's axis is lifecycle stage.** A test level is "an instance of the test
process, performed in relation to software at a given stage of development."

**Google's axis is resources touched.** *Software Engineering at Google* ch.11
(https://abseil.io/resources/swe-book/html/ch11.html) explicitly rejects the
scope naming in favour of size (quote below). Small = single process, no
sleeping/I/O/blocking calls; Medium = multiple processes, network calls to
`localhost` only; Large = multiple machines. That is a usable decision rule.

**Fowler/Vocke: the names don't survive contact.** The pyramid's layer names "can
be quite misleading", and on the base level: "If you ask three different people
what 'unit' means in the context of unit tests, you'll probably receive four
different, slightly nuanced answers."

**RST/Bach's axis is risk, and he rejects the stack outright.** The Round Earth
Test Strategy (https://www.satisfice.com/blog/archives/4947) calls the pyramid "a
context-free geometric analogy... this is not an argument; this is not reasoning"
— the shape is asserted, not earned. He replaces it with concentric spheres in
which "risk grows toward the user", inverting the pyramid so attention lands on
"the surface of the product, 'where the people live.'"

Honest framing: ISTQB gives the learner vocabulary their colleagues will actually
use, which is worth having. It does not give them a *decision procedure* for
which level a test belongs to — Google's resource rule does, and RST denies the
stack is the right shape at all.

*(All three fetched this session. The Round Earth quotes came via a summarising
fetch — re-read that post directly before quoting it in a lesson.)*

## e. Worked examples worth adapting

- **"The Practical Test Pyramid", Ham Vocke (martinfowler.com)** —
  https://martinfowler.com/articles/practical-test-pyramid.html — the closest
  free thing to this exact deliverable. A Spring Boot service with three
  endpoints (`GET /hello`, `/hello/{lastname}`, `/weather`), four layers
  (**Controller, Repository, Client, Domain**), a PostgreSQL database and one
  external HTTP API. It shows a real test at *each* level: unit (mock the
  `PersonRepository`), narrow integration (H2 in-memory DB; Wiremock for the
  external API), contract (Pact, both sides), UI (Selenium), end-to-end
  (REST-assured). Adapt this architecture as the spine of the map — it is already
  UI→DB. On the top level: "you should aim to reduce the number of end-to-end
  tests to a bare minimum."
- **Ariane 5 Flight 501** — the canonical proof that passing at one level says
  nothing about the next. The inertial reference software was correct, reused
  from Ariane 4, and killed the rocket when integrated into a vehicle with a
  different trajectory. See the Inquiry Board quote below. (Official ESA PDF is a
  scan with no text layer; readable transcript at
  https://www.di.unito.it/~damiani/ariane5rep.html — verify against the official
  report before shipping.)
- **Exercise that writes itself:** hand the learner §2.2.1's five attributes as
  blank columns and the five levels as rows, for one login request. That *is* the
  deliverable — and exactly the table ISTQB omits.

## Verbatim quotes

**§2.2, p.27** — "Test levels are groups of test activities that are organized and managed together. Each test level is an instance of the test process, performed in relation to software at a given stage of development, from individual components to complete systems or, where applicable, systems of systems."

**§2.2, p.27** — "In sequential SDLC models, the test levels are often defined such that the exit criteria of one level are part of the entry criteria for the next level. In some iterative models, this may not apply. Development activities may span through multiple test levels. Test levels may overlap in time."

**§2.2.1, pp.27–28** — "Component testing (also known as unit testing) focuses on testing components in isolation. It often requires specific support, such as test harnesses or unit test frameworks. Component testing is normally performed by developers in their development environments." / "Component integration testing (also known as unit integration testing) focuses on testing the interfaces and interactions between components. Component integration testing is heavily dependent on the integration strategy approaches like bottom-up, top-down or big-bang."

**§2.2.1, pp.27–28** — "System testing focuses on the overall behavior and capabilities of an entire system or product, often including functional testing of end-to-end tasks and the non-functional testing of quality characteristics... System testing may be performed by an independent test team, and is related to specifications for the system." / "System integration testing focuses on testing the interfaces of the system under test and other systems and external services."

**§2.2.1, p.28** — "Acceptance testing focuses on validation and on demonstrating readiness for deployment, which means that the system fulfills the user's business needs. Ideally, acceptance testing should be performed by the intended users. The main forms of acceptance testing are: user acceptance testing (UAT), operational acceptance testing, contractual and regulatory acceptance testing, alpha testing and beta testing."

**§2.2.1, p.28** — "Test levels are distinguished by the following non-exhaustive list of attributes, to avoid overlapping of test activities: • Test object • Test objectives • Test basis • Defects and failures • Approach and responsibilities"

**§5.1.6, p.49** — "The higher the layer, the lower the test granularity, test isolation and test execution time. Tests in the bottom layer are small, isolated, fast... The top layer represents complex, high-level, end-to-end tests."

**SWE at Google, ch.11** — "we make this distinction, as opposed to the more traditional 'unit' or 'integration,' because the most important qualities we want from our test suite are speed and determinism, regardless of the scope of the test."

**Vocke, The Practical Test Pyramid** — "Don't become too attached to the names of the individual layers in Cohn's test pyramid. In fact they can be quite misleading."

**Bach, Round Earth Test Strategy** — "The original pyramid (really a triangle) was a context-free geometric analogy... this is not an argument; this is not reasoning."

**Ariane 5 Inquiry Board report** — "No test was performed to verify that the SRI would behave correctly when being subjected to the count-down and flight time sequence and the trajectory of Ariane 5."
