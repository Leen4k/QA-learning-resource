# QA-050 — Automate a critical end-to-end flow

> Dossier, not lesson content. Every claim below must be re-read at source
> before it ships in a lesson.

- **Verdict:** WRONG-DOCUMENT
- **Named source:** https://playwright.dev/docs/intro
- **Best primary source:** Playwright Test official docs — https://playwright.dev/docs/best-practices (spine), with https://playwright.dev/docs/auth as the deliverable's crux
- **Exact sections to read:** In order — *Writing tests* (§Actions, §Assertions, §Test isolation); *Best Practices* (§Test user-visible behavior, §Make tests as isolated as possible, §Avoid testing third-party dependencies, §Use locators, §Use web first assertions); *Authentication* (§Basic: shared account, signed-in state, §**Multiple signed in roles**, §**Testing multiple roles together**); *Page object models*.
- **Read time:** ~50 min (10 / 15 / 20 / 5)

## a. Does the named source cover this?

No. `/docs/intro` is titled **Installation**. It covers `npm init playwright@latest`, what the scaffold writes, how to run the example suite, HTML reports, UI Mode, Node version requirements, and how to upgrade. It contains no locator, no assertion, no login, no workflow. It teaches the precondition and stops.

The page says so itself — it ends by pointing at the next steps: *"Write tests using web-first assertions, fixtures and locators."* The plan link is one click short of the material the deliverable actually needs.

This is a one-line URL swap, not a research problem. But note the swap is not to *one* page: the deliverable has three parts (log in, drive a workflow, hit an approval/decision point) and no single Playwright page covers them. `/docs/intro` still belongs in the lesson — as the 10-minute setup step before the reading, not as the source.

## b. Best primary source

Playwright's own docs are unambiguously the right authority here; the task is "use this tool well." Two pages carry it:

**Best Practices** is the maintainability spine — it is where the learning goal's word "maintainable" is actually defined: user-visible behaviour over implementation details, role/text locators over CSS and XPath, web-first assertions over manual checks, isolation, and mocking anything you don't control.

**Authentication** is the crux, and the reason this task is worth 10 hours. It answers both hard parts of the deliverable:

| Deliverable phrase | Section |
|---|---|
| "Automate login" | §Basic: shared account — log in once in a **setup project**, save `storageState` to `playwright/.auth/user.json`, bootstrap every test already signed in |
| "one critical workflow" | *Writing tests* §Actions + §Assertions |
| "**including an approval or decision point**" | §**Testing multiple roles together** — two `browser.newContext()` calls with different `storageState`, so a requester and an approver act in the same test |
| "maintainable" | *Best Practices* + *Page object models* |

That last row is the find. An approval point means two actors, and Playwright ships the exact pattern for it. A learner who writes login inline in every test — the obvious first instinct — produces the unmaintainable version of this deliverable; the setup-project/`storageState` pattern is what separates a capstone from a demo.

## c. What it leaves out

- **Which journey to automate.** "Critical" and "high-value" are risk judgments; the Playwright docs never raise the question. Fowler supplies the missing sentence (§d). Without it the learner automates whatever is easiest to click.
- **Server-side state and teardown — the big one.** Playwright's "Test isolation" means *browser* isolation only: *"Pages are isolated between tests due to the Browser Context."* An approval workflow **mutates the database**. Run the test twice and the second run finds the request already approved. Nothing in the pages read here tells the learner to seed a fresh record per run or to clean up. This is the single most likely reason a QA-050 submission passes once and never again — teach it explicitly.
- **How to create the precondition.** The approval test needs a record already in "awaiting approval". Seed via API (`request` fixture) or drive the UI? Best Practices says only to test against a staging environment with controlled data and stops there.
- **What to assert at a decision point.** Only the happy branch is obvious. The interesting assertions are the rejected branch, and the negative authorization case — *can a non-approver approve?* The docs treat assertions as a syntax topic, not a design one. (That negative case overlaps QA-051's authorization checks; decide which task owns it.)
- **What to do when it flakes.** Docs cover writing non-flaky tests; there is a `/docs/test-retries` page I did **not** read this session — check it before writing the quarantine-vs-fix guidance.

## d. Credible disagreement

**1. Google disagrees with the task's premise.** *"Just Say No to More End-to-End Tests"* (Google Testing Blog, Apr 2015) argues the E2E advantage of simulating real users is *"quickly outweighed by all the disadvantages of the end-to-end feedback loop"* — flake volume, runtime inflation, and the cost of localizing a failure across integrated systems. It puts the mix near 70% unit / 20% integration / 10% E2E. QA-050 asks for exactly one E2E test, which is compatible; but a lesson that presents E2E automation as the *goal* of a QA course would be contradicted here.

**2. Fowler sharpens it into scope advice, and it happens to endorse the deliverable.** *"Due to their high maintenance cost you should aim to reduce the number of end-to-end tests to a bare minimum"* — then: *"Try to come up with user journeys that define the core value of your product and translate the most important steps of these user journeys into automated end-to-end tests… Maybe you'll find one or two more crucial user journeys… Everything more than that will likely be more painful than helpful."* Use this to justify why the deliverable says **one** flow. The correct lesson framing is "one is the target, not the starting point."

**3. RST: what the learner produces is a check, not a test.** Bach & Bolton define **checking** as *"the mechanistic process of verifying propositions about the product"* and **testing** as *"evaluating a product by learning about it through experiencing, exploring, and experimenting."* Their line is hard: *"checking is a process that can, in principle be performed by a tool,"* whereas *"testing can only be supported by tools"* — *"Humans can perform motivated actions; tools can only exhibit programmed behaviour."*

So an automated login-and-approve script confirms propositions the learner already believed. It will never find the bug nobody predicted. Do not let the capstone imply the flow has been "tested" — QA-049 (manual cycle) is the testing half; QA-050 is the checking half. Saying this out loud is the most useful thing the lesson can do, and it costs one paragraph.

## e. Worked examples worth adapting

- **`tests-examples/demo-todo-app.spec.ts`** — shipped locally by `npm init playwright@latest`, so the learner already has it after the setup step. 25 tests across 8 `describe` blocks (New Todo, Mark all as completed, Item, Editing, Counter, Clear completed button, Persistence, Routing). *Caveat: I read a public third-party mirror, not the microsoft repo path — the official raw URLs I tried 404'd. Verify against the locally generated file.*
- **Its Persistence test is the closest thing to the deliverable's shape**: act → assert → `page.reload()` → assert the same things again. That is the "did the decision actually stick?" move an approval test needs.
- **Its `checkNumberOfCompletedTodosInLocalStorage` helper** teaches the deeper point: assert the state *behind* the UI, not only the rendered text. Adapt as an API check that the approval was persisted server-side, not just that a green badge appeared.
- **The two-context example from *Authentication* §Testing multiple roles together** is the exercise skeleton, near-verbatim: build `adminContext` and `userContext` from different `storageState` files, have the user submit in `userPage`, the admin approve in `adminPage`, then assert the user sees the approved state. Give the learner this scaffold and let them fill in their own app.
- **`npx playwright codegen`** as a deliberate teaching trap: record the flow, then have the learner rewrite every generated locator by hand into `getByRole`/`getByLabel`. The diff between recorded and rewritten *is* the maintainability lesson.
- **Real story, usable as-is:** the Google post's scenario of a team waiting **three days** for E2E results only to learn the fix hadn't worked. No fetched defect story about an approval flow specifically — do not invent one.

## Verbatim quotes

**Playwright, /docs/intro (Installation):** next-steps list includes "Write tests using web-first assertions, fixtures and locators". Page scope is install, scaffold, run examples, reports, UI Mode, system requirements, upgrading.

**Playwright, Best Practices:** "Automated tests should verify that the application code works for the end users, and avoid relying on implementation details." · "Each test should be completely isolated from another test and should run independently with its own local storage, session storage, data, cookies etc." · locators have "auto waiting and retry-ability"; prefer `page.getByRole('button', { name: 'submit' })` over CSS/XPath. · "By using web first assertions Playwright will wait until the expected condition is met." · on external services, "use the Playwright Network API and guarantee the response needed".

**Playwright, Writing tests:** "Locators represent a way to find element(s) on the page at any moment." · "Playwright waits for the element to be actionable before performing the action, so you don't need to wait for it to become available." · "Playwright includes async matchers that wait until the expected condition is met. Using these matchers makes tests non-flaky and resilient." · "Pages are isolated between tests due to the Browser Context, which is equivalent to a brand new browser profile."

**Playwright, Authentication:** "We recommend to create `playwright/.auth` directory and add it to your `.gitignore`… tests will reuse this state and start already authenticated." · shared-account case works "without server-side state. Authenticate once in the setup project, save the authentication state, and then reuse it to bootstrap each test already authenticated" — appropriate "When you can imagine all your tests running at the same time with the same account, without affecting each other." · per-worker auth is for when "Your tests modify shared server-side state." · §Multiple signed in roles: "You have more than one role in your end to end tests, but you can reuse accounts across all tests." · §Testing multiple roles together: "You need to test how multiple authenticated roles interact together, in a single test" — via `browser.newContext({ storageState: 'playwright/.auth/admin.json' })` and a second context for the user.

**Playwright, Page object models:** "Page object models… simplify maintenance by capturing element selectors in one place and create reusable code to avoid repetition."

**Google Testing Blog, "Just Say No to More End-to-End Tests" (Apr 2015):** "if you mostly use E2E tests, then your test runtime (and the number of test flakes) will inflate significantly." · the E2E realism advantage is "quickly outweighed by all the disadvantages of the end-to-end feedback loop." · mix ≈ 70/20/10 unit/integration/E2E; "in general, it should retain that pyramid shape."

**Fowler, "The Practical Test Pyramid":** "Due to their high maintenance cost you should aim to reduce the number of end-to-end tests to a bare minimum." · "They are notoriously flaky and often fail for unexpected and unforeseeable reasons." · "Browser quirks, timing issues, animations and unexpected popup dialogs…" · "Try to come up with user journeys that define the core value of your product and translate the most important steps of these user journeys into automated end-to-end tests." · "Everything more than that will likely be more painful than helpful."

**Bach & Bolton, "Testing and Checking Refined" (satisfice.com):** testing is "the process of evaluating a product by learning about it through experiencing, exploring, and experimenting…"; checking is "the mechanistic process of verifying propositions about the product." · "testing can only be *supported* by tools" while "checking is a process that can, in principle be performed by a tool." · "Humans can perform motivated *actions*; tools can only exhibit programmed *behaviour*."
