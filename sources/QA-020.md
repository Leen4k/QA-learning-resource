# QA-020 — Browser developer tools

> Dossier, not lesson content. Every claim below must be re-read at source
> before it ships in a lesson.

- **Verdict:** PARTIAL
- **Named source:** https://developer.chrome.com/docs/devtools
- **Best primary source:** Chrome DevTools documentation — the same doc set, pointed two levels deeper: https://developer.chrome.com/docs/devtools/dom, /javascript, /network, /network/reference, /storage/localstorage
- **Exact sections to read:** `/dom` "View DOM nodes" → "Edit the DOM" → "Force state" → "Access nodes in the Console"; `/javascript` steps 1–8; `/network` whole tutorial; `/network/reference` the five capture headings quoted below; `/storage/localstorage` whole page
- **Read time:** ~75 min hands-on (dom ~15, javascript ~20, network ~20, network/reference ~10, localstorage ~5, console overview ~5)

## a. Does the named source cover this?

Half. The URL in the plan is an **index page, not a document** — but unlike a roadmap
page, it is the front door to the right doc set, and the real teaching is two clicks away.

The landing page itself is navigation: a nav rail (AI assistance / Panels / Settings /
Accessibility / For agents), a grid of feature cards, and one paragraph of marketing prose.
`/docs/devtools/overview` is barely better — it names each panel in a single sentence
("Elements panel: View and change the DOM and CSS.") and links out. Neither page would
leave a learner able to investigate anything.

The sub-pages, however, are strong and cover three of the four named panels as **hands-on
tutorials with live demo pages**:

- **Elements** → `/dom`: interactive, embedded demos, 18 headings from "Inspect a node"
  through "Force state" and "Break on DOM changes".
- **Console** → `/console/`: thin overview ("Viewing logged messages", "Running
  JavaScript") but links to real sub-pages.
- **Sources/JS** → `/javascript`: an 8-step tutorial against a deliberately broken hosted
  demo (`5 + 1 = 51`).
- **Network** → `/network`: 10-step hands-on tutorial with its own demo page; `/network/reference`
  adds HAR export, Copy as cURL, Preserve log, Disable cache, throttling.
- **Storage** → `/storage/localstorage`: ~450 words of where-to-click. This is the weak one.

Two naming traps for the lesson: the deliverable says "Storage", Chrome calls the panel
**Application**. And the overview page's Application blurb still advertises "Web SQL
databases" and "Application Cache" — both removed from Chrome years ago. That page is not
well maintained; do not quote it as current.

**So the verdict is PARTIAL for two reasons, and only one is about the URL.** Fix the URL
by naming the five sub-pages. The second reason is not fixable by relinking: this doc set
is written for developers fixing their own code, and the task's `wants` line is *"when
reproducing issues."* See (c).

## b. Best primary source

**Chrome DevTools docs, the specific pages listed above.** There is no better primary
source and no need to look for one — it is the vendor's own documentation for the tool,
free, stable, versioned with the browser, and genuinely instructional at depth. The plan
does not need a different source; it needs a more precise pointer.

**Secondary, for cross-browser reality:** Firefox DevTools user docs —
https://firefox-source-docs.mozilla.org/devtools-user/ — Mozilla's official set, with
Page Inspector, Web Console, Network Monitor, and a **Storage Inspector** ("Inspect
cookies, local storage, indexedDB, and session storage present in a page"). Worth one link
because QA-019 and QA-021 both already point at MDN, and because a Safari- or Firefox-only
bug is a routine QA situation that the Chrome docs cannot help with.

## c. What it leaves out

Everything that makes this a *testing* task rather than a debugging task:

1. **Reproduction.** Step 1 of the JS tutorial is literally "Reproduce the bug", and the
   bug is `5 + 1 = 51` — deterministic, one click, always. The docs contain no method for
   establishing repro steps, narrowing variables, or handling a failure that only happens
   sometimes. That is the entire content of the `wants` line.
2. **Evidence capture as a deliverable.** HAR export, Copy as cURL, screenshots and
   Preserve log all exist in `/network/reference` — but as feature descriptions, never
   framed as "this is what you attach to the ticket." Nothing tells a learner what to
   attach or in what order. Note the export is named "Save all as HAR **(sanitized)**":
   HARs carry cookies and auth tokens, and the docs do not dwell on why that matters.
3. **Storage concepts.** `/storage/localstorage` explains where to click, not what
   localStorage vs sessionStorage vs cookies are, nor why stale storage produces
   "works on my machine." Clearing storage and re-testing is the highest-value QA move in
   that panel and it is not taught.
4. **Reading an error.** The obvious page — `/console/understand-messages` — turned out to
   be a **Gemini feature page**, not a guide to stack traces. It requires being 18+, in a
   supported location, signed into Chrome with a Google account, and English (US). There is
   no plain "how to read a console error" page. Real gap; the lesson must supply it.
5. **Where to stop.** Every tutorial ends at "Apply a fix." Nothing addresses the handoff
   boundary — how far a tester should investigate before writing the bug up.

## d. Credible disagreement

The Chrome docs model an issue as: reproduce (trivial) → inspect → localise → fix. The
context-driven camp puts nearly all the difficulty in the step the docs skip, and disagrees
about what a tester owes before reporting.

**Bach, "'Mipping': A Strategy for Reporting Iffy Bugs"** (satisfice.com/blog/archives/97).
His rule is "All bugs shall be reported, without exception" — anything questionable gets
*mentioned in passing* in a status report rather than either formally investigated or
silently dropped. That cuts against the implicit lesson of the DevTools tutorials, which is
that you diagnose first and report a localised cause. Under mipping, an observation you
cannot reproduce and cannot explain is still reportable, immediately.

The lesson should land this as a limit on the tool: DevTools makes it feel like every bug
should be root-caused before it is written up, and that feeling makes testers sit on
findings they cannot yet explain.

## e. Worked examples worth adapting

1. **The `5 + 1 = 51` demo** — https://googlechrome.github.io/devtools-samples/debug-js/get-started
   Live, hosted, free, no setup, deliberately broken (string concatenation instead of
   addition). The best ready-made "sample UI problem" available.
2. **Network tutorial demo** — https://chrome.dev/devtools-network-activity/getstarted.html
3. **The adaptation problem.** The JS demo exercises Sources and Console but touches
   neither Network nor Storage, and the deliverable names four panels. Stitching two demos
   together is one option; the better one is a **stale-localStorage bug**, which is the
   classic case that forces all four panels: Elements shows the wrong rendered state,
   Console shows the error, Network shows the request that returned perfectly fine, Storage
   shows the stale value — and clearing it fixes the page. That also feeds directly into
   QA-021 (caching and stale states), the very next task in the plan.
4. **Gap:** no real, published defect story anywhere in the Chrome docs — constructed demos
   only. If the lesson wants a true story it must come from elsewhere or be labelled a
   hypothetical.

## Verbatim quotes

**Landing page, https://developer.chrome.com/docs/devtools** (the whole body prose):
- "Chrome DevTools is a set of web developer tools built directly into the Google Chrome browser. DevTools lets you edit pages on-the-fly and diagnose problems quickly, which helps you build better websites, faster."

**`/docs/devtools/overview`, panel blurbs — the entire treatment of each:**
- Elements panel: "View and change the DOM and CSS."
- Console panel: "View messages and run JavaScript from the Console."
- Network panel: "View and debug network activity."
- Application panel: "Inspect all resources that are loaded, including IndexedDB or Web SQL databases, local and session storage, cookies, Application Cache, images, fonts, and stylesheets." *(stale: Web SQL and Application Cache are gone from Chrome)*

**`/docs/devtools/javascript`:**
- "This tutorial teaches you the basic workflow for debugging any JavaScript issue in DevTools."
- "The label below the button says `5 + 1 = 51`. The result should be `6`. This is the bug you're going to fix."
- Steps: 1 Reproduce the bug / 2 Get familiar with the Sources panel UI / 3 Pause the code with a breakpoint / 4 Step through the code / 5 Set a line-of-code breakpoint / 6 Check variable values / 7 Apply a fix / 8 Next steps

**`/docs/devtools/network`:**
- "This is a hands-on tutorial of some of the most commonly-used DevTools features related to inspecting a page's network activity."
- "Click the **Timing** tab to view a breakdown of the network activity for this resource."

**`/docs/devtools/network/reference` — the five evidence-capture headings:**
- "Save all network requests to a HAR file" → "Copy > Save all [listed] as HAR (sanitized)"
- "Copy as cURL" (under "Copy a request, a filtered set of requests, or all of them to the clipboard")
- "Save requests across page loads" → "check the **Preserve log** checkbox"
- "Emulate a first-time visitor by disabling the browser cache" → "check the **Disable cache** checkbox"
- "Emulate slow network connections" → "select the corresponding preset from the **Throttling** drop-down menu"

**`/docs/devtools/storage/localstorage` (complete intro):**
- "This guide shows you how to use Chrome DevTools to view, edit, and delete `localStorage` key-value pairs. Local storage saves data across browser sessions."

**`/docs/devtools/console/understand-messages` — not what the title suggests:**
- "Ask Gemini to provide insights right in the DevTools **Console**, so you can better understand errors and warnings."
- Requirements include: "Are at least 18 years old and are in one of the supported locations" and "Are signed into Chrome with your Google Account."

**Bach, "'Mipping': A Strategy for Reporting Iffy Bugs"** (satisfice.com/blog/archives/97):
- "Mention In Passing, or 'mipping'. All bugs shall be reported, without exception."
- "Any bug that seems questionable or prohibited we will 'mention in passing' in our status reports or emails."
- "That way we are not accused of wasting time investigating and reporting the bug formally, but we also can't be accused of missing it entirely."
