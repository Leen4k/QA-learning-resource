# QA-021 — Async requests, caching, and rendering

> Dossier, not lesson content. Every claim below must be re-read at source
> before it ships in a lesson.

- **Verdict:** WRONG-DOCUMENT
- **Named source:** https://developer.mozilla.org/en-US/docs/Learn_web_development
- **Best primary source:** MDN, "HTTP caching" — https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching
- **Exact sections to read:** MDN HTTP caching §"Fresh and stale based on age", §"Validation" (incl. ETag/If-None-Match), §"Don't cache", §"Heuristic caching", §"Reload and force reload" — plus MDN `Window: fetch()` rejection note, MDN "Critical rendering path", and Playwright §"Abort requests" + §"Mock API requests"
- **Read time:** ~55 min

## a. Does the named source cover this?

No — twice over.

**First, it is a front door, not a document.** `/Learn_web_development` is the index
of MDN's entire curriculum. Its own prose is orientation copy ("Don't know where to
get started?", "Test your skills", "Contact us"). Citing it for a specific 4-hour
task is citing a table of contents.

**Second — the real problem — the tree it indexes does not cover two of the three
named topics.** I walked it:

- **Async requests:** covered, thinly. `Core/Scripting/Network_requests` teaches
  `fetch`, `response.ok`, and a `.catch`. It never mentions loading states, retry,
  or *why* `fetch` behaves the way it does on a 500. `Extensions/Async_JS` covers
  promises, `async`/`await`, workers.
- **Caching:** **absent.** No caching module in Learn. I checked Extensions → Web
  Performance — all 11 articles (perceived performance, measuring, images, video,
  performant JS/HTML/CSS, business case, best practices); none covers HTTP caching.
  The real material is in MDN's `Web/HTTP` tree, which Learn does not route you to.
- **Rendering:** **absent from Learn.** Critical rendering path lives under
  `Web/Performance/Guides/`, outside the curriculum this URL indexes.

Against the DELIVERABLE — **loading, failure, retry, stale-cache** — the named source
and everything reachable from it gives one of four states (failure, partially) and no
tooling to provoke any of them. Same URL is already named on QA-019; reusing a
curriculum index across two tasks is the tell that no one picked a document for either.

## b. Best primary source

**MDN, "HTTP caching"** — https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching

Free, stable, ~25 min, and it owns the one concept the learner will otherwise get
wrong. "Stale" is not a synonym for "wrong" or "old" — it is a defined protocol
state with a defined transition (validation) back to fresh. A tester who does not
know that will write "check the cache clears," which is not a check.

It covers one third of the task. There is no single document for all three; the
honest spine is:

- **Stale-cache** — MDN HTTP caching (above), §Fresh and stale based on age,
  §Validation, §Don't cache, §Heuristic caching, §Reload and force reload.
- **Failure semantics** — MDN `Window: fetch()`, the rejection note —
  https://developer.mozilla.org/en-US/docs/Web/API/Window/fetch
- **Rendering** — MDN "Critical rendering path" (DOM → CSSOM → Render Tree → Layout
  → Paint) — https://developer.mozilla.org/en-US/docs/Web/Performance/Guides/Critical_rendering_path
- **Provoking the states** — Playwright §Abort requests, §Mock API requests, §Modify
  API responses — https://playwright.dev/docs/network , https://playwright.dev/docs/mock
- **Manual equivalent** — Chrome DevTools Network reference, §Disable cache,
  §Emulate slow network connections, §Emulate offline —
  https://developer.chrome.com/docs/devtools/network/reference

**RFC 9111 (HTTP Caching)** — https://www.rfc-editor.org/rfc/rfc9111.html — is the
normative authority (§4.2 fresh/stale/freshness lifetime, §4.2.4 serving stale, §4.3
validation). Cite for precision; do not assign as reading. MDN says it in a tenth of
the words.

## c. What it leaves out

- **Retry — nothing, anywhere.** Not MDN, not RFC 9111, not Playwright's guides. One
  quarter of the deliverable has **no primary source**. The lesson must supply the
  model: what is retried (idempotent GETs, not POSTs), how many times, backoff, and —
  the tester's question — whether the *user* can tell a retry is happening.
- **Loading states.** MDN teaches how to fire a request, never what to show while it
  is in flight. Nothing on spinners vs. skeletons, no minimum-display-time problem
  (the flash of a 50ms spinner), no double-submit while pending.
- **Application-level caching.** MDN's guide is the HTTP cache. Most stale data a
  tester meets comes from a client cache *above* HTTP — TanStack Query, SWR, Apollo —
  with its own `staleTime`/`gcTime` that HTTP headers do not govern.
- **"Rendering" in this task is doing the wrong job.** The critical rendering path is
  a *performance* topic (DOM → CSSOM → paint). The deliverable needs "what does the UI
  render in each state" — state coverage, not pipeline. Read CRP for vocabulary; don't
  let it set the lesson's agenda.
- **Combinatorics.** Four states × data origin (network / HTTP cache / app cache /
  bfcache) is a matrix. No source tells the learner to build one.

## d. Credible disagreement

1. **Mock the network** (Playwright's documented position). `route.abort('timedout')`
   and `route.fulfill({status: 500})` are the only reliable way to produce a hang or a
   500 on demand. Deterministic, fast, runs in CI.
2. **Mocking a failure tests your mock.** A faked 500 exercises your error branch, not
   the system's. Real timeouts, real `Cache-Control` headers, real proxy behaviour only
   appear against a real backend — and that is where stale-cache bugs live. MDN's
   heuristic-caching section is the proof: a response with *no* `Cache-Control` still
   gets cached, for a duration "up to the implementation." No mock reproduces that.
3. **Rapid Software Testing (Bach & Bolton).** Writing four named checks is *checking*,
   not testing — "the mechanistic process of verifying propositions about the product."
   Async defects are emergent and timing-dependent: click submit twice, hit back
   mid-load, go offline between request and response. None is one of your four states,
   and no pre-written check finds them.

Land (3) — it is a real limitation of the artifact the learner is about to build.
Frame (1) vs (2) as a scoping decision, not a right answer.

## e. Worked examples worth adapting

- **bfcache stale data (web.dev)** — https://web.dev/articles/bfcache — the best real
  stale-state story I found, and a documented hazard rather than a hypothetical: a
  back navigation onto a restored checkout page "could potentially expose out-of-date
  information." Plus the security variant: sign out on a public computer, next user
  hits back. Two test cases straight off the page, neither in any normal test plan.
- **The `fetch` 404 trap.** MDN states outright that a `fetch()` promise "does not
  reject if the server responds with HTTP status codes that indicate errors." Best
  exercise in the task: hand the learner a component whose `.catch` never fires on a
  500, ask why the error state never renders. Semantics and a real bug class in one.
- **Heuristic caching (MDN).** The `Last-Modified` one-year example with the ~10%
  reuse heuristic is a ready-made "why is it still showing the old price when we never
  set a cache header" scenario.
- **TanStack Query cache lifecycle** —
  https://tanstack.com/query/latest/docs/framework/react/guides/caching — documents the
  behaviour that produces the bug testers see: on remount "the query immediately
  returns the available cached data while the `fetchTodos` function is being run in the
  background." Stale content, no loading indicator, by design. Good "is this a bug or
  the spec?" discussion.
- **Gap:** no citable public post-mortem where a caching or loading-state defect caused
  a named production incident. Write one as an explicit hypothetical, or pull from the
  learner's own workplace.

## Verbatim quotes

- **MDN HTTP caching §Fresh and stale based on age:** "Stored HTTP responses have two states: fresh and stale. The fresh state usually indicates that the response is still valid and can be reused, while the stale state means that the cached response has already expired." / "The criterion for determining when a response is fresh and when it is stale is age. In HTTP, age is the time elapsed since the response was generated."
- **§Validation:** "Stale responses are not immediately discarded. HTTP has a mechanism to transform a stale response into a fresh one by asking the origin server. This is called validation, or sometimes, revalidation." — (§If-Modified-Since) "The server will respond with 304 Not Modified if the content has not changed since the specified time... there is no response body — there's just a status code."
- **§Don't cache:** "The `no-cache` directive does not prevent the storing of responses but instead prevents the reuse of responses without revalidation. If you don't want a response stored in any cache, use `no-store`."
- **§Heuristic caching:** "HTTP is designed to cache as much as possible, so even if no `Cache-Control` is given, responses will get stored and reused if certain conditions are met." / "the specification recommends about 10% (in this case 0.1 year) of the time after storing."
- **§Reload and force reload** — the difference a tester must know: reload sends `Cache-Control: max-age=0` + `If-None-Match`, so "a request is validated"; force reload sends `Cache-Control: no-cache`, so "you can be sure you'll get a 200 OK from the origin server."
- **MDN `Window: fetch()`:** "A `fetch()` promise only rejects when the request fails, for example, because of a badly-formed request URL or a network error. A `fetch()` promise does not reject if the server responds with HTTP status codes that indicate errors (`404`, `504`, etc.). Instead, a `then()` handler must check the `Response.ok` and/or `Response.status` properties."
- **MDN `Cache-Control`:** `must-revalidate` — "can be reused while fresh. If the response becomes stale, it must be validated with the origin server before reuse." `stale-while-revalidate` — "the cache could reuse a stale response while it revalidates it to a cache."
- **RFC 9111 §4.2:** "A 'fresh' response is one whose age has not yet exceeded its freshness lifetime."
- **MDN "Critical rendering path":** "The Critical Rendering Path is the sequence of steps the browser goes through to convert the HTML, CSS, and JavaScript into pixels on the screen."
- **Playwright `route.abort([errorCode])`** — the failure modes you can actually simulate: `'timedout'`, `'internetdisconnected'`, `'connectionrefused'`, `'connectionreset'`, `'namenotresolved'`, `'blockedbyclient'`, `'accessdenied'`, `'addressunreachable'`, `'aborted'`, `'blockedbyresponse'`, `'connectionaborted'`, `'connectionclosed'`, `'connectionfailed'`, `'failed'` (default). `route.fulfill({status, body, json, headers})` — "Response status code, defaults to 200."
- **Chrome DevTools Network reference:** §"Emulate a first-time visitor by disabling the browser cache" — "check the Disable cache checkbox." §"Emulate offline" — "select Offline from the Network throttling drop-down menu."
- **Bach & Bolton, "Testing and Checking Refined"** (satisfice.com/blog/archives/856): "Checking is the mechanistic process of verifying propositions about the product." / "Testing is the process of evaluating a product by learning about it through experiencing, exploring, and experimenting..."
- **web.dev "bfcache", §Update stale or sensitive data after bfcache restore:** "bfcache is a snapshot of the entire page in memory, including the JavaScript heap, whereas the HTTP cache contains only the responses for previously made requests." / "if a user navigates to a checkout page and then updates their shopping cart, a back navigation could potentially expose out-of-date information if a stale page is restored from bfcache."
