# QA-051 — Performance and security review: one load check, two authorization checks, safely

> Dossier, not lesson content. Every claim below must be re-read at source
> before it ships in a lesson.

- **Verdict:** PARTIAL
- **Named source:** https://grafana.com/docs/k6/latest/get-started/running-k6/
- **Best primary source:** *two — no single document covers both halves.* **Performance:** k6 *Thresholds* (not the named page) — https://grafana.com/docs/k6/latest/using-k6/thresholds/ · **Authorization:** OWASP WSTG §4.5 — https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/05-Authorization_Testing/
- **Exact sections to read:** k6 *Running k6* (all 7 headings) → *Thresholds* (intro + option block) → *Metrics reference* (the built-ins) → *Load testing websites* § "Scripting considerations" (the permission rule). Then **WSTG-ATHZ-02** *Bypassing Authorization Schema* and **WSTG-ATHZ-04** *Insecure Direct Object References* — Summary, Test Objectives, How to Test.
- **Read time:** ~50 min (k6 ~25, WSTG ~20, safety para ~5)

## a. Does the named source cover this?

**It covers one of the three things the deliverable asks for and is silent on the
other two.** Fetched this session, the page has seven headings: *Before you
begin*, *Run local tests*, *Add VUs*, *The init context and the default
function*, *Set options*, *Ramp VUs up and down in stages*, *Execution modes*. It
genuinely teaches the small performance check — a runnable script,
`k6 run --vus 10 --duration 30s script.js`, and a `stages` array for ramping.
That half is fine.

What is missing is not a detail, it is two thirds of the deliverable:

- **The two authorization checks — nothing.** Not one sentence. This is a load
  testing page. A learner following this line cannot produce two of the three
  required artifacts.
- **"Safely" — nothing on this page.** I searched it specifically for permission,
  authorization-to-test, production, or ethics of pointing load at a host. None.
  k6 *does* say it, on a page the plan never links (§c).
- **No thresholds, so no evidence.** The page ends at "the test ran." It never
  reaches pass/fail criteria, so the learner produces console output rather than
  a reviewable result. For a capstone whose noun is *review*, that is the part
  that matters most.

Fix is cheap: keep this page as step one, add *Thresholds*, add WSTG §4.5.
Extend the line, don't delete it.

## b. Best primary source

**Performance: k6's *Thresholds* page.** Thresholds are what turn a run into
evidence — *"Thresholds are the pass/fail criteria that you define for your test
metrics"* — giving a binary outcome plus a non-zero exit code, which is what
makes the result reviewable and CI-able. Pair with *Metrics reference* so the
learner can say what `http_req_duration` measures instead of quoting a number
they don't understand.

**Authorization: OWASP WSTG §4.5.** Right primary because it is structured as
*tests*, not concepts, and two entries map one-to-one onto "two authorization
checks": **ATHZ-02** (horizontal + vertical bypass, with a two-session protocol)
and **ATHZ-04** (IDOR, with four ready-made parameter shapes to tamper with).

**Do not route this through ISTQB.** I read CTFL v4.0 §2.2.2 (p.28) in the PDF
this session: performance and security appear *only* as two bullets in the
ISO/IEC 25010 list — "Performance efficiency", "Security" — with no method, no
example, no tooling. Wrong altitude for a doing-task. Use it for one sentence of
vocabulary (these are *non-functional* test types) and move on.

## c. What it leaves out

- **The safety rule is on a different k6 page than the plan links.** *Load
  testing websites* § Scripting considerations: *"Don't load test servers that
  you don't own."* That sentence is the entire "safely" half of the deliverable.
  Promote it.
- **Where "a safe test environment" comes from.** k6 says pre-production is safer
  and production is *"more risky"*, but assumes you have one; WSTG assumes a
  scoped engagement and two accounts. Neither tells a self-taught learner what to
  point at. The lesson must supply the target (§e).
- **How to get a second user account.** ATHZ-02's method depends on holding two
  sessions at once; it never says how to provision the second user or keep two
  cookie jars apart in one browser (two profiles, or one normal + one private
  window — the practical answer, absent from the doc).
- **What "small" means.** Nothing bounds it, so learners run 5 seconds
  (meaningless) or hammer something for an hour. State it: ~1 min, ≤10 VUs, one
  endpoint, one threshold.
- **A baseline.** `p(95)<200` is arbitrary unless the learner first measures at 1 VU.
- **What to do with a finding.** WSTG stops at "the application is vulnerable."
  No severity, no disclosure, no write-up format.

## d. Credible disagreement

**The named page teaches the load model that performance specialists say
under-reports latency, and never flags it.** `vus` + `duration` — the page's
whole configuration story — is a *closed* model. Grafana's own docs say what that
costs, on a page the plan never links: *"when the target system is stressed and
starts to respond more slowly, a closed model load test will wait, resulting in
increased iteration durations and a tapering off of the arrival rate of new VU
iterations… In some testing literature, this problem is known as coordinated
omission."* The system under test throttles its own test: the slower it gets, the
less load you apply, and the p95 you report is flattering. The counter-position
is the *open* model (`constant-arrival-rate`), where *"the response times of the
target system no longer influence the load on the target system."*

**Honesty note:** coordinated omission is Gil Tene's term and his QCon deck is
its canonical statement, but I could **not** open it this session — the InfoQ PDF
returned 403 and the presentation page carries no transcript. Everything above is
quoted from Grafana's docs. **Do not attribute wording to Tene without opening
his deck first.**

For a *small* check, closed-model `vus`/`duration` is defensible. The teachable
point is that the learner should know they chose it. One line in the write-up —
"closed model, so this p95 is optimistic under stress" — is what separates a
review from a screenshot.

## e. Worked examples worth adapting

- **OWASP Juice Shop is the safe target and it ships the exercise.** Its Broken
  Access Control chapter defines the same two axes WSTG does, and two challenges
  *are* the two authorization checks, pre-built and legal to attack:
  - **View Basket** (⭐⭐) — *"View another user's shopping basket."* Hint: *"a
    client-side association of user to basket that you can try to manipulate."*
    → ATHZ-04, horizontal, real object reference.
  - **Admin Section** (⭐⭐) — *"Access the administration section of the store."*
    → ATHZ-02, vertical, via forced browsing.
  Two checks, two axes, one target. That is the deliverable.
- **Point the load check at a host that invites it.** The named page itself uses
  `https://quickpizza.grafana.com/` and `http://test.k6.io` — Grafana's own demo
  hosts, so "don't test servers you don't own" is satisfied by construction. Or
  run k6 against the learner's local Juice Shop container and get both halves
  from one app.
- **The two-session drill (ATHZ-02):** two users of identical privilege, two live
  sessions, swap `SessionID` while leaving `username=example_user` untouched —
  *"If the attacker's response contain the data of the example_user, then the
  application is vulnerable."*
- **Four IDOR shapes to hunt (ATHZ-04):** `?invoice=12345`, `?user=someuser`,
  `?img=img00011`, `?menuitem=12`. Good as a "find one of these" scavenger hunt
  before any tampering.
- **The evidence artifact:** one threshold block plus the pass/fail line —
  `thresholds: { http_req_failed: ['rate<0.01'], http_req_duration: ['p(95)<200'] }`
- **No real breach story fetched this session.** A01:2021 gives scale, not a
  narrative. Do not invent one.

## Verbatim quotes

**k6 *Running k6* (named source):** "Code in the init context defines functions
and configures the test options (like `duration`)." · "Every test also has a
`default` function, which defines the VU logic." · "VUs are essentially parallel
`while(true)` loops." · **Contains no sentence on permission, safety, production,
or authorization.**

**k6 *Thresholds*:** "Thresholds are the pass/fail criteria that you define for
your test metrics." · on failure "the test finishes with a failed status" and k6
exits non-zero; on pass "k6 considers this test a `pass` and exits with an exit
code `0`." · `rate<0.01` = "less than 1% of requests return an error";
`p(95)<200` = "95% of requests have a response time below 200ms".

**k6 *Metrics reference*:** `http_req_duration` — "Total time for the request.
It's equal to `http_req_sending + http_req_waiting + http_req_receiving`" ·
`http_req_waiting` — "Time spent waiting for response from remote host (a.k.a.
'time to first byte', or 'TTFB')" · `checks` — "The rate of successful checks".

**k6 *Load testing websites* § Scripting considerations:** "Don't load test
servers that you don't own. Many applications make calls to third-party providers
for authentication, social sharing, and marketing analytics. Disable these
requests unless you have permission to include them in your tests." · "Testing in
production yields the most accurate results, but it's also more risky."

**k6 *Open and closed models*:** "In a closed model, VU iterations start only when
the last iteration finishes." · "In some testing literature, this problem is known
as *coordinated omission.*"

**WSTG-ATHZ-02:** "This test case focuses on identifying authorization weaknesses
where an authenticated user is able to access resources or perform actions beyond
their assigned permissions, including horizontal and vertical privilege
escalation." · Objective: "Assess if unauthenticated, horizontal, or vertical
access is possible." · "An application will be considered vulnerable if the
responses are the same, contain same private data or indicate successful
operation on other users' resource or data." · Also notes `X-Original-URL` /
`X-Rewrite-URL` header bypasses of infrastructure-layer access control.

**WSTG-ATHZ-04:** "Insecure Direct Object References (IDOR) occur when an
application provides direct access to objects based on user-supplied input." ·
Objectives: "Identify points where object references may occur"; "Assess the
access control measures and if they're vulnerable to IDOR."

**ISTQB CTFL v4.0 §2.2.2 (p.28), read in the PDF this session:** "Non-functional
testing evaluates attributes other than functional characteristics of a component
or system. Non-functional testing is the testing of 'how well the system
behaves'." · ISO/IEC 25010 list: "Performance efficiency · Compatibility ·
Usability · Reliability · Security · Maintainability · Portability". **That is
the syllabus's entire treatment of both topics — two bullets, no method.**

**OWASP Top 10 A01:2021:** "Access control enforces policy such that users cannot
act outside of their intended permissions." · "94% of applications were tested for
some form of broken access control with the average incidence rate of 3.81%, and
has the most occurrences in the contributed dataset with over 318k."

**Juice Shop companion guide:** "Vertical privilege escalation… where a lower
privilege user or application accesses functions or content reserved for higher
privilege users" · "Horizontal privilege escalation, where a normal user accesses
functions or content reserved for other normal users."
