# QA-025 — Locators, actions, and assertions

> Dossier, not lesson content. Every claim below must be re-read at source
> before it ships in a lesson.

- **Verdict:** WRONG-DOCUMENT
- **Named source:** https://playwright.dev/docs/intro
- **Best primary source:** Playwright docs, "Locators" — https://playwright.dev/docs/locators — as the spine, with three siblings from the same doc set (below)
- **Exact sections to read:** Locators §§ *Quick Guide* → *Strictness* (skip *Rare use cases*) · Best Practices §§ *Testing philosophy* + *Best Practices* (stop at *Configure debugging*) · Assertions §§ *Auto-retrying assertions* → *Soft assertions* · Auto-waiting (whole page, it is short) · Authentication §§ *Core concepts* + *Basic: shared account in all tests*
- **Read time:** ~50 min

## a. Does the named source cover this?

No. `/docs/intro` is titled **Installation**. I fetched it: its headings are *Installing
Playwright · What's Installed · Running the Example Test · HTML Test Reports · Running the
Example Test in UI Mode · Updating Playwright · System requirements · What's next*. It
teaches npm invocation and project scaffolding. "Locator" and "assertion" appear once, in
the *What's next* links — "Write tests using web-first assertions, fixtures and locators" —
pointing away, at `/docs/writing-tests`.

A learner who reads only this page can install Playwright and run somebody else's example.
They cannot write the DELIVERABLE: they have not been shown a single locator. Right doc set,
wrong page — the fix is one click, not a new source. Keep it as the 10-minute setup step.

## b. Best primary source

**Spine: Playwright docs, "Locators."** Free, versioned, written by the tool's authors, and
the only page that treats the locator as an abstraction rather than a syntax list:
*"Locators are the central piece of Playwright's auto-waiting and retry-ability."* Its
structure maps onto the DELIVERABLE almost exactly — seven recommended locators, then
*Filtering Locators*, then *Lists*, then *Strictness*. The filtered-list scenario lives in
*Lists* (§ *Count items in a list*, § *Assert all text in a list*).

Three siblings, each covering one leg the spine misses:
1. **Best Practices** — https://playwright.dev/docs/best-practices. Supplies the *why*: test
   user-visible behavior, prefer user-facing attributes, use web-first assertions. Turns
   syntax into judgment. Read it *before* Locators, not after.
2. **Assertions** — https://playwright.dev/docs/test-assertions. The auto-retrying vs
   non-retrying split is the highest-value distinction on the task, and is on no other page.
3. **Auto-waiting** — https://playwright.dev/docs/actionability. Five named checks (visible /
   stable / receives events / enabled / editable). Short, and it is what makes "no
   `waitForTimeout`" a rule rather than a preference.

For the login half add **Authentication** — https://playwright.dev/docs/auth — but read (d)
first: it argues against what the DELIVERABLE asks for.

## c. What it leaves out

The Playwright docs are a *tool manual*. Against a QA deliverable they omit:
- **What to assert.** Every example asserts something obviously true. Auto-retry makes
  `toBeVisible()` on an already-visible element pass vacuously, so a learner can write a
  green suite that proves nothing. No page distinguishes an assertion that would catch a
  regression from one that is a tautology. Biggest gap; the lesson must supply it.
- **Test data.** The *Lists* examples assert `toHaveCount(3)` against a page the doc authors
  control. On a real filtered list the assertion is only as good as the seeded data — and
  nothing says so, or says how to seed it.
- **What to do when the app has bad markup.** `getByRole` needs an accessibility tree. The docs
  note role locators *"do not replace accessibility audits"* but never warn the reverse: on a
  div-soup app user-facing locators are simply unavailable, and the learner will conclude the
  advice is wrong rather than that the app is.
- **Diagnosing the strict-mode violation.** Strictness is stated as a rule; the recovery
  workflow (read the error's element list → filter or chain → re-run) is nowhere. First error
  every beginner hits.
- **Assertion vs action waiting.** `expect(...).toBeVisible()` and `.click()` both wait, for
  different reasons, on different timeouts (assertions 5 s; actions use the action timeout).
  Never shown side by side; learners conflate them.
- **When automation is the wrong answer** — nothing. See (d).

## d. Credible disagreement

**1. Playwright contradicts itself on test ids.** *Best Practices*: *"we recommend
prioritizing user-facing attributes and explicit contracts."* *Locators* § *Locate by test id*:
*"Testing by test ids is the most resilient way of testing as even if your text or role of the
attribute changes, the test will still pass."* Opposite advice, one click apart. **Testing
Library** breaks the tie the other way — its Priority list puts `ByTestId` dead last, because
*"The user cannot see (or hear) these"* (https://testing-library.com/docs/queries/about/). And
Playwright's own flagship example suite uses `getByTestId('todo-item')` throughout, practising
what its best-practices page argues against. Do not smooth this over; it is the most teachable
moment on the task. The real rule: a user-facing locator asserts the *user's* contract, a test
id asserts the *team's* — know which one you are testing.

**2. Playwright argues against the DELIVERABLE's own login test.** *Authentication* recommends
storing auth state once and reusing it: *"This eliminates the need to authenticate in every
test and speeds up test execution."* The DELIVERABLE says "automate login." Both are right, for
different tests — write *one* UI login test because login is a feature, then never log in
through the UI again. Say this explicitly or the learner builds a suite that logs in 40 times.

**3. RST: there is no such thing as an automated test.** Bach & Bolton, *Testing and Checking
Refined* (satisfice.com, fetched this session): testing is *"the process of evaluating a product
by learning about it through experiencing, exploring, and experimenting"*; checking is *"the
mechanistic process of verifying propositions about the product."* Bluntly: *"There is no such
thing as automated testing. Testing cannot be automated."* Machine checking *"verif[ies]
propositions without the mediation of humans"*; *"Testing can only be supported by tools."*
Applied here: the DELIVERABLE produces two *checks*. The sapient work was choosing which
propositions were worth encoding — skip that framing and the lesson teaches Playwright, not QA.

## e. Worked examples worth adapting

- **`demo-todo-app.spec.ts` — the closest thing to the DELIVERABLE that exists.** Ships with
  `npm init playwright@latest` in `tests-examples/`. Its `Routing` describe block *is* the
  filtered-list scenario: click "Active", assert count, assert surviving items by text.
  Verbatim from the copy I read:
  `await page.getByRole('link', { name: 'Active' }).click(); await expect(todoItem).toHaveCount(2); await expect(todoItem).toHaveText([TODO_ITEMS[0], TODO_ITEMS[2]]);`
  What that teaches for free: a count assertion alone would pass on the *wrong* two items —
  the `toHaveText([...])` array form is what actually verifies the filter.
  **Provenance caveat:** I read a third-party mirror
  (`raptatinha/tau-introduction-to-playwright`, which has added `@smoke -` prefixes); I could
  not confirm the canonical path inside `microsoft/playwright` this session. Scaffold locally
  and read the authentic file before quoting it. Live app: https://demo.playwright.dev/todomvc/
- **The strict-mode violation, as a deliberate drill.** Write `page.getByRole('link')` on a page
  with many links; read the error. Fix it twice — once with `.filter()`, once by chaining inside
  a container. Strictness, filtering, and error-reading in one ten-minute loop; the docs state
  the rule but supply no such drill.
- **The vacuous-assertion drill.** Write an assertion that passes *before* the feature is
  implemented, then find it. Directly attacks the gap in (c).
- **`codegen`** (Best Practices § *Use `codegen` to generate locators*) — good as a
  locator-*suggestion* tool, dangerous as a test generator; generated waits and selectors need
  pruning. Frame it that way or learners ship the recording.
- **Gap.** No citable named-company defect story about a brittle-locator suite; the field is
  vendor blog posts. Use an explicit hypothetical, or the test-id contradiction in (d).

## Verbatim quotes

**Playwright, "Locators":**
- "Locators are the central piece of Playwright's auto-waiting and retry-ability. In a nutshell, locators represent a way to find element(s) on the page at any moment."
- "CSS and XPath are not recommended as the DOM can often change leading to non resilient tests. Instead, try to come up with a locator that is close to how the user perceives the page."
- "Locators are strict. This means that all operations on locators that imply some target DOM element will throw an exception if more than one element matches."
- § *Locate by test id*: "Testing by test ids is the most resilient way of testing as even if your text or role of the attribute changes, the test will still pass."
- § *Locate by role*: "Note that role locators **do not replace** accessibility audits and conformance tests, but rather give early feedback about the ARIA guidelines."

**Playwright, "Best Practices":**
- "Automated tests should verify that the application code works for the end users, and avoid relying on implementation details"
- "To make tests resilient, we recommend prioritizing user-facing attributes and explicit contracts."
- "By using web first assertions Playwright will wait until the expected condition is met."

**Playwright, "Assertions":**
- "The following assertions will retry until the assertion passes, or the assertion timeout is reached." (auto-retrying)
- "These assertions allow to test any conditions, but do not auto-retry." (non-retrying)
- "By default, the timeout for assertions is set to 5 seconds."
- Soft assertions: "failed soft assertions **do not** terminate test execution, but mark the test as failed."

**Playwright, "Auto-waiting" / "Actions" / `toHaveText` / "Authentication":**
- "Playwright performs a range of actionability checks on the elements before making actions to ensure these actions behave as expected."
- "Element is considered stable when it has maintained the same bounding box for at least two consecutive animation frames."
- `/docs/input`: "Most of the time, you should input text with locator.fill(). … You only need to type characters if there is special keyboard handling on the page."
- `toHaveText` array form: "Locator resolves to a list of elements. The number of elements equals the number of expected values in the array. Elements from the list have text matching expected array values, one by one, in order."
- Auth: "Tests can load existing authenticated state. This eliminates the need to authenticate in every test and speeds up test execution."

**Testing Library, "About Queries" § Priority:**
- `ByTestId` (ranked last): "The user cannot see (or hear) these, so this is only recommended for cases where you can't match by role or text or it doesn't make sense."

**Bach & Bolton, "Testing and Checking Refined" (satisfice.com):**
- "There is no such thing as automated testing. Testing cannot be automated."
- Testing: "the process of evaluating a product by learning about it through experiencing, exploring, and experimenting…"; Checking: "the mechanistic process of verifying propositions about the product."
- "Testing can only be *supported* by tools."
