## a. Does the named source cover this?

No. The plan names the root index of MDN's entire Learn curriculum — a table of
contents linking to ~15 modules, with no instructional text on any topic. I fetched it:
the body is an intro paragraph, four "which path should I take" signposts, a module
list, and a partner-links footer. "Single-page app," "service worker," and "client-side
routing" appear only inside module titles and sidebar nav, never in prose. It cannot get
a learner to the DELIVERABLE because it makes no claim they could put on a checklist.

Link two of its children instead: *JavaScript frameworks and libraries* (React-based;
its accessibility page is the best SPA focus-management walkthrough I found — see §e)
and the *Testing* extension module. Neither covers PWAs or static delivery.

## b. Best primary source

**Spine: MDN, "Best practices for PWAs."** Free, stable, vendor-neutral, already
checklist-shaped — its headings *are* risk categories: adapt to all browsers / adapt to
all devices / provide an offline experience / support deep links / make it fast / make
it accessible. Near one-to-one with the DELIVERABLE. Use its headings as the checklist's
skeleton, not its prose as the content.

Three supplements, each covering one leg the spine misses:

1. **Jake Archibald, "The Service Worker Lifecycle"** (web.dev, updated 2016-09-29) —
   https://web.dev/articles/service-worker-lifecycle. Canonical on the highest-severity
   risk here: install → **waiting** → activate, and why a user sits on a stale build
   indefinitely. Nothing else explains the waiting state properly.
2. **MDN, "Caching" (PWA guides)** —
   https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Caching.
   Cache-first vs network-first, plus the freshness and eviction failure modes.
3. **React Router, "Single Page App (SPA)"** — https://reactrouter.com/how-to/spa. §4 is
   the deep-link 404, from the framework's own docs — the most testable SPA-vs-static
   defect, and the spine does not mention it.

For the *static* leg, Osmani & Miller, "Rendering on the Web"
(https://web.dev/articles/rendering-on-the-web, 2019-02-06, upd. 2026-01-05) compares
static / CSR / SSR / hydration — read for vocabulary, not for the checklist.

## c. What it leaves out

The spine is a *build* guide written for developers. Against a QA deliverable it is
missing most of what matters:

- **No SPA routing failure modes.** It endorses deep links as a feature but never says
  what breaks: hard-refresh on a client route returning 404, back/forward, scroll
  restoration, in-memory state lost on reload. That cluster is the most common
  small-React-SPA bug family and it is absent.
- **No warning that caching can strand users.** It tells you to work offline; it never
  mentions that a bad service worker traps every user on a broken build. That risk lives
  only in Archibald and the MDN Caching page.
- **No testing method whatsoever.** No oracle, no repro steps, no tooling (DevTools →
  Application → Service Workers → *Offline* / *Update on reload*), no environment matrix.
  Every source here says what to *build*, never how to *check* it.
- **No prioritisation.** Twelve headings, equally weighted; the DELIVERABLE says "focused"
  and "small." The lesson must supply the cut rule — suggestion: keep only risks that fail
  *invisibly* (stale cache, lost focus, 404-on-refresh).
- **Nothing on static delivery.** CDN cache headers, build-time data going stale, how a
  static host handles unknown paths — none of it. Nor does "Rendering on the Web," which
  treats static rendering purely as a performance win.

## d. Credible disagreement

**1. The premise itself is contested.** Alex Russell, "The Market for Lemons"
(2023-02-04, https://infrequently.org/2023/02/the-market-for-lemons/) argues the
SPA-by-default choice *is* the defect, not a neutral backdrop: JS-framework architecture
produced "new services being built to a self-defeatingly low UX and performance
standard," and after a decade "the framework-centric pitch is still phrased in
speculative terms because there's no there there." QA reading: the first checklist
question is *does this need to be an SPA at all* — the whole risk list follows from that
one decision. (Quotes and date verified; his stated credentials came back thin from my
fetch — confirm in a browser before leaning on his authority.)

**2. A concrete, testable disagreement about `skipWaiting()`.** web.dev's Learn PWA
*Update* module warns against it — the default wait "prevents the new service worker
from taking over old clients that might not be compatible," and using it "means that
your new service worker is probably controlling pages that were loaded with an older
version." Archibald presents it neutrally as a tool, and the common practitioner pattern
(Workbox's update prompt) reaches for it routinely. This changes the checklist: *"new
version activates immediately"* and *"old tabs keep working until closed"* are opposite
acceptance criteria. Pick one deliberately.

**3. Rapid Software Testing angle — flagged, not sourced.** The RST objection (a
pass/fail checklist is *checking*, not testing) bites hard here: these risks fail
silently — a stale cache and a lost focus ring both render a page that looks fine. I did
**not** fetch an RST document this session; verified Bach & Bolton quotes are in
`sources/QA-016.md` §d. Re-fetch before quoting.

## e. Worked examples worth adapting

- **Best defect story available: Archibald's self-inflicted deadlock.** A cache-first
  service worker serves a stale `index.html`, which points at the old worker, so the new
  worker can never be fetched — the app is frozen and refreshing never helps. Ready-made
  as a "what went wrong" exercise. *My fetch returned this quote and the 24-hour
  update-check rule fragmented — re-read* Updating the service worker *and* Avoid
  changing the URL *at source first.*
- **MDN React accessibility tutorial** — a full worked defect with repro and fix:
  swapping templates destroys the focused element, "so there's no visual cue as to where
  the browser's focus is." Adapts directly to route changes, the same bug at larger scale.
- **The 404-on-refresh exercise.** Build a small React Router SPA, deploy to any static
  host, hard-refresh a deep link. React Router's docs supply the diagnosis verbatim (§4).
  Cheap to run; teaches why "works in dev" is not an oracle.
- **The offline-send scenario** in MDN Best practices (long email composed, "Send"
  pressed with no connectivity) prompts an *offline* test case that isn't "show a banner."
- **Gap — no public postmortem found.** No citable named-company incident report for a
  service-worker cache failure. A search surfaced Angular issue #43163, "There should be
  a seamless way to get rid of broken service worker state," which looks like a real
  discussion of this defect class — **I did not fetch it**. Otherwise the field is blog
  posts. Write the story as an explicit hypothetical, not a dressed-up blog post.

## Verbatim quotes

**MDN, "Best practices for PWAs":**
- "At the very least, your PWA should provide a custom offline page that informs the user that they are offline instead of showing the generic browser error page."
- "To ensure compatibility, it's essential to test your app across various browsers and operating systems."
- "Using feature detection allows you to deliver a usable experience to the broadest audience."
- "Making different sections of your app available via unique URLs allows users to bookmark, navigate directly to, and share specific content within your app."

**MDN, "Caching" (PWA guides), § Caching strategies / § Deleting cached data:**
- "The drawback of 'cache first' is that once a response is in the cache, it is never refreshed until a new version of the service worker is installed."
- "The main drawback, of course, is freshness: caching is less appropriate for resources which need to be up to date. Also, for some types of requests, such as POST requests, caching is never appropriate."
- "Caches have a limited amount of storage space, and the browser may evict an app's cached data if the limit is exceeded... The user can also clear an app's cache at any time."

**MDN, "Using Service Workers," § Basic architecture:**
- "Once all pages controlled by the old version of the service worker have closed, it's safe to retire the old version."
- "documents will have to be reloaded to actually be controlled, because a document starts life with or without a service worker and maintains that for its lifetime."

**Archibald, "The Service Worker Lifecycle" (web.dev), § Waiting / § Skip the waiting phase** — RE-VERIFY, fetch returned these partly fragmented:
- "After it's successfully installed, the updated service worker delays activating until the existing service worker is no longer controlling clients. This state is called 'waiting.'"
- "skipWaiting() prevents the waiting, meaning the service worker activates as soon as it's finished installing."
- "the user never gets sw-v2.js, because sw-v1.js is serving the old version of index.html from its cache."

**web.dev, Learn PWA § Update:**
- "The new service worker will be installed but waiting for activation by default. The wait prevents the new service worker from taking over old clients that might not be compatible."
- "Installing a new service worker version doesn't automatically remove previously cached assets. You should explicitly delete assets you no longer need."

**React Router, "Single Page App (SPA)," §4 Direct all URLs to index.html:**
- "Common to deploying any SPA, you'll need to configure your host to direct all URLs to the index.html of the client build. Some hosts do this by default, but others don't."
- "If you're getting 404s at valid routes for your app, it's likely you need to configure your host."

**Osmani & Miller, "Rendering on the Web" (web.dev):**
- CSR: "the amount of JavaScript required tends to grow as an application grows, which can impact a page's INP."
- Hydration: "can have a significant negative impact on TBT and INP" — pages "look ready but none of its interactive features work."

**MDN, React accessibility tutorial:**
- "the element that we were focused on no longer exists, so there's no visual cue as to where the browser's focus is. This could confuse a wide variety of users — particularly users who rely on the keyboard, or users who use assistive technology."
