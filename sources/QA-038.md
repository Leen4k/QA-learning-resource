# QA-038 — Stress, spike, and soak testing

> Dossier, not lesson content. Every claim below must be re-read at source
> before it ships in a lesson.

- **Verdict:** WRONG-DOCUMENT
- **Named source:** https://grafana.com/docs/k6/latest/get-started/running-k6/
- **Best primary source:** ISTQB *CTFL Specialist Syllabus — Performance Testing* v2018 — https://astqb.org/assets/documents/ISTQB-CTFL-PT-Syllabus-2018.pdf
- **Exact sections to read:** ISTQB CT-PT §1.2 (pp.12–13), §1.5 (pp.15–16), §4.1.1–4.1.2 (pp.32–37), §4.2.4 (pp.42–43), §4.3 (pp.50–51). Then k6 *Test types* (all six pages) + *Thresholds*.
- **Read time:** ~70 min (ISTQB ~50, k6 ~20)

## a. Does the named source cover this?

No. `get-started/running-k6/` is a hello-world page: write a script, add VUs, add
duration, ramp with `stages`, run locally or in the cloud. It never uses the words
stress, spike, or soak. No test-type taxonomy, no thresholds, no pass/fail
criteria, no abort conditions. Its most substantive line is *"VUs are essentially
parallel `while(true)` loops."*

Both halves fail. The **want** is "when to use load, stress, spike, and soak" — this
page doesn't know those categories exist. The **deliverable** is a plan with limits,
stop conditions, and success criteria — this page teaches the `options` object and
stops. QA-035's pattern again: **right site, wrong page.** Grafana publishes the
missing content two clicks away at `/docs/k6/latest/testing-guides/test-types/` (one
page per type) and `/docs/k6/latest/using-k6/thresholds/`. Repoint; don't drop k6.

## b. Best primary source

**Two sources; neither alone produces the deliverable.**

**ISTQB CT-PT (2018) gives the plan.** §4.1.2 "The Performance Test Plan" is
section-by-section a template for this deliverable: Objective, Test Objectives,
System Overview, **Types of Performance Testing to be Conducted**, **Acceptance
Criteria**, Test Data, System Configuration, Test Environment, Test Tools, Profiles,
Relevant Metrics, Risks. §1.2 defines the types; §4.2.4 defines load profiles
(ramp-up / ramp-down / steps / distributions). Free, 59pp, no account. Access note:
istqb.org 403s automated fetches, but the ASTQB link above is the **full 59-page
syllabus PDF, not an ASTQB summary page** — fetched and read this session.

**k6 gives the numbers.** ISTQB defines types but never says how big or how long;
k6's comparison table does. k6 Thresholds is also the only source here that makes
**stop conditions** executable (`abortOnFail` / `delayAbortEval`).

Stress and spike share names across both sources; the rest do not:

| Deliverable term | ISTQB CT-PT | k6 |
|---|---|---|
| load | Load Testing §1.2 | Average-load test |
| soak | **Endurance** Testing §1.2 | Soak test |
| limits | Capacity / Scalability §1.2 | Breakpoint test |
| success criteria | Acceptance Criteria §4.1.2 | Thresholds |
| stop conditions | *(absent — see c)* | `abortOnFail` |

## c. What it leaves out

- **ISTQB has no stop-conditions section.** §4.1.2 has Acceptance Criteria but no
  abort criteria; the only mention is buried in §4.3 prose (quoted below) and is a
  judgement call, not a plan artifact. The deliverable demands stop conditions be
  written in advance, so the lesson must supply that section, borrowing k6's
  `abortOnFail` as the mechanism.
- **No magnitudes, durations, or a stated baseline.** Nothing says a soak is 8h not
  40min, or a stress run is 2–3x average — nor where the "average" you multiply comes
  from. §4.2.3 (operational profiles) is the pointer but is out of scope for 4h; in
  practice the number comes from production telemetry.
- **Ordering constraints live only in k6, and matter.** Stress only after
  average-load; soak only after smoke and average-load. A plan that schedules a soak
  first is wrong.
- **k6 teaches no plan document at all** — it is tool docs. Hence the pairing. And
  **CT-PT is 2018**, pre-dating the SRE/observability framing now standard.

## d. Credible disagreement

**On the taxonomy — from one of the syllabus's own co-authors.** Podelko is
credited on the CT-PT working group, yet in *Load Testing: See a Bigger Picture*
he rejects the crisp split the syllabus teaches: terminology is *"rather vague"*,
definitions *"different (and sometimes conflicting)"*, the types *"not mutually
exclusive"*. Teach the four names as **lenses on one workload experiment**, not
four disjoint projects. "Which one is this?" has no single answer.

**On stop conditions — Google SRE disagrees head-on.** *"Load test components until
they break."* ISTQB's acceptance criteria and k6's `abortOnFail` both halt the run
when criteria break; SRE says the data you need starts *there* — whether the system
degrades gracefully or falls over, and whether it recovers once load is removed.
Name the tension: a stop condition protects your environment and budget, and it also
discards the failure mode you most need to see. Resolve it by writing **two** — an
abort for safety, plus a deliberate ride-past-break for a breakpoint run in an
environment you are willing to destroy.

## e. Worked examples worth adapting

- **ISTQB §4.2.4 Diagram 1, "Example of constructing a 'stress' load profile"**
  (p.43). Three stacked charts: a flat 100-VU background load from Operational
  Profile 1; a ramp to 220 VUs held two hours from Profile 2; the two summed into a
  three-hour stress period crossing a drawn "Maximum Normal Load" line. Best
  exercise here — stress as *background + peak*, not "turn the dial up", and that
  drawn line is the "clear limit" the deliverable wants. Have learners redraw it.
- **ISTQB §1.5, six named failure modes with causes** (pp.15–16) — each maps to a
  test type, so it doubles as the when-to-use-which exercise: seven-second web
  response (load); crash under a ticket-sales rush (spike); degradation over time
  from memory leaks / disk fragmentation / database growth (soak); graceless error
  handling at over-limit load (stress); batch overrunning its window; a real-time
  component missing its update rate.
- **SRE Workbook *Managing Load* — a launch that load-tested 5x and got 50x.** Cold
  open for why a stress multiplier is a guess. **The chapter names the product; I
  read it via a summarising fetch and did not see the name verbatim — confirm.**
- **k6 spike profile:** `{duration:'2m',target:2000}` then `{duration:'1m',target:0}`
  — no plateau, deliberately. k6 warns *"Errors are common under these scenarios"*:
  a spike test with errors is not automatically a failed test.

## Verbatim quotes

ISTQB CT-PT §1.2 (p.12):
> "Stress testing focuses on the ability of a system or component to handle peak
> loads that are at or beyond the limits of its anticipated or specified workloads."
> "Spike testing focuses on the ability of a system to respond correctly to sudden
> bursts of peak loads and return afterwards to a steady state."
> "Endurance testing focuses on the stability of the system over a time frame
> specific to the system's operational context... no resource capacity problems
> (e.g., memory leaks, database connections, thread pools)."

ISTQB CT-PT §4.1.2 (p.34):
> "Acceptance criteria should be set for all relevant measures and related back to
> the following as applicable: Overall performance test objectives; Service Level
> Agreements (SLAs); Baseline values..."

ISTQB CT-PT §4.3 (p.51) — the closest thing to a stop condition:
> "it may be necessary to stop the test or make some on-the-fly adjustments to the
> performance test or the system configuration if the test deviates from the
> expected behavior."

k6 *Test types* (…/testing-guides/test-types/): "no single test type eliminates all
risk." Table — Stress: "High (above average)" / "Mid (5-60 minutes)"; Soak:
"Average" / "Long (hours)"; Spike: "Very high" / "Short (a few minutes)";
Breakpoint: "Increases until break" / "As long as necessary".
k6 *Soak*: "Some typical values are 3, 4, 8, 12, 24, and 48 to 72 hours." / "Don't
run soak tests before running smoke and average-load tests."
k6 *Stress*: "Only run stress tests after running average-load tests."
k6 *Breakpoint*: "Breakpoint testing aims to find system limits. They increase load
until the system fails." / "To stop the test using a threshold, you must define
`abortOnFail` as true."
k6 *Thresholds* (…/using-k6/thresholds/): "Thresholds are the pass/fail criteria
that you define for your test metrics."

Podelko, *Load Testing: See a Bigger Picture* (CMG, p.1) — alexanderpodelko.com/docs/Load_Testing_CMG12.pdf:
> "terminology is rather vague here... Many different terms are used for such kind of
> multi-user testing, such as performance, concurrency, stress, scalability,
> endurance, longevity, soak, stability, reliability, etc. There are different (and
> sometimes conflicting) definitions of these terms... Mostly these terms describe
> testing from somewhat different points of view, so they are not mutually exclusive."

Google SRE book, *Addressing Cascading Failures* — sre.google/sre-book/addressing-cascading-failures/:
> "Load test components until they break. As load increases, a component typically
> handles requests successfully until it reaches a point at which it can't handle
> more requests."

SRE Workbook *Managing Load* — sre.google/workbook/managing-load/:
> "Prior to launch, they load-tested their software stack to process up to 5x their
> most optimistic traffic estimates." / "The actual launch requests per second (RPS)
> rate was nearly 50x that estimate."
