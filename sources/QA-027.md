# QA-027 — Cross-browser and headless testing

> Dossier, not lesson content. Every claim below must be re-read at source
> before it ships in a lesson.

- **Verdict:** PARTIAL
- **Named source:** https://playwright.dev/docs/intro
- **Best primary source:** Playwright, "Browsers" — https://playwright.dev/docs/browsers (spine), plus Chrome for Developers, "Chrome Headless mode" — https://developer.chrome.com/docs/chromium/headless for the headless half
- **Exact sections to read:** Playwright *Browsers* §§ *Configure Browsers* → *Run tests on different browsers*, *Chromium* / *Chromium: headless shell* / *Chromium: new headless mode*, *Firefox*, *WebKit*, *Defaults* + *Regression testing* · Playwright *Projects* §§ *Introduction*, *Configure projects for multiple browsers*, *Run projects* · Playwright *Visual comparisons* § *Introduction* · Chrome *Headless mode* § *Use old Headless mode*
- **Read time:** ~30 min

## a. Does the named source cover this?

Right project, wrong page. `/docs/intro` is titled **Installation** — a getting-started
walkthrough (Installing Playwright / What's Installed / Running the Example Test / HTML
Test Reports / UI Mode / Updating / System requirements), not a browser-differences doc.

What it delivers by side effect: `npm init playwright@latest` writes a config whose default
is three projects, and `npx playwright test` runs all of them. So a learner who follows
this page *does* execute the example spec in Chromium, Firefox and WebKit — half the
DELIVERABLE, accidentally. "Headless" appears twice, both times in passing.

What it does not deliver at all:
- No `--project` flag (that's on *Running tests*), so no way to isolate a browser.
- No statement that Playwright's WebKit ≠ Safari or its Firefox ≠ branded Firefox.
- Nothing on headless-vs-headed and no mention of the headless shell — the single biggest
  source of "headless-only problems," the explicit second half of the learning goal.
- No method for **recording** differences: no triage, no per-browser snapshot, no oracle.

I asked the page directly whether it explains debugging a one-browser failure. It does not.
PARTIAL rather than WRONG-DOCUMENT: correct project's docs, and it does get three engines
installed and running. Step 0 only — then straight to *Browsers*.

## b. Best primary source

**Playwright, "Browsers"** (https://playwright.dev/docs/browsers). The only page covering
both halves of this task at once: how to point the suite at each engine, *and* what each
bundled engine actually is. §*Configure Browsers* states the default config gives you three
projects; the per-engine sections are the caveats needed to interpret a red run;
§*Chromium: headless shell* is where the headless-only failure mode is documented at all.

Three companions, each covering one thing *Browsers* only gestures at:

1. **Playwright, "Projects"** (https://playwright.dev/docs/test-projects) — the mechanism.
   §*Configure projects for multiple browsers* has the config block, §*Run projects* has
   `--project`. This is what the learner copies to build the smoke suite.
2. **Chrome for Developers, "Chrome Headless mode"**
   (https://developer.chrome.com/docs/chromium/headless) — the authority for *why*
   headless-only bugs exist. Playwright quotes this page; go to the source.
3. **Playwright, "Visual comparisons"** (https://playwright.dev/docs/test-snapshots) — for
   "record any differences": per-project/OS snapshot names, `maxDiffPixels`.

Concept layer, if needed: **MDN, "Introduction to cross browser testing"** — §*Why do
cross-browser issues occur?* only. https://developer.mozilla.org/en-US/docs/Learn_web_development/Extensions/Testing/Introduction

## c. What it leaves out

- **No triage method.** *Browsers* says the engines differ; nothing says what to do when one
  goes red. App bug, engine bug, Playwright-patch artifact, or timing flake? The lesson must
  supply that decision tree — no source I fetched does.
- **No worked list of what actually differs.** Playwright names media codecs and platform
  APIs and stops. The recurring offenders (date parsing, `input type=date`, sticky/scroll
  behaviour, sub-pixel font rendering) are enumerated nowhere official.
- **No smoke-suite design guidance, and no cost framing.** "Small suite" is the task's word,
  not the docs'. Nothing says which checks are worth tripling — and tripling is the CI cost.
- **The headless story is split across two vendors.** Playwright says it ships a headless
  shell; Chrome says why that shell behaves differently. Neither page says both. (And MDN's
  module is pre-automation — use it for *why*, never *how*.)

## d. Credible disagreement

**1. Chrome and Playwright disagree about the default, in writing.** Chrome's docs call the
new headless mode "the real Chrome browser, and is thus more authentic, reliable" (quoted
*by Playwright itself*), yet Playwright still ships the separate headless shell as the
default and makes the real thing opt-in via `channel: 'chromium'`. That is the whole
headless lesson in one sentence: **by default you are not testing the browser your users
run.** Sourced on both sides — no blending needed.

**2. Playwright's WebKit is not Safari, and Playwright says so.** §*WebKit*: built from
WebKit main "often before these updates are incorporated into Apple Safari," and it
"doesn't work with the branded version of Safari since it relies on patches." The
vendor-blog camp (BrowserStack et al.) sells real-Safari-on-real-hardware off this —
commercially interested, but the fact is Playwright's own. Green WebKit ≠ Safari works;
same caveat for Firefox.

**3. RST — checking is not testing.** Bach & Bolton, "Testing and Checking Refined"
(satisfice.com/blog/archives/856, 10 Aug 2024): "Checking is the mechanistic process of
verifying propositions about the product," while testing "can only be *supported* by
tools." A three-browser smoke suite is three sets of checks; it passes on a page visibly
broken in one engine, because nobody looked. High bite here — cross-browser defects are
disproportionately *visual*, the exact class assertions cannot see.

## e. Worked examples worth adapting

- **Best defect story available — real, dated, official: Playwright issue #33566, "Changes
  in Chromium headless in Playwright v1.49."** Moving from headless shell to real headless
  Chrome changed behaviour four ways: PDFs render in-page instead of downloading, screenshots
  differ enough to need updated expectations, runs got slightly slower, GPU/WebGL
  availability changed. Show the symptoms, ask why, then reveal the Chrome architecture line
  — old headless "didn't share any of the Chrome browser code in `//chrome`."
- **Deliberate three-engine break.** MDN §*Handling common HTML and CSS problems* supplies
  cheap real breakages to plant: a `-moz-`-prefixed pseudo-class inside a comma-separated
  selector list, which "all browsers other than Firefox will ignore the entire block";
  `input type="date"`, which non-supporting browsers silently render as `type="text"`.
  Both fail in exactly one engine and neither throws — good for teaching oracle choice.
- **The snapshot trap.** Add `toHaveScreenshot`, run three projects, watch three baselines
  appear. Playwright's own warning is the lesson: rendering varies with OS, hardware,
  **power source (battery vs. adapter)**, and headless mode. That last one lands.
- **Gap — no public postmortem found.** No citable named-company incident report for a
  cross-browser or headless-only production defect; the rest of the field is vendor content
  marketing (BrowserStack, LambdaTest). #33566 is the real artifact — use it.

## Verbatim quotes

**Playwright, "Browsers" § Chromium: headless shell / § Chromium: new headless mode:**
- "Playwright ships a regular Chromium build for headed operations and a separate chromium headless shell for headless mode."
- "You can opt into the new headless mode by using `'chromium'` channel."
- (quoting Chrome) "New Headless on the other hand is the real Chrome browser, and is thus more authentic, reliable, and offers more features. This makes it more suitable for high-accuracy end-to-end web app testing or browser extension testing."

**Playwright, "Browsers" § WebKit / § Firefox / § Defaults:**
- "Playwright's WebKit is derived from the latest WebKit main branch sources, often before these updates are incorporated into Apple Safari and other WebKit-based browsers. ... Playwright doesn't work with the branded version of Safari since it relies on patches. Instead, you can test using the most recent WebKit build."
- "While running WebKit on Linux CI is usually the most affordable option, for the closest-to-Safari experience you should run WebKit on mac, for example if you do video playback."
- "Playwright's Firefox version matches the recent Firefox Stable build. Playwright doesn't work with the branded version of Firefox since it relies on patches."
- (in both § Firefox and § WebKit) "Note that availability of certain features, which depend heavily on the underlying platform, may vary between operating systems. For example, available media codecs vary substantially between Linux, macOS and Windows."

**Playwright, "Browsers" § Configure Browsers / "Projects" / "Running tests":**
- "The default config when installing Playwright gives you 3 projects, Chromium, Firefox and WebKit."
- "Tests run in headless mode by default, meaning no browser window opens while running the tests and results appear in the terminal."
- `npx playwright test --project=firefox` · `npx playwright test --project webkit --project firefox` · `npx playwright test --headed`

**Playwright, "Visual comparisons" § Introduction:**
- "Browser rendering can vary based on the host OS, version, settings, hardware, power source (battery vs. power adapter), headless mode, and other factors."
- "Screenshots differ between browsers and platforms due to different rendering, fonts and more, so you will need different snapshots for them."

**Chrome for Developers, "Chrome Headless mode" § Use old Headless mode:**
- "Headless mode was a separate, alternate browser implementation that happened to be shipped as part of the same Chrome binary. It didn't share any of the Chrome browser code in `//chrome`."
- Since Chrome 132.0.6793.0, "the old Headless mode is only available as a standalone binary named `chrome-headless-shell`".

**Playwright issue #33566, "Changes in Chromium headless in Playwright v1.49":** PDFs render
in-page rather than downloading; screenshots differ and need updated expectations; runs are
generally slightly slower; GPU/WebGL availability, features and performance vary.

**MDN — cross-browser Intro § *Why do issues occur?* and § *Handling common HTML and CSS problems*:**
- "sometimes browsers have bugs, or implement features differently... Browsers are much better at following standards these days, but differences and bugs still creep through sometimes."
- "Don't include a `:-moz-` prefixed pseudo class or pseudo-element within a comma-separated group of selectors outside of a `:is()` or `:where()` forgiving selector list as all browsers other than Firefox will ignore the entire block."
- "If a browser didn't support an input type, the browser used the default of `type=\"text\"`."

**Bach & Bolton, "Testing and Checking Refined" (satisfice.com, 10 Aug 2024):**
- "Checking is the mechanistic process of verifying propositions about the product." / "Checking is a process that can, in principle be performed by a tool instead of a human, whereas testing can only be *supported* by tools."
