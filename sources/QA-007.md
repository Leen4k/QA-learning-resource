## c. What it leaves out

1. **A test case template. There isn't one anywhere in the syllabus.** §1.4.1
   says only that test design "includes elaborating the test conditions into
   test cases and other testware". The closest thing is one sentence in §4.5.3:
   test cases "contain sentences in natural language involving the necessary
   preconditions (if any), the inputs, and the postconditions." No ID, no
   numbered steps, no expected-result field, no test data column. The learner's
   stated want — *cases another person can follow* — is the one thing Chapter 4
   never addresses.
2. **Worked examples.** In all of §4.2 there is exactly one concrete number: the
   3-value BVA illustration on p.39. EP, decision tables and state transition
   get definitions and coverage formulas with zero data. The examples live in a
   *separate* document (§e) the syllabus never cross-references.
3. **What "invalid" actually looks like.** §4.2.1 establishes that invalid
   partitions must be covered; it never enumerates candidate values (empty,
   null, whitespace-only, >255 chars, Unicode, negative, wrong type).
4. **How many cases to write.** The deliverable says 10–15; the syllabus talks
   only in coverage percentages and pushes sizing off to §5.1.5.
5. **Abstract vs concrete cases**, and **§4.1 defers the detail to
   ISO/IEC/IEEE 29119-4**, which is paywalled.

## d. Credible disagreement

**Rapid Software Testing vs ISTQB — RST denies that test cases are the unit of
testing at all.**

Bach & Hodder, *Test Cases Are Not Testing* (Testing Trapeze debut issue, 2014;
page updated 2021-07-07, https://www.satisfice.com/download/test-cases-are-not-testing):
"creating and performing test cases is not the same thing as doing testing. In
fact, test cases are a poor basis for organizing a test process and no basis at
all for measuring testing progress." The industry's obsession with test cases
must end, they argue, or "testing as a field will be never be worthy of respect."

Bolton's testing/checking distinction (2009-08-29,
https://developsense.com/blog/2009/08/testing-vs-checking; refined 2013 with
Bach) sharpens it: a **check** is "a process of confirmation, verification, and
validation" that "provides a binary result — true or false"; **testing** is "a
process of exploration, discovery, investigation, and learning" and "has an
open-ended result." A test case written so another person can follow it is *by
construction* a check, not a test.

Do not blend these. Honest framing: this deliverable produces checks, which is
legitimate — a regression suite, a handover artifact, a shared definition of
"works". What RST denies is the next step, where the 15 cases become the
*measure* of whether the flow was tested. §4.4.3 half-concedes it: high-level
checklists yield "potentially greater coverage but less repeatability".

## e. Worked examples worth adapting

**ISTQB CTFL v4.0 Sample Exam set A** — the missing worked-example half of the
syllabus: free, official, four K3 problems with published rationale. Both PDFs
read this session — ISTQB documents *hosted by* ASTQB, the real thing, not an
ASTQB summary page. Questions v1.0, 30pp — https://astqb.org/assets/documents/ISTQB_CTFL_Sample-Exam-Questions_v4.0.pdf
Answers v1.0, 34pp — https://astqb.org/assets/documents/ISTQB_CTFL_Sample-Exam-Answers_v4.0.pdf

- **Q20 (FL-4.2.1, K3, EP)** — apartment search form, two criteria: floor
  {ground; first; second or higher} × garden type {none; small; large}, rule
  that only ground-floor apartments may have gardens. Minimal Each-Choice set is
  4: (ground, small), (ground, large), (first, none), (second+, none). **The
  best single exercise here** — two parameters plus a validity constraint.
- **Q21 (FL-4.2.2, K3, BVA)** — course grading, 0–50 failed / 51–60 fair /
  61–70 satisfactory / 71–80 good / 81–90 very good / 91–100 excellent. Twelve
  2-value boundary values: 0, 50, 51, 60, 61, 70, 71, 80, 81, 90, 91, 100. Six
  covered → 50%. *Discrepancy between the two v1.0 PDFs: the question table
  lists TC6 = 80, the answer rationale lists "TC7 – 51". 6/12 either way, but
  check before quoting.*
- **Q22 (FL-4.2.3, K3, decision table)** — bicycle rental: members get 20% off,
  discount lost if a return deadline is missed, T-shirt after 15 rentals. An
  8-column table where R6 is the infeasible rule. Shows a decision table
  *finding a requirement gap*, not just cases.
- **Q23 (FL-4.2.4, K3, state transition)** — INIT → DEBUG MODE / IN OPERATION →
  ON HOLD → OFF, events test/run/pause/resume/error/done; 3 cases for valid
  transitions coverage.
- **Q29 (ATDD)** — an "As an Editor…" story with six acceptance criteria; asks which candidate is a legitimate ATDD test. Use for §4.5.3's scoping rule.

**Test Heuristics Cheat Sheet** (Hendrickson, Lyndsay & Emery; Ministry of
Testing edition by Simon Tomes, 2022-03-31) —
https://www.ministryoftesting.com/articles/test-heuristics-cheat-sheet — fills
gap (c)(3) with actual values. Sections: Data Type Attacks, Paths/Files, Time
and Date, Numbers, Strings, Web/API/Mobile Tests. Numbers list: "0, 32768
(2^15), 32769 (2^15 + 1), 65536 (2^16), 65537 (2^16 +1), 2147483648 (2^31)";
boundary heuristic "Approaching the Boundary (almost too big, almost too small),
At the Boundary". *© 2006 Quality Tree Software / © 2022 Ministry of Testing; no
open licence stated — link, don't reproduce.*

**Defect story, from the syllabus itself (§4.2.2, p.39):** a spec of `if (x ≤ 10)`
implemented as `if (x = 10)`. No 2-value BVA data (x = 10, x = 11) catches it; x = 9 from 3-value BVA does.

## Verbatim quotes

**§4.2.1, p.38** — "Equivalence Partitioning (EP) divides data into partitions (known as equivalence partitions) based on the expectation that all the elements of a given partition are to be processed in the same way by the test object."

**§4.2.1, p.39** — "A partition containing valid values is called a valid partition. A partition containing invalid values is called an invalid partition." … "test cases must exercise all identified partitions (including invalid partitions) by covering each partition at least once."

**§4.2.1, p.39** — "Each Choice coverage requires test cases to exercise each partition from each set of partitions at least once. Each Choice coverage does not take into account combinations of partitions."

**§4.2.2, p.39** — "BVA focuses on the boundary values of the partitions because developers are more likely to make errors with these boundary values. Typical defects found by BVA are located where implemented boundaries are misplaced to positions above or below their intended positions or are omitted altogether."

**§4.2.3, p.40** — "The strength of decision table testing is that it provides a systematic approach to identify all the combinations of conditions, some of which might otherwise be overlooked. It also helps to find any gaps or contradictions in the requirements."

**§4.5.3, p.45** — "Typically, the first test cases are positive, confirming the correct behavior without exceptions or error conditions … After the positive test cases are done, the team should perform negative testing."

**§4.5.3, p.45** — "Test cases should be expressed in a way that is understandable for the stakeholders. Typically, test cases contain sentences in natural language involving the necessary preconditions (if any), the inputs, and the postconditions." … "The test cases must cover all the characteristics of the user story and should not go beyond the story. … In addition, no two test cases should describe the same characteristics of the user story."

**§1.4.1, p.18** — "Test design includes elaborating the test conditions into test cases and other testware (e.g., test charters). This activity often involves the identification of coverage items, which serve as a guide to specify test case inputs."

**Bach & Hodder 2014/2021, abstract** — "creating and performing test cases is not the same thing as doing testing. In fact, test cases are a poor basis for organizing a test process and no basis at all for measuring testing progress."

**Bolton 2009-08-29** — a check "provides a binary result—true or false, yes or no"; a test "has an open-ended result."
