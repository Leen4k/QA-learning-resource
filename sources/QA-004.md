## c. What it leaves out

1. **Gray-box does not exist in ISTQB.** §4.1: "test techniques are classified as black-box, white-box, and experience-based." The third category is *experience-based*, not gray-box. I also checked the **ISTQB Standard Glossary v3.7** (2022-10-31, 48pp): the G-run on p.18 goes `game state testing → generic test automation architecture → graphical user interface (GUI) → GUI testing → hacker`. **No grey-box or gray-box entry exists.** ⚠️ A web search asserted ISTQB officially defines grey-box as "a test type that combines elements of black-box testing and white-box testing" — that is a third-party gloss (Tricentis / istqb.guru), **not** in the glossary. Do not repeat it. The deliverable's middle category has no ISTQB backing; the lesson must source it elsewhere or say plainly that it is industry vernacular, not a standards term.
2. **No selection criteria.** FL-4.1.1 is K2 *Distinguish*, not *select*. The syllabus says what the categories **are**, never when one is the right choice. Nothing on access, contract, cost, tester skill, or risk as the deciding factor. §4.3.3 is the sole fragment of argument, and there is no counterpart "value of black-box testing" section.
3. **No worked classification set.** No list of sample tests with labels anywhere. The learner invents all twelve; the lesson must supply them.
4. **The ambiguous middle is explicitly out of scope** — exactly where gray-box would live. §4.3: "There are also white-box test techniques used in higher test levels (e.g., API testing)… These techniques are not discussed in this syllabus." So API tests, DB-state assertions, and log-inspection tests get no ruling.
5. **Two overlapping framings, unreconciled.** Black-box is a technique family (§4.2) *and* a test type (§2.2.2); the glossary lists `white-box testing` ("Testing based on an analysis of the internal structure") separately from `white-box test technique` ("**only** based on the internal structure"). Teach the classification target explicitly: the test's *information source*, not its level, tool, or author.

## d. Credible disagreement

**Henrik Emilsson, thetesteye.com, 2013-02-18** (fetched this session) — https://thetesteye.com/blog/2013/02/black-box-vs-white-box/. Argues the split is not about *access to code* at all, but about *where your attention is*: "Black Box Testing: When you worry about what happens outside the box." / "White Box Testing: When you worry about what's going on inside the box."

His point: a tester may hold full internal knowledge while doing outward-focused testing, and vice versa — "what matters is that there might be a difference in scope, question formulation, and information objectives." He adds that in practice he rarely sorts testing into these categories, using them instead as heuristics to shift perspective.

A sharp, usable conflict. ISTQB classifies by **what the tests are derived from** (specification vs. internal structure) — a property of the artifact. Emilsson classifies by **what question the tester is asking** — a property of the intent. Under ISTQB a test has one correct label; under Emilsson the same test can be either, depending on why you ran it. Run the twelve samples through both lenses and the disagreements *are* the lesson.

Retrieve it before quoting. ## e. Worked examples worth adapting

All from the syllabus, all short enough to drop into a classification table's "reason" column.

- **§4.2.2 (p.39) — the 3-value BVA defect.** `if (x ≤ 10)` mis-implemented as `if (x = 10)`. Neither 2-value BVA datum (x=10, x=11) catches it; x=9 from 3-value BVA does. A black-box test whose adequacy turns on a choice made without seeing code.
- **§4.3.1 (p.41) — what 100% statement coverage misses.** "it may not detect defects that are data dependent (e.g., a division by zero that only fails when a denominator is set to zero)." The canonical case for why white-box coverage is not sufficiency.
- **§4.3.3 (p.42) — defects of omission (Watson 1996).** "if the software does not implement one or more requirements, white box testing may not detect the resulting defects of omission." The mirror image: white-box cannot find what was never written. Pair with the previous item as the two-sided case for using both.
- **§4.3.2 (p.42) — subsumption.** "Branch coverage subsumes statement coverage… any set of test cases achieving 100% branch coverage also achieves 100% statement coverage (but not vice versa)." A crisp, checkable fact.
- **§4.2.4 (p.41) — fault masking.** "Testing only one invalid transition in a single test case helps to avoid fault masking, i.e., a situation in which one defect prevents the detection of another."

## Verbatim quotes

**§4.1, p.38** — "In this syllabus, test techniques are classified as black-box, white-box, and experience-based."

**§4.1, p.38** — "Black-box test techniques (also known as specification-based techniques) are based on an analysis of the specified behavior of the test object without reference to its internal structure. Therefore, the test cases are independent of how the software is implemented. Consequently, if the implementation changes, but the required behavior stays the same, then the test cases are still useful."

**§4.1, p.38** — "White-box test techniques (also known as structure-based techniques) are based on an analysis of the test object's internal structure and processing. As the test cases are dependent on how the software is designed, they can only be created after the design or implementation of the test object."

**§4.1, p.38** — "Experience-based test techniques effectively use the knowledge and experience of testers for the design and implementation of test cases… Experience-based test techniques can detect defects that may be missed using the black-box and white-box test techniques. Hence, experience-based test techniques are complementary to the black-box and white-box test techniques."

**§2.2.2, p.29** — "Black-box testing (see section 4.2) is specification-based and derives tests from documentation external to the test object. The main objective of black-box testing is checking the system's behavior against its specifications." / "White-box testing (see section 4.3) is structure-based and derives tests from the system's implementation or internal structure (e.g., code, architecture, work-flows, and data flows). The main objective of white-box testing is to cover the underlying structure by the tests to the acceptable level." / "All the four above mentioned test types can be applied to all test levels, although the focus will be different at each level."

**§4.3, p.41** — "There are also white-box test techniques used in higher test levels (e.g., API testing), or using coverage not related to code (e.g., neuron coverage in neural network testing). These techniques are not discussed in this syllabus."

**ISTQB Glossary v3.7, p.5** — "black-box test technique — *Synonyms:* black-box test design technique, specification-based test technique — A test technique based on an analysis of the specification of a component or system."

**ISTQB Glossary v3.7, p.48** — "white-box test technique — *Synonyms:* white-box test design technique, structure-based test technique — A test technique only based on the internal structure of a component or system." / "white-box testing — *Synonyms:* clear-box testing, code-based testing, glass-box testing, logic-coverage testing, logic-driven testing, structural testing, structure-based testing — Testing based on an analysis of the internal structure of the component or system."

**roadmap.sh gray-box node, complete** — "Gray box testing is a software testing technique to test a software product or application with partial knowledge of the internal structure of the application. The purpose of gray box testing is to search and identify the defects due to improper code structure or improper use of applications."
