# QA-019 — Reading a web page well enough to investigate it

> Dossier, not lesson content. Every claim below must be re-read at source
> before it ships in a lesson.

- **Verdict:** PARTIAL
- **Named source:** https://developer.mozilla.org/en-US/docs/Learn_web_development
- **Best primary source:** Chrome DevTools documentation — https://developer.chrome.com/docs/devtools — paired with MDN's Forms module for the forms/validation half
- **Exact sections to read:** Chrome DevTools "View and change the DOM" (steps 1–4 + Appendix *HTML versus the DOM*) · "Inspect network activity" (whole tutorial) · Application → Storage (Local storage, Session storage, Cookies) · MDN Forms "How to structure a web form" + "Client-side form validation"
- **Read time:** ~110 min

## a. Does the named source cover this?

The URL as written is a hub page, not a document. Its six headings are "About Learn web
development", "Don't know where to get started?", "Test your skills", "Getting our code
examples", "Contact us", "See also". It teaches nothing. Anyone handed this link is being
handed a table of contents and told to figure it out. What it fans out to is genuinely good
— this is not roadmap.sh — but it aims at the wrong target in two ways.

**Wrong altitude.** MDN Learn is a curriculum for *building* web pages. The nine Core
modules — Structuring content with HTML, CSS styling basics, CSS text styling, CSS layout,
Dynamic scripting with JavaScript, JavaScript frameworks and libraries, Accessibility,
Design for developers, Version control — are framed as what "every web developer should have
a good grounding in" so they can "design and build a basic, accessible web app". The
deliverable asks the learner to *inspect* a page they did not write. CSS layout and version
control do not serve that, and the Core path is tens of hours against a 6h budget.

**It drops half the deliverable.** The one page in the Learn path that maps to the task is
"What are browser developer tools?" Its sections: "How to open the devtools in your
browser", "The Inspector: DOM explorer and CSS editor", "The JavaScript debugger", "The
JavaScript console". No Network section — despite the article's own intro promising to
cover "showing which assets the page has requested and how long they took to load." That
promise is never kept anywhere on the page. Storage/cookie inspection is absent too, and it
never draws the view-source-versus-live-DOM distinction — the single concept a tester most
needs.

Scored against the four deliverable items: **forms — yes, well; validation — yes, very
well; state changes — no; network calls — no.** Two of four, from pages the plan does not
name. PARTIAL, and the plan should be edited to point at specific URLs.

## b. Best primary source

No single free document covers all four. Use two.

**Spine — Chrome DevTools docs** (https://developer.chrome.com/docs/devtools). The tool the
deliverable is performed in, documented as hands-on tutorials against live demo pages rather
than reference prose.

- **"View and change the DOM"** (/docs/devtools/dom) — steps: *View DOM nodes*, *Edit the
  DOM*, *Access nodes in the Console*, *Break on DOM changes*, *Next steps*. The Appendix
  section **"HTML versus the DOM"** is the load-bearing paragraph for this whole task, and
  *Break on DOM changes* is the sleeper: the cleanest way to catch a state change in the act.
- **"Inspect network activity"** (/docs/devtools/network) — self-described as "a hands-on
  tutorial", demo page at `chrome.dev/devtools-network-activity/getstarted.html`. Covers
  filtering by string/regex/property and resource type, plus the Headers / Response /
  Preview tabs on a single request. **Get Data** fires the fetch/XHR case the task needs.
- **Application → Storage** (/docs/devtools/storage/localstorage, /sessionstorage,
  /docs/devtools/application/cookies) — where "state changes" lives; skim, don't study.

**Forms half — MDN Forms module** (/en-US/docs/Learn_web_development/Extensions/Forms). Read
only **"How to structure a web form"** and **"Client-side form validation"** — the latter is
the strongest single page in the named source. Watch the URL: the module sits under
`Extensions/`, not `Core/`; `Core/Forms/Form_validation` returns 404.

Firefox equivalent for the network half (Opening the Network Monitor · UI overview ·
Network request list / details): https://firefox-source-docs.mozilla.org/devtools-user/network_monitor/

## c. What it leaves out

Chrome's docs are written for the developer who owns the code. Five gaps for a tester:

- **No reading strategy.** They say what each panel does, never what to *look for*. A tester
  needs a sweep order — what fires on load, what fires on submit, what changed. The lesson
  must supply it; no source will.
- **Status codes are named, not taught.** The network tutorial mentions "The HTTP response
  code" and shows blocked requests in red, but never what 4xx versus 5xx means for who you
  file the bug against. Pull that from MDN's HTTP status reference separately.
- **Nothing on turning an observation into a bug report** — the whole point for a QA reader,
  and outside the scope of both sources.
- **No treatment of "the request succeeded but the payload is wrong."** A 200 with a bad
  body is the most common web defect a tester finds; neither doc frames it.
- **MDN's validation article addresses the developer adding validation**, not the tester
  defeating it — same facts, inverted posture. See (d).

## d. Credible disagreement

**The sharp one is about what a tester should do with this skill once they have it.**
Bolton's "A Letter To The Programmer" argues the tester's job stops at the observation:
"I tell you what I observe, in this case entirely from the outside," and — withholding
diagnosis — "until you've looked at the code, neither do you." DevTools fluency cuts
against this. A tester who can read a stack trace and a failed request feels qualified to
write "the API returns null because the auth token expired," is often wrong, and has now
anchored the developer on a false lead. Report the symptom and your evidence; let the person
who owns the code find the cause. Land this explicitly, because the lesson is actively
creating the temptation.

**The second is a posture flip on validation.** MDN teaches client-side validation as a
developer feature. The tester's reading is adversarial, and MDN supplies the ammunition
itself: it "is too easy to bypass, so malicious users can still easily send bad data through
to your server." The tester's question is never "does the red text appear?" but "what
happens when I strip the attribute and submit anyway?" Same document, opposite use — don't
teach it in MDN's voice.

Note: I found no RST position *against* technical literacy for testers. Bach and Bolton are
pro-technical-skill; the disagreement is about scope of claim, not about whether testers
should learn this. Do not overstate it.

## e. Worked examples worth adapting

- **Chrome's network demo page** (`chrome.dev/devtools-network-activity/getstarted.html`) —
  free, live, instrumented. Its **Get Data** button fires a JSON request: a ready-made "find
  the API call behind the button" exercise, no setup, exact motion.
- **"Break on DOM changes"** from the Chrome DOM tutorial. Adapt into: give the learner a
  page where something changes and they cannot say why; make them set a subtree-modification
  breakpoint and catch it. Teaches "state change" as an observable event, not a word.
- **The validation-bypass drill.** Take any form with `required` and `pattern`, delete the
  attributes in the Elements panel, submit, watch what the server does. Highest-value 10
  minutes in the task: makes the client/server split concrete, produces a real finding on
  most real apps, MDN's own warning is the citation. Scope it to the learner's own app.
- **Gap — no defect story found.** No citable, free, specific production incident caused by
  client-side-only validation. OWASP WSTG §4.7 (Input Validation Testing) has 22 tests, none
  a client-side-bypass test; the nearest, §4.11.6 Testing for Client-side Resource
  Manipulation, is a different thing. A story must come from the learner's workplace or be
  written as an explicit hypothetical.

## Verbatim quotes

**Chrome DevTools, "View and change the DOM", Appendix — "HTML versus the DOM":**
- "HTML represents initial page content and the DOM represents active, current page content. When JavaScript adds, removes, or edits nodes, the DOM becomes different than the HTML."

**Chrome DevTools, Application panel overview:**
- "Use the Application panel to inspect, modify, and debug many aspects of your web app including its manifest, service workers, storage, and cache data."

**MDN, "Client-side form validation" — §"What is form validation?":**
- "Validation done in the browser is called client-side validation, while validation done on the server is called server-side validation."

**MDN, "Client-side form validation" — §"Client-side form validation":**
- "However, client-side validation should not be considered an exhaustive security measure! Your apps should always perform validation, including security checks, on any form-submitted data on the server-side as well as the client-side, because client-side validation is too easy to bypass, so malicious users can still easily send bad data through to your server."
- "Warning: Never trust data passed to your server from the client. Even if your form is validating correctly and preventing malformed input on the client-side, a malicious user can still alter the network request."

**MDN, "Client-side form validation" — §"Using built-in form validation"** lists exactly:
`required`, `minlength`/`maxlength`, `min`/`max`/`step`, `type`, `pattern`.

**MDN, "What are browser developer tools?" — intro promise vs. actual sections (the gap):**
- Intro claims it covers "showing which assets the page has requested and how long they took to load."
- Section headings, in full: "How to open the devtools in your browser", "The Inspector: DOM explorer and CSS editor", "The JavaScript debugger", "The JavaScript console". No network section exists.

**Michael Bolton, "A Letter To The Programmer" (developsense.com, 2009-09):**
- "I tell you what I observe, in this case entirely from the outside."
- "I think it might be important, though, for us to understand why the problem is there in the first place. That's because I don't know whether the problem that I'm seeing is a big deal. And the thing is, until you've looked at the code, neither do you."
