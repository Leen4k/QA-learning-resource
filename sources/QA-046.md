## c. What it leaves out

- **It never shows a single worked prompt for a test task.** All 71 pages contain exactly one concrete prompt pair, and it is a throwaway (§2.1.3). Every hands-on objective *describes* an exercise — "create a prompt that instructs the AI to generate functional test cases" — without printing one. The learner gets a six-slot checklist and no filled-in instance. For this deliverable that is the biggest gap.
- **No oracle for the review step.** §2.3.1's metrics measure output "against expert-written test cases, requirements, or other standards" — they presuppose you already hold the answer key. If you had it you wouldn't need the AI. The circularity is never named.
- **"Missing cases" is the deliverable's hardest column, and the syllabus hands it to the model.** §2.2.1 offers "Support coverage analysis"; HO-2.2.2a has the prompt "verify the completeness of the generated test cases… by having the AI generate a table summarizing the coverage." Asking the model that wrote the tests whether the tests are complete is a weak oracle. The syllabus does not flag it. The lesson must.
- **No recording format.** §3.1.1's three-way taxonomy (hallucination / reasoning error / bias) is a good spine for the deliverable's log, but there is no template, severity scale, or worked defect entry anywhere.
- **The efficiency claim is assumed, not evidenced.** §2.3.1 lists "Time Efficiency: Evaluates the time saved compared to manual test efforts" — the metric presupposes time is saved. No study cited. See §d.
- **Privacy is policy-level, not desk-level.** §3.2.3 gives organisational controls (data minimization, anonymization, encryption, "involve senior Security Engineers, Legal counsel, the CTO, or the CISO"). Nothing tells a solo learner the one thing they need before pasting a user story into a chatbot: whether *this* vendor tier trains on input by default. Consumer-vs-API retention differences are absent entirely.
- **The exercises are gated.** Hands-on objectives target accredited courses (min. 13.6 hours instruction); the syllabus describes them but supplies no materials.

## d. Credible disagreement

**1. RST attacks the syllabus's core framing.** Bach, *Rapid Software Testing and AI* (satisfice.com/rapid-software-testing-and-ai-rst-ai, fetched): all AI is a black box "whose behavior is neither controlled, nor understood, nor otherwise known to be safe," and of current AI-in-testing work, "too much of that work is 'slop.' Too much of it is fake testing." ISTQB treats GenAI as an assistant whose output you score with metrics and improve with better prompts; RST treats it as an unaccountable oracle demanding "constant vigilance," where the operator owns the result outright. Name the split, don't blend it: **ISTQB asks "did the output score well?"; RST asks "am I willing to sign my name to this?"** The RST question is the one that actually generates a mistake log.

**2. The syllabus disagrees with itself — a free teaching hook.** §2.2.1 sells GenAI on "Prioritize test conditions based on risk level." §3.1.1 then concedes: "Test planning and test case prioritization are examples of test tasks that require logical reasoning and where LLMs can make reasoning errors." Put those two sentences side by side and the reader learns more about calibrating trust than any amount of prose.

**3. METR RCT — the productivity premise is empirically contested.** *Measuring the Impact of Early-2025 AI on Experienced Open-Source Developer Productivity* (metr.org, 10 Jul 2025; arXiv:2507.09089): 16 experienced developers, 246 issues, repos averaging 22k+ stars and 1M+ LOC. Result: **developers took 19% longer with AI tools** — while forecasting a 24% speedup beforehand and still believing they had been sped up 20% afterwards. Carry the authors' own caveat: they explicitly do *not* claim this generalises to most developers, beyond software development, or forward as models improve. Use it for the perception gap, not as a verdict.

## e. Worked examples worth adapting

- **HO-2.2.1b (§2.2.1) — the deliverable's spine, already written.** Prompt-chain a user story through three verified stages: identify ambiguities → evaluate testability → evaluate completeness, with results "manually verified and corrected" at each step so "the next stage uses a clean result from the previous stage." Adapt directly.
- **HO-3.1.2a (§3.1.2) — the mistake-log generator.** Deliberately induce a hallucination: "confront at least two LLMs with a situation in which the LLMs invent irrelevant elements, e.g., add unrelated criteria that do not exist in the given contextual data." Watching a model invent an acceptance criterion beats any warning paragraph.
- **HO-3.1.2b (§3.1.2) — reasoning error with a known answer.** A test-estimation/prioritization problem where "the result of the LLM will be compared with the exact result that should be achieved," across an LLM, an SLM and a reasoning model. The rare exercise with a real oracle — build the verification step on it.
- **§2.3.1 metric table — a ready-made review rubric.** Seven rows (Accuracy, Precision, Recall, Relevance and Contextual Fit, Diversity, Execution Success Rate, Time Efficiency), each with a testing-specific example. Have the learner score the AI's draft on three of these rather than inventing a scale.
- **§3.2.2 attack vector table** — Context Manipulation / Request manipulation / Data poisoning / Malicious code generation, each with a concrete example ("Generation of code to open a communication channel with a specific, malicious IP"). Four rows, all quotable.
- **HO-2.2.2b (§2.2.2)** — few-shot Gherkin generation from user stories, if the learner already writes given-when-then. **§2.2.5** maps the three techniques to task types.
- **Real privacy story: Samsung, March 2023.** AI Incident Database #768 (fetched): "Samsung engineers are reported to have inadvertently leaked sensitive company data sometime in March 2023, including source code and internal meeting notes, by using ChatGPT to assist with tasks" — at least three incidents within weeks of an internal ban being lifted, ending in a company-wide ban (Bloomberg/Forbes, 2 May 2023, **not fetched — verify before quoting figures**). Pairs exactly with §5.1.1 Shadow AI, and makes the deliverable's privacy column concrete: the leak was ordinary engineers doing ordinary debugging.
