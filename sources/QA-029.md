# QA-029 — HTTP and API fundamentals

> Dossier, not lesson content. Every claim below must be re-read at source
> before it ships in a lesson.

- **Verdict:** WRONG-DOCUMENT
- **Named source:** https://learning.postman.com/docs/getting-started/quick-start/
- **Best primary source:** MDN Web Docs, HTTP guide — https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Overview (spine), normatively backed by RFC 9110 *HTTP Semantics* — https://www.rfc-editor.org/rfc/rfc9110.html
- **Exact sections to read:** MDN *Overview of HTTP* §§ *HTTP Messages* → *Requests*, *Responses* · MDN *HTTP response status codes* (five class headings; read 200/201/400/401/403/404/422/500) · MDN *HTTP authentication* §§ *general framework*, *WWW-Authenticate…*, *Authorization…*, *Authentication schemes*, *Security of basic authentication* · MDN Glossary *Safe (HTTP)*, *Idempotent* · RFC 9110 §9, §9.2.1, §9.2.2, §11, §15.5.1/.2/.4 · RFC 9457 · OWASP API Security Top 10 2023, API1
- **Read time:** ~55 min

## a. Does the named source cover this?

No. A five-minute product tour of a GUI, filed under a learning goal about a protocol. Its three
headings: *Send an API request*, *Create a collection and save your request*, *Write a test for
your API request*.

Score it against the four nouns in the goal — requests, responses, authentication, JSON contracts
— and it is 0/4. "GET" appears once in passing, with no explanation of what a method is. Status
codes appear only as the literal `200` inside a snippet the learner picks from a dropdown; nothing
says what the number means or that there are five classes. Headers and authentication: absent.
JSON: absent as a concept — `pm.response.json()` is not on the page. Against the DELIVERABLE it
does slightly better and still fails: one saved request and one positive assertion, produced by
clicking **Snippets → Status code: Code is 200**. The negative half gets one sentence (quoted
below), then no instruction and no second snippet.

WRONG-DOCUMENT, not PARTIAL — the tool is right, the page is not a source on the topic. Keep it as
~10 min of onboarding, then leave. If the plan wants a Postman link, name
`/docs/tests-and-scripts/write-scripts/test-examples/` instead: jsonSchema, header and body
assertions — though still no negative-testing section.

## b. Best primary source

**MDN's HTTP guide** — free, stable, vendor-neutral, the only prose covering all four nouns in one
sitting. Four pages, in order: **Overview of HTTP** (`/Web/HTTP/Guides/Overview`), whose
§*Requests* / §*Responses* five-part anatomy *is* the "document one API request" template; **HTTP
response status codes** (`/Web/HTTP/Reference/Status`), where the 401-vs-403 paragraph is the
highest-value text on the page for a tester; **HTTP authentication**
(`/Web/HTTP/Guides/Authentication`) for `WWW-Authenticate` → `401` → `Authorization`; and
**Glossary: Safe** + **Idempotent**, two short pages that decide which negative tests are legal to
run twice. **RFC 9110** is the normative backstop: §9.2.1 safe, §9.2.2 idempotent, §11 auth,
§15.5.1/.2/.4 for 400/401/403.

For "JSON contracts" MDN has nothing. Use **OpenAPI v3.2.0** (19 Sep 2025,
spec.openapis.org/oas/latest.html) — *Responses / Response / Media Type Object*, which is what
"contract" means industrially — and **RFC 9457 Problem Details for HTTP APIs** (Jul 2023), the
standard shape of an *error* body and the missing half of every API lesson. Practice target:
**httpbin.org**, verified live this session via its own `spec.json` — `/status/{codes}`,
`/basic-auth/{user}/{passwd}`, `/bearer`, `/get` `/post` `/put` `/delete`. No signup, no key.

**Access note:** RFC 9110 is too long for the fetch tool — it truncates inside §6.4.2, before
Methods or Status Codes. Section numbers verified, §9.2.x/§15.5.x text not. Cite it by section.

## c. What it leaves out

- **All of the testing.** MDN is a protocol reference; it never says what to test or how to turn
  a status code into a case. The bridge — equivalence partitioning per request field, valid
  partition → positive case, each invalid → one negative — is the lesson's own work. See QA-007.
- **Modern auth, and a stale citation.** MDN's auth page is overwhelmingly Basic, with Apache and
  Nginx config sections; Bearer and AWS4-HMAC-SHA256 get one line each, while real APIs are Bearer
  tokens and API keys. It also states verbatim that "RFC 7235 defines the HTTP authentication
  framework" — obsoleted by RFC 9110 §11. Do not repeat that.
- **Who checks the contract, and in what notebook.** OpenAPI *describes* a response shape; nothing
  says anyone verifies it. Postman's `jsonSchema` assertion does — but Postman never calls it
  contract testing and MDN never mentions schemas. OpenAPI is also a machine format: no source
  fetched gives a human-readable one-request template. RFC 9457 adoption is thin — have the
  learner note its *absence* as a finding, not assume it.

## d. Credible disagreement

**1. RST: the deliverable is a set of checks, not tests.** Bolton, *Testing vs. Checking* (29 Aug
2009): "When a check passes, we don't know whether the program works; we only know that it's still
working within the scope of our expectations." Refined by Bach & Bolton (2024): checking is "the
mechanistic process of verifying propositions about the product," and "testing can only be
*supported* by tools." `pm.response.to.have.status(200)` is the purest check there is — it passes
on a 200 returning `null`, the wrong user's data, or an empty array where ten rows belong. High
bite: the plan's unit is "test cases," and that is exactly RST's target.

**2. The IETF reversed itself on how strict an API should be — and that decides what the
negative test asserts.** RFC 9413 *Maintaining Robust Protocols* (IAB, Jun 2023) takes on
Postel, §2: "Be strict when sending and tolerant when receiving." §4.1: an implementation
following that advice "enters a pathological feedback cycle." Not academic: send `age: "twelve"`
to an endpoint expecting an integer — is `200` a bug or a feature? A tolerant API says feature;
RFC 9413 says the tolerance *is* the defect. Decide before writing the assertion; the right move
is to file the ambiguity as a question. See QA-002.

## e. Worked examples worth adapting

- **Best JSON-contract defect story available, vendor-documented: X/Twitter `id` vs `id_str`.** IDs
  are 64-bit unsigned integers, "In JavaScript, integers are limited to 53 bits," and
  `10765432100123456789` silently becomes `10765432100123458000` — so the API ships every ID
  *twice*, as number and as string. Valid JSON, status 200, assertions green, data wrong. Kills
  "200 means it worked" in one slide; argues for asserting on value and type.
- **A negative test with teeth: OWASP API1:2023, Broken Object Level Authorization.** Scenario 1
  in OWASP's text — `/shops/{shopName}/revenue_data.json`, shop names harvested from another
  endpoint, revenue for thousands of stores. The exercise writes itself: authenticate as user A,
  request user B's object ID, assert **not 200**. OWASP's prevention list ends "Write tests to
  evaluate the vulnerability of the authorization mechanism" — the deliverable, in its own words.
- **The 401/403 drill on httpbin.** `GET /basic-auth/user/passwd` with no, wrong, then right
  credentials. MDN gives the expected answers verbatim: invalid → 401, valid-but-inadequate → 403.
- **The idempotency trap, from MDN's Glossary.** Its own worked sequence: `DELETE /idX/delete` →
  200, then 404, then 404. Have the learner write "DELETE returns 200" as a case, then run it
  twice. The case is correct and it fails — the whole lesson on why a negative expectation needs
  the request's history in it.
- **Gap:** no public postmortem found for an API contract break at a named company. X/Twitter is the
  real artifact; don't dress vendor blog posts up as case studies.

## Verbatim quotes

**Postman quick start** — "For example, you might write a test to validate your API's error
handling by sending a request with incomplete data or wrong parameters." · "Postman sent a GET
request to the Postman Echo API server" · `pm.test("Status code is 200", function () {
pm.response.to.have.status(200); });` · Confirmed **absent**: negative-testing instruction, 4xx,
schema validation, headers, authentication, `pm.response.json()`.

**MDN *HTTP response status codes*** — classes `100`–`199` / `200`–`299` / `300`–`399` /
`400`–`499` / `500`–`599`. · 401: "Although the HTTP standard specifies 'unauthorized',
semantically this response means 'unauthenticated'." · 403: "The client does not have access
rights to the content… Unlike `401 Unauthorized`, the client's identity is known to the server." ·
404: "Servers may also send this response instead of `403 Forbidden` to hide the existence of a
resource from an unauthorized client."

**MDN *HTTP authentication*** — "RFC 7235 defines the HTTP authentication framework" ← **stale,
superseded by RFC 9110 §11.** · "If a (proxy) server receives *invalid* credentials, it should
respond with a `401`… If a (proxy) server receives valid credentials that are *inadequate* to
access a given resource, the server should respond with the `403` `Forbidden` status code."

**MDN Glossary *Safe* / *Idempotent*** — "safe if it doesn't alter the state of the server… All
safe methods are also idempotent, but not all idempotent methods are safe." · "the first call of a
`DELETE` will likely return a `200`, while successive ones will likely return a `404`."

**RFC 9457 (Jul 2023)** — defines "a 'problem detail' to carry machine-readable details of errors
in HTTP response content to avoid the need to define new error response formats for HTTP APIs";
members `type`, `title`, `status`, `detail`, `instance`. · **RFC 9413 (IAB, Jun 2023)** §2: "Be
strict when sending and tolerant when receiving." §4.1: "An implementation that reacts to
variations in the manner recommended in the robustness principle enters a pathological feedback
cycle." · **OpenAPI v3.2.0** Responses Object: "The list of possible responses as they are
returned from executing this operation."

**Bolton, *Testing vs. Checking* (29 Aug 2009) / Bach & Bolton, *Testing and Checking Refined*
(satisfice.com/blog/archives/856, 10 Aug 2024)** — "A person who needs a test script to proceed is
a checker, not a tester." · "Checking is the mechanistic process of verifying propositions about
the product"; "testing can only be *supported* by tools."

**OWASP API1:2023** — "Attackers can exploit API endpoints that are vulnerable to broken
object-level authorization by manipulating the ID of an object that is sent within the request."
· "Write tests to evaluate the vulnerability of the authorization mechanism." · **X, *X IDs***
(docs.x.com/fundamentals/x-ids) — "X IDs are 64-bit unsigned integers generated using a system
called 'Snowflake.'" · "In JavaScript, integers are limited to 53 bits. This causes precision
loss with large IDs." v1.1 returns both `id` and `id_str`, "always use `id_str`"; v2 uses strings.
