# QA-034 — Mobile automation options: cross-platform vs. native

> Dossier, not lesson content. Every claim below must be re-read at source
> before it ships in a lesson.

- **Verdict:** PARTIAL

## a. Does the named source cover this?

No. `appium.io/docs/en/latest/` is the docs **Welcome page** — a nav index: one
definition ("an open-source project and ecosystem of related software, designed
to facilitate UI automation of many app platforms") plus a link list (Welcome ·
Blog · Introduction · Quickstart · Ecosystem · Reference · Guides · …). Checked
directly: **no comparison** against Espresso, XCUITest or Detox, **no discussion
of cross-platform vs. native trade-offs**. Worth zero of the 5h.

PARTIAL not WRONG-DOCUMENT only because the site behind it carries the Appium
half (§b) and the Quickstart delivers "run one sample project." But it is vendor
docs for one of four named tools, and vendor docs never argue the other side.
The comparison this task asks for has **no single primary source anywhere**.

## b. Best primary source

**Spine — Appium, "Appium Core"** (https://appium.io/docs/en/latest/intro/appium/):
the only page stating a *design philosophy* rather than an API. Its methodology
bullets are the lesson skeleton — open source, **vendor-provided tools**,
**unmodified apps**, standards. Appium is a wrapper, not an engine.

Then the three it wraps or competes with, in their own words. (The
**appium-espresso-driver README** — https://github.com/appium/appium-espresso-driver
— is the only primary text that puts two of them side by side.)

1. **Espresso** — https://developer.android.com/training/testing/espresso plus
   `/espresso/basics`: the `onView().perform().check()` triad, the sync contract,
   the "targeted at developers" line (§d).
2. **XCUITest** — Apple, *User Interface Testing* (https://developer.apple.com/library/archive/documentation/DeveloperTools/Conceptual/testing_with_xcode/chapters/09-ui_testing.html).
   Archived, but still Apple's clearest statement of *why* UI testing works as it
   does: XCTest + Accessibility, and the three classes.
3. **Detox** — https://wix.github.io/Detox/docs/introduction/getting-started/ plus
   the repo README: the gray-box argument, aimed at Appium's black-box model.

## c. What it leaves out

- **No decision framework anywhere.** Nobody publishes "choose X when Y." Appium
  has no guide comparing drivers; Espresso and XCUITest never mention each other
  or Appium; Detox compares itself only to an unnamed generic "black box."
- **The app-access requirement is never priced.** Detox's setup page lists Gradle
  edits, a `DetoxTest.java` androidTest class, ProGuard rules and a
  `network_security_config.xml`; the Espresso driver needs Gradle, matching
  signatures and **non-obfuscated class names**. No page draws the consequence:
  you cannot test the binary that ships to the store.
- **Who writes and owns the tests** — devs in-repo (Espresso/XCUITest/Detox) vs.
  a separate QA repo in any language (Appium). Usually the *real* deciding
  factor; no doc mentions it. Same for device farms, parallelism, CI cost.
- **Lock-in and rot, both undocumented.** Appium clients are JS/Java/Python/
  Ruby/C# but "each client is independently maintained" with differing coverage;
  Detox is JS/TS + Jest; Espresso Java/Kotlin; XCUITest Swift/Obj-C. The drivers
  table carries live ⚠️ flags (Windows 2022, Linux 2022, Tizen 2020) — re-read.
  Also: every "Detox vs Appium" search hit was a testing-vendor blog. Don't cite.

## d. Credible disagreement

**1. Appium vs. Detox — a real architectural fight, both sides on record.**
Appium: *"rely on automation tools that allow automation of unmodified apps
(prefer not to require the user to build in additional SDKs or software that
introduce discrepancies between the test version of the app and the production
version)."* Detox: *"the only way to tackle flakiness head on is by moving from
black box testing to gray box testing"* — by *"having access to the internals of
the app under test."* Same fact, opposite verdict: Appium treats in-app
instrumentation as a **fidelity risk** (you tested a build users never get),
Detox as the **only cure for flakiness**. Give the learner both; let them pick.

**2. Google contradicts itself, usefully.** Espresso: *"full power is unlocked by
those who are familiar with the codebase under test."* UI Automator: *"lets you
test an app from outside of the app's process… release versions with
minification applied."*

**3. The framing dissent — maybe don't do this at all.** Google Testing Blog,
Wacker, *"Just Say No to More End-to-End Tests"* (Apr 2015): roughly 70/20/10
unit/integration/E2E. A learner spending 5h picking a mobile E2E tool should hear
that the strongest expert position may be "write fewer, not pick a better runner."

## e. Worked examples worth adapting

- **Appium Quickstart, verbatim** — install server, `appium driver install
  uiautomator2`, then a JS test against the **built-in Android Settings app**
  (`appPackage: com.android.settings`, `appActivity: .Settings`,
  `automationName: UiAutomator2`) finding `//*[@text="Apps"]` by XPath and
  clicking it. No sample APK to source, no app build — the cheapest possible
  "run one sample project." Have the learner notice the locator is XPath on
  **visible text**, then ask what a localised build does to it.
- **Espresso's canonical triad**, on the same slide as that XPath:
  `onView(withId(R.id.my_view)).perform(click()).check(matches(isDisplayed()))`.
  `R.id.my_view` is a compile-time resource ID reachable only from inside the
  repo. That one diff *is* the lesson.
- **Apple's UI recording** — record a flow, read the generated `XCUIApplication`
  /`XCUIElement`/`XCUIElementQuery` code, then break it by deleting an
  accessibility identifier. Proves UI testing rests on XCTest **and
  Accessibility**: bad a11y = untestable app.
- **The obfuscation trap, as a 20-minute decision exercise.** Appium's Espresso
  driver requires *"The package under test must not have mangled class names"*
  plus a shared signature; UI Automator supports *"release versions with
  minification applied."* Hand the learner "test the build that ships to the
  store" and let the constraint pick the tool. Detox's mirror-image constraint:
  *"Runs on Devices: … (not yet supported on iOS)"* (re-verify).
- **Deliverable shape.** Four rows × six columns: needs app source? · needs
  unobfuscated build? · language & runner · platforms · who owns the tests · can
  it leave the app? Every cell fillable from §b; none from the named URL.

## Verbatim quotes

**Appium "Appium Core" — Methodology:** "As far as possible, rely on
vendor-provided tools for a given platform" · "…rely on automation tools that
allow automation of unmodified apps (prefer not to require the user to build in
additional SDKs or software that introduce discrepancies between the test
version of the app and the production version)". **Goals** include "Make
platform-specific automation capabilities available under a cross-platform,
standard API". **Nutshell:** Core / Drivers / Clients / Plugins.

**appium-espresso-driver README:** UiAutomator2 is "black-box", Espresso
"grey-box" — "the Espresso framework itself has access to the internals of
Android applications". Needs a Gradle build of the Espresso server; "Apps and
server must share the same digital signature"; "The package under test must not
have mangled class names". *Re-verify the v5 / Appium-3 requirement at source.*

**Espresso:** "targeted at developers, who believe that automated testing is an
integral part of the development lifecycle. While it can be used for black-box
testing, Espresso's full power is unlocked by those who are familiar with the
codebase under test." Sync waits until the message queue is clear, no `AsyncTask`
runs, and "All developer-defined idling resources are idle". **UI Automator:**
"lets you test an app from outside of the app's process. This lets you test
release versions with minification applied."

**Apple "User Interface Testing":** "UI tests rests upon two core technologies:
the XCTest framework and Accessibility." · "three new classes: XCUIApplication,
XCUIElement, XCUIElementQuery." (Archived Apple doc — still the clearest source.)

**Detox:** "an open-source end-to-end (E2E) testing framework for React Native
mobile applications" · "maximum velocity and zero flakiness" · "the only way to
tackle flakiness head on is by moving from black box testing to gray box testing"
· gray box = "having access to the internals of the app under test" · "Runs on
Devices: … (not yet supported on iOS)" — *re-verify*.

**Google Testing Blog, Wacker (Apr 2015):** "Although end-to-end tests do a better
job of simulating real user scenarios, this advantage quickly becomes outweighed
by all the disadvantages."
